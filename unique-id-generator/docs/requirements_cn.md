# 需求：唯一 ID 生成器

## 概述

一个 Python 唯一 ID 生成器库，实现了 System Design Interview 第 8 章中介绍的 Twitter Snowflake 方案。生成 64 位唯一 ID，可按时间排序、数值有序，适合分布式系统。支持可配置的位布局、每个数据中心/机器多生成器实例、时钟漂移处理、批量生成和 ID 解析。提供备用策略 (UUID v4、时间戳-随机) 用于对比和回退场景。

## 功能性需求

### FR-1：ID 生成 (Snowflake 算法)

系统应使用 Twitter Snowflake 方案生成唯一的 64 位 ID：

- **FR-1.1**：每个 ID 应为一个 64 位正整数 (符号位始终为 0)。
- **FR-1.2**：默认情况下，ID 应由以下部分组成：符号位 (1) + 时间戳 (41) + 数据中心 ID (5) + 机器 ID (5) + 序列号 (12)。
- **FR-1.3**：时间戳分量应表示自可配置自定义起始时间以来的毫秒数。
- **FR-1.4**：时间上较晚生成的 ID 应具有更高的数值 (可按时间排序)。
- **FR-1.5**：在同一台机器、同一毫秒内生成的 ID，其序列号应递增。
- **FR-1.6**：序列号应在每个新毫秒开始时重置为 0。
- **FR-1.7**：ID 应仅为数字 (不包含连字符、字母或特殊字符)。

### FR-2：位布局配置

- **FR-2.1**：时间戳、数据中心 ID、机器 ID 和序列号的位分配应可配置。
- **FR-2.2**：总位数 (不含符号位) 必须始终等于 63。
- **FR-2.3**：自定义起始时间应可配置 (默认值为项目特定起始时间，例如 2024-01-01T00:00:00Z)。
- **FR-2.4**：配置应校验所有位分配均为正整数且总和正确。
- **FR-2.5**：配置应校验数据中心 ID 和机器 ID 不超过其分配位宽可表示的范围。
- **FR-2.6**：默认配置应支持：41 位时间戳 (~69 年)、5 位数据中心 (32 个数据中心)、5 位机器 (每个数据中心 32 台机器)、12 位序列号 (每毫秒每台机器 4096 个 ID)。

### FR-3：多生成器支持

- **FR-3.1**：系统应支持创建多个生成器实例，使用不同的数据中心 ID 和机器 ID。
- **FR-3.2**：每个生成器实例应独立配置，拥有自己的位布局和起始时间。
- **FR-3.3**：来自不同生成器 (不同数据中心/机器组合) 的 ID 在无需协调的情况下应全局唯一。
- **FR-3.4**：系统应拒绝创建数据中心 ID 或机器 ID 超过配置位容量的生成器。

### FR-4：时钟处理

- **FR-4.1**：生成器应使用单调时间跟踪，确保 ID 始终递增。
- **FR-4.2**：如果系统时钟发生回拨 (检测到时钟漂移)，生成器应抛出带有漂移时长的 `ClockMovedBackwardsError`。
- **FR-4.3**：当序列号在一个毫秒内溢出 (超过已配置位宽的最大值)，生成器应等待下一毫秒后再生成下一个 ID。
- **FR-4.4**：时钟抽象层应同时支持系统时钟和单调时钟实现。
- **FR-4.5**：生成器应跟踪上次使用的时间戳，以检测时钟回拨。

### FR-5：批量生成

- **FR-5.1**：系统应提供 `generate_batch(count)` 方法，用于在一次调用中高效生成多个 ID。
- **FR-5.2**：批量生成的 ID 应保持所有唯一性和顺序性保证。
- **FR-5.3**：批量生成应比在循环中调用 `generate()` 更高效 (减少锁获取开销)。

### FR-6：ID 解析

- **FR-6.1**：系统应提供一个 `IDParser`，将 Snowflake ID 分解为其构成部分：时间戳、数据中心 ID、机器 ID 和序列号。
- **FR-6.2**：解析器应将提取出的时间戳转换回 Python `datetime` 对象。
- **FR-6.3**：解析器应使用与创建该 ID 的生成器相同的配置 (位布局、起始时间)。
- **FR-6.4**：解析器应返回一个结构化的 `ParsedID` 对象，包含所有已提取字段。

### FR-7：线程安全

- **FR-7.1**：生成器应安全地被多个线程并发使用。
- **FR-7.2**：线程安全应通过 threading 锁实现，用于保护序列号和时间戳状态。
- **FR-7.3**：锁的持有时间应尽可能短 (仅在状态变更期间持有)。

### FR-8：备用策略

- **FR-8.1**：系统应提供一个 UUID v4 生成器作为备用策略 (128 位随机，无顺序保证)。
- **FR-8.2**：系统应提供一个时间戳-随机生成器，通过组合毫秒时间戳前缀和随机位来实现简单性。
- **FR-8.3**：备用策略应实现公共接口以支持互换。
- **FR-8.4**：备用策略应记录其与 Snowflake 相比的权衡 (唯一性保证、可排序性、大小)。

## 非功能性需求

### NFR-1：性能

- **NFR-1.1**：生成器在单线程上每秒应能产生超过 10,000 个 ID。
- **NFR-1.2**：单个 ID 生成应在 1 毫秒内完成 (不包含等待下一毫秒的场景)。
- **NFR-1.3**：批量生成 1,000 个 ID 应在 100 毫秒内完成。
- **NFR-1.4**：多线程访问下的锁竞争不应将吞吐量降低到 10,000 ID/秒以下。

### NFR-2：唯一性保证

- **NFR-2.1**：在同一个生成器实例内 (相同数据中心 + 机器) 不得生成重复 ID。
- **NFR-2.2**：当数据中心/机器 ID 组合唯一时，跨不同生成器不得生成重复 ID。
- **NFR-2.3**：唯一性应在已配置起始时间的生命周期内成立 (41 位时间戳约为 69 年)。

### NFR-3：单调性

- **NFR-3.1**：同一个生成器实例生成的 ID 应严格单调递增。
- **NFR-3.2**：在较晚壁钟时间生成的 ID，其时间戳分量应高于较早生成的 ID (时钟漂移除外)。
- **NFR-3.3**：在同一毫秒内，ID 应按序列号排序。

### NFR-4：项目结构

- **NFR-4.1**：项目应使用 `pyproject.toml` 配合 hatchling 构建系统。
- **NFR-4.2**：项目应使用 src 布局 (`src/unique_id/`)。
- **NFR-4.3**：项目应要求 Python >= 3.9。
- **NFR-4.4**：项目应在各处包含类型提示。
- **NFR-4.5**：项目应包含使用 pytest 编写的单元测试。
- **NFR-4.6**：项目应包含使用 Hypothesis 编写的基于属性的测试。
- **NFR-4.7**：项目应提供演示基本用法和多生成器场景的示例。
