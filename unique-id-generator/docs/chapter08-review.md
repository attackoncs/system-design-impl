# 第 08 章原书核对

## 2026-11-09 持久化重启高水位

**做了什么**：新增可选 [HighWaterMark](../src/unique_id/high_water.py)，`SnowflakeGenerator(..., high_water=HighWaterMark(path, window_ms=1000))`。不传时行为与此前完全相同。下文“未实现持久化时间戳高水位”的边界由此关闭；身份租约、时钟同步与自动故障切换仍未实现。

**为什么**：原实现只在单个实例生命周期内拒绝回拨。进程在同一毫秒内重启，或重启时系统时钟已回拨，新实例的 `_last_timestamp` 从 -1 开始，会以相同身份重发旧ID。

**设计**：
- 文件只保存一个Unix毫秒上限。签发时间戳 `t` 超过已预留上限时，先持久化 `t + window_ms` 再发布状态；窗口内后续签发无I/O，每窗口最多一次写入。写入在生成器锁内完成，与既有加锁一致。
- 启动时读取上限；首次签发须满足 `t > 上限`。差距能在 `overflow_timeout_seconds` 内追上就有界等待（快速重启的常见情况），否则立即抛 `ClockMovedBackwardsError`（真实回拨不空等），调用方稍后重试。
- 文件缺失视为首次启动；内容损坏抛 `ValueError`，绝不当作“无历史”。

**崩溃安全论证**：写入顺序为临时文件→fsync→`os.replace` 原子替换→目录fsync（POSIX）。任一步骤失败都抛异常且不发布状态、不返回ID；任意时刻崩溃，磁盘上要么是旧上限要么是新上限，绝无半写文件。由于每个返回ID的时间戳 `t` 都满足 `t ≤ 已落盘上限`，且新实例只签发 `> 上限` 的时间戳，重启前后的ID区间不相交，与时钟是否回拨、是否同毫秒重启无关。代价：重启最多等待一个窗口；窗口越大写入越少、重启等待越长。

**边界**：一个文件只能属于一个 (datacenter_id, machine_id) 和一个存活实例；不做跨进程锁或身份租约。磁盘丢失/回滚到旧快照不在保护范围内。

**验证**：/tmp 一次性脚本（不入库）验证：每窗口只写一次；回拨5秒重启立即拒绝；时钟停滞时有界等待后拒绝；真实时钟连续三次快速重启（窗口200ms，等待约0.1–0.2秒）共15,020个ID无重复；8线程共享实例16,000个ID无重复；损坏文件被拒绝；无临时文件残留。既有测试 122 passed（`-W error`），未修改测试与基准代码。

## 使用和运行边界

`SnowflakeGenerator(config, clock, overflow_timeout_seconds=1.0)` 支持配置等待期限；0 表示耗尽时立即失败。只在容量耗尽时检查超时，不改变正常生成路径。批量失败之前产生的 ID 已被消耗，批量生成不提供事务回滚。

线程安全只覆盖同一个生成器实例。复用相同节点身份的多个实例、进程或重启实例可能生成重复 ID；本项目未实现分布式身份租约、持久化时间戳高水位或重启隔离。部署时必须保证身份唯一，并确保重启后的时间超过该身份最后成功生成 ID 的毫秒。不能把 MonotonicClock 当作跨进程的身份/时钟协调服务。

原书将时钟同步的实现明确放在范围之外；这里对回拨拒绝发号，不自动修正系统时间。高可用性仍依赖部署多个不同身份的生成器，未提供协调服务故障转移。4096 ID/ms 是位分配容量，不是经过压测的吞吐承诺；原书的 10,000 ID/s 应在目标环境另行压测。
