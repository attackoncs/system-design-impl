# 需求文档：限流组件（Rate Limiter）

## 概述

一个 Python 限流库，支持多种算法、可配置规则，以及本地（内存）和分布式（Redis）两种存储后端。Flask/FastAPI适配器生成HTTP拒绝响应与限流头；通用装饰器默认抛出异常，也可配置为返回响应字典。

## 功能性需求

### FR-1：多种限流算法

系统应支持以下限流算法，并可按规则选择：

- **FR-1.1**：Token Bucket（令牌桶）—— 允许最大桶容量内的突发流量，令牌以固定速率补充。适合可容忍短暂突发的 API。
- **FR-1.2**：Leaking Bucket（漏桶）—— 以固定速率排空虚拟占用量，立即决定是否接纳一个完整请求。真实FIFO匀速执行由独立、可选的进程内`LeakyBucketQueue`提供；限流判定算法不调度HTTP执行。
- **FR-1.3**：Fixed Window Counter（固定窗口计数器）—— 在固定时间窗口内（例如每分钟）统计请求数。简单且节省内存，但在窗口边界处可能允许高达 2 倍的限制量。
- **FR-1.4**：Sliding Window Log（滑动窗口日志）—— 为滚动窗口内每个已接纳请求保留时间戳和唯一成员；拒绝请求不追加日志。
- **FR-1.5**：Sliding Window Counter（滑动窗口计数器）—— 通过当前窗口与上一窗口计数的加权和来近似滑动窗口。在准确度与内存效率之间取得平衡。

### FR-2：存储后端

- **FR-2.1**：系统应提供内存存储后端，用于单进程部署，采用线程安全的数据结构。
- **FR-2.2**：系统应提供 Redis 存储后端，用于分布式部署，使用中心化 Redis 存储在多个限流实例之间同步状态。
- **FR-2.3**：存储后端应可互换，且无需修改限流逻辑（基于接口抽象）。

### FR-3：配置驱动的规则

- **FR-3.1**：限流规则应通过配置（Python dataclass）定义。
- **FR-3.2**：每条规则应指定：键类型（IP、用户 ID、自定义）、算法、限流值、时间窗口。
- **FR-3.3**：规则应支持通过 `update_rules()` 在运行时动态更新，无需重启服务。
- **FR-3.4**：同一接口可应用多条规则（例如按IP和按用户双重限制），顺序检查适用规则；任意拒绝即拒绝，返回最长重试延迟。先前规则已扣除的额度不做整组回滚。
- **FR-3.5**：每条规则可可选指定路径模式，以便针对特定接口进行限流。
- **FR-3.6**：每条规则可可选指定可读名称，便于识别。

### FR-4：集成方式

- **FR-4.1**：系统应提供 Python 装饰器（`@rate_limit`），用于函数级别限流。
- **FR-4.2**：系统应提供兼容 FastAPI/Starlette 的 ASGI 中间件。
- **FR-4.3**：系统应提供带有 `before_request` / `after_request` 钩子的 Flask 扩展。
- **FR-4.4**：集成层应能自动从请求中提取客户端标识（IP、用户 ID）。

### FR-5：HTTP 响应处理

- **FR-5.1**：框架适配器默认返回HTTP 429（Too Many Requests），也可配置其他4xx/5xx状态。通用装饰器默认抛异常；`raise_exception=False`返回字典，不是框架HTTP响应。
- **FR-5.2**：响应应包含 `X-RateLimit-Remaining` 响应头，表示剩余请求数。
- **FR-5.3**：响应应包含 `X-RateLimit-Limit` 响应头，表示允许的最大请求数。
- **FR-5.4**：开启响应头时，拒绝响应应包含`Retry-After`，取正整数相对秒数。
- **FR-5.5**：开启响应头时，`X-RateLimit-Reset`表示向上取整的算法相对重置时长。
- **FR-5.6**：`include_headers`和`auto_headers`两个开关同时约束放行与拒绝响应中的限流头。

### FR-6：限流键解析

- **FR-6.1**：默认按连接对端IP限流；仅在清理了转发头的可信代理之后显式开启`trust_forwarded=True`，才读取X-Forwarded-For。
- **FR-6.2**：支持应用提供的已认证身份或自定义解析器。凭证派生键使用稳定哈希；限流库不负责验证JWT、API key或session。
- **FR-6.3**：系统应支持通过可配置的键函数按自定义属性进行限流。
- **FR-6.4**：系统应支持组合多个提取器形成复合键（例如 IP + 接口路径）。
- **FR-6.5**：系统应支持按请求路径和 HTTP 方法进行限流。

### FR-7：容错能力

- **FR-7.1**：系统应支持可配置的 fail-open 行为：当存储（Redis）不可用时，允许请求继续（默认）。
- **FR-7.2**：系统应支持可配置的 fail-closed 行为：当存储不可用时，拒绝请求。
- **FR-7.3**：存储层故障应以警告级别记录，不应导致应用崩溃。

## 非功能性需求

### NFR-1：竞态条件安全

- **NFR-1.1**：Redis 操作应使用 Lua 脚本保证检查与递增的原子性，防止分布式环境中的竞态条件。
- **NFR-1.2**：内存存储后端应使用线程锁，保证并发访问时的线程安全。

### NFR-2：性能

- **NFR-2.1**：内存限流以低于1ms为目标，报告并发尾延时，不作普遍保证。
- **NFR-2.2**：稳态每条适用规则执行一次EVALSHA；首次使用/缓存丢失时额外执行SCRIPT LOAD和一次EVALSHA。一个请求可匹配多条规则。
- **NFR-2.3**：Redis 连接应支持可配置超时，防止连接故障时阻塞。

### NFR-3：可扩展性

- **NFR-3.1**：新算法应可通过实现 `BaseAlgorithm` 抽象基类进行添加。
- **NFR-3.2**：新存储后端应可通过实现 `BaseStorage` 抽象基类进行添加。
- **NFR-3.3**：自定义键提取函数应可通过 `key_func` 参数注入。

### NFR-4：项目结构

- **NFR-4.1**：项目应采用标准的 Python 打包方式（使用 hatchling 的 pyproject.toml）。
- **NFR-4.2**：项目应全面使用类型注解。
- **NFR-4.3**：项目应包含基于 pytest 的单元测试。
- **NFR-4.4**：项目应提供基础、FastAPI、Flask 三种集成的使用示例。

## 2026-10-27复审验收补充

规则必须应用key_type与query-free路径glob，复制配置并原子替换完整集合；
文件64KiB/100条、严格字段、无效更新保留旧规则。桶容量与稳态速率分离。
时钟在存储原子操作内采样并保留回退高水位，Redis必须采用TIME；返回值
严格校验。内存键数/巡查预算、Redis连接数/超时均有界，不自动重试扣额。
共享HTTP正文/整数重试头、两个开关及可配状态；可信代理须显式选择。
固定维度监控、可停止的轮询/有界FIFO、真实多进程Redis证据和迁移说明。
性能为实测目标，不保证所有并发场景1ms；详见benchmarks/REPORT.md。
日志明确只记录接纳请求，分布式HA/全球配额/持久队列仍不在当前实现范围。

## 2026-10-31复审验收补充

- 适用规则的字符串主体在两个检查入口中均须满足1–8192字符限制，非法输入不能扣额。
- 过深的规则JSON须保留原规则并记录错误，后续合法文件无需重启worker即可生效。
- 每个存储实例的脚本缓存须有界；NOSCRIPT恢复不能重置配额或破坏原子准入，
  超时/连接错误不能重放扣额。文档须说明冷缓存往返和Redis权限变化。
