# 设计：Proximity Service（邻近服务）

## 存储与发布

SQLite WAL（预写日志）按商家 ID、所有者、JSON 正文和墓碑标记存储草稿；公开记录保持不可变，并建有 `(precision, geohash, shard, business_id)` 索引；同时维护活跃版本元数据和幂等响应。写入使用 `BEGIN IMMEDIATE` 事务。发布操作在单个事务中复制所有存活草稿并构建六个前缀索引，随后切换版本、移除前一份快照。现有 WAL 读取器在其事务结束前仍可读取旧代数据。自动发布发生在下一次 UTC 日期之后的首次主读或变更操作时；调度器也可调用 CLI。当日首次变更会先冻结昨日草稿，再接受新变更。发布是按需触发的，而非持续运行的午夜定时任务。另有一个带鉴权的强制端点用于演示。

公开读取使用单个 SQLite 读事务，将元数据、候选集合和完整对象绑定到同一快照。两类缓存均包含 lineage（血缘）和 version（版本）标识。缓存为进程内有界 LRU，采用单调递增 TTL；旧条目不会泄漏到新快照。详情读取使用已发布数据，因此更新/删除操作同样具有延迟可见语义。变更仅限所有者执行；不存在草稿读取 API。重放键（replay key）按所有者、载荷哈希和方法/路径限定范围；响应与变更一同提交，过期记录在写入过程中被清理。分片数持久化在元数据中，服务重启不会静默改变查找位置。

## 地理计算

实现标准的经度/纬度交错 base32 geohash。默认精度从 6/5/5/4/4 开始，对应 500/1000/2000/5000/20000 米。使用保守的球面边界框来确定所有相交的网格单元，包含相邻单元。经度区间在 ±180 处跨越；触及极点的圆形会覆盖全部经度。若所需网格单元超过 4096，则降低精度直到有界。这避免了在高纬度地区使用固定 3×3 网格导致的假完整性假设。前缀索引得到的候选集合经过去重、水合，再用 haversine 距离（地球平均半径 6,371,008.8 米，数值容差 1 微米）过滤；距离和 ID 共同决定稳定排序。这里使用的是球面距离，不是道路距离或椭球大地测量距离。

索引按单元进行哈希分区，形成可配置的逻辑分片。本地 SQLite 后端将这些分区保存在同一个数据库中；不宣称物理分布式分片。按本章节建议，优先使用读副本而非物理分片。Quadtree（四叉树）能适应不均匀密度，但需要重建树和邻居遍历；S2 球面单元对极区失真处理更好，但需要额外的几何计算后端。

## 网络角色

主 HTTP 进程负责写入和快照发布。只读副本进程通过 HTTP 拉取带鉴权的 JSON 快照到独立的 SQLite 文件，原子安装并建立索引。主进程不可用时，副本继续服务其最近的完整版本；健康状态显示快照日期与版本号。拉取间隔控制数据新鲜度。快照协议包含 lineage ID 和单调递增版本；血缘不匹配或回滚会被拒绝。这是全量快照复制，不是 MySQL/PostgreSQL WAL 副本。副本导出仅包含公开商家，不包含所有者令牌、草稿和重放记录。

网关将公开读取请求路由到配置区域的副本列表，采用轮询策略，在传输失败/5xx 时重试。永远不会跨越配置的区域边界，也永远不会在写入操作上重试。单次查询的所有结果都来自同一副本；不同副本的版本可能不一致。游标版本冲突会被显式暴露，而不是静默重试。管理员/所有者访问使用常量时间的 Bearer 令牌比较。令牌从本地 JSON 配置加载，不会回显。HTTP 请求大小和缓存大小均有上限。副本和网关是只读的。

## 扩展与限制

营业时间窗口采用 UTC 星期/起始分钟/结束分钟区间；跨午夜的窗口必须拆分成多天。分页使用查询指纹、版本和偏移量；游标会被验证而非直接信任用于鉴权。不持久化精确位置，也不记录 HTTP 访问日志；仅记录聚合基准计时。生产部署需要 TLS、真实鉴权、所有者证明、区域本地数据存储、增量复制、感知健康的服务发现、监控、备份、高可用（HA）和物理分区部署。合成的本地测量数据既不代表真实地理部署，也不证明原书规模的 QPS。
