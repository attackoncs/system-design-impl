# 通知系统设计

本文对应第 11 章审查后的实际执行链。章节覆盖和部署边界见 [chapter11-review.md](chapter11-review.md)。

## 组件与资源归属

`NotificationService` 校验并解析请求，持有按用户分条带的接受锁、偏好、联系人、模板注册表、内存限频窗口和内容 TTL 去重器。它只负责接受入队。`create_worker_pool()` 将同一队列、偏好和 tracker 接给重试器及 worker，确保重试发送前也检查退订。

`MessageQueue` 按通道维护可用时间堆。底层 `dequeue()` 是取走任务；需要恢复的消费者应使用 `claim()/ack()/reschedule()`。worker 领取后保留容量，直到终态确认或原子转为延迟任务。旧领取凭据被拒绝，避免错误补偿将完成任务复活。

`SQLiteMessageQueue` 使用 `notification_jobs` 表实现相同契约。数据库修改通过 `asyncio.to_thread` 执行，实例内锁顺序提交，多实例通过 SQLite `BEGIN IMMEDIATE` 隔离事务。数据库使用 WAL、synchronous FULL，每次操作关闭连接，无额外后台调度任务需要关闭；监控深度使用同步快照查询。

`Provider.deliver(task)` 接收解析后的正文和本次 `task.endpoint`。单 worker 逐端点发送，并给每次调用设置超时；可配置多个 worker 并发。内置 provider 模拟投递。真实适配器需转换各厂商的响应，支持取消并实现外部幂等键。

## 接受流程

1. 校验请求类型、带时区的计划时间；取得用户条带锁，有业务事件 ID 时先查询已有接受记录。
2. 解析端点、检查偏好，校验基本邮件和电话号码格式。每次通知最多 100 个端点，解析后的标题加正文最多 1 MiB。
3. 模板仅解析一次，并复制请求中可变字典。已登记的平台筛选对应 token；旧无平台 token 仍兼容。
4. 检查该用户的通道额度与跨通道总额度。未传 `event_id` 时，检查单 service 实例的内容 TTL 去重，标题正文采用无歧义序列化。
5. 先记录本地 CREATED/QUEUED，再向 worker 暴露任务。入队成功后才占用额度和内容去重；拒绝记录本地 FAILED，不污染限频和去重。
6. SQLite 同一接受事务写通知任务、QUEUED 审计和可选唯一 `(event_id, recipient_id, channel)` 账本。容量包含计划及已领取任务。重复通过 `DuplicateNotificationError` 提供原通知 ID，终态完成后仍生效；正文改变的重放同样采用首次接受内容。

同一 service 的用户锁覆盖该用户所有通道；数据库唯一约束另外保护多个队列实例。限频窗口和元数据并未跨进程共享。接受期间取消可能发生数据库已提交、调用方未拿到响应的情况，上游应使用稳定事件 ID 重放。

## worker、租约及重试

SQLite 领取任务时设置随机凭据，原行在终态确认前一直保留；心跳续租，进程停止后租约到期可由其他 worker 重新领取。续期、重调度和确认均检查当前凭据及有效租约，旧领取者不能修改新领取者的任务。

数据库领取被取消时，等待事务结果并归还已成功领取的任务。若子领取任务刚完成、父 worker 正好收到取消，也显式归还，防止内存队列永久占用容量。worker 池串行 start/stop，拒绝重复 start，并回收部分启动后失败的 worker。

优雅停止完成当前投递，不会排空所有等待或计划任务；立即停止会取消并等待 worker，同时归还任务。provider 异常和超时进入重试。队列领取临时故障采用可中断且有上限的退避，避免 worker 退出或空转。

worker 调用重试器时使用 `defer=True`，原子增加尝试次数并写回未来可用时间，释放 worker 给其他就绪通知。重试器直接作为旧组件调用时保留等待退避的兼容行为。配置严格检查整数、有限正数等边界，退避指数先截断，避免大整数增长。

多设备成功端点、永久拒绝端点分别保存。普通重试只发送剩余暂时失败的端点；永久与暂时失败混合时继续处理可重试端点，最终有永久拒绝则整体 FAILED。端点进度在重调度时落盘，检查点前崩溃仍可能重发已联系端点。

## 审计、调度与 HTTP

SQLite 终态确认在同一事务中删除待处理任务并写终态审计。`SQLiteNotificationLog` 支持条件查询和保留期清理；尝试日志可能先出现 FAILED 尝试，再出现后续成功，不能把它当成终态状态机。`EventTracker` 是当前进程实时状态机，重试允许 `SENDING -> QUEUED`。

HTTP 示例持有持续运行的事件循环线程，将所有 service 操作提交给该循环，并启动 worker。所有请求需要共享 bearer key，限制 JSON 对象及 1 MiB 请求体，接受成功返回 202。`--database` 使队列和日志复用同一 SQLite 文件。偏好和模板修改也在所属循环执行；送达/点击回调更新内存状态，重启后的回调历史重建尚未完成。

`send(request, scheduled_at=aware_datetime)` 持久化到期时间。领取查询筛选就绪通知，因此未来任务不会阻塞即时通知。`depth()` 包含等待、计划及到期可重领任务，`in_flight()` 包含有效租约；分析接口提供通道积压和当前进程状态统计。

## 保证与部署边界

SQLite 接受成功后的任务可在进程退出、租约到期后恢复，投递语义为至少一次。外部服务接受和本地确认无法组成一个原子事务；事件去重避免重复接受，外部副作用还需适配器逐端点幂等。

本地 SQLite 写事务串行化，不提供复制消息代理、自动水平扩容、共享元数据数据库与缓存、跨进程限频或真实第三方渠道。联系人、偏好、模板和内存历史需在恢复 worker 前重建。外部告警送达、厂商回调签名、按客户授权、TLS 仍是部署集成。事件账本保留与审计清理独立，不声称生产吞吐量。
