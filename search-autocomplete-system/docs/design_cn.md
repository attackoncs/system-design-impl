# 设计：搜索自动补全系统

## 章节映射

本章将"采集/构建"与"在线服务"两部分解耦。本模块通过持久化 SQLite 事件日志、批量处理 Worker、不可变 Trie 快照、查询缓存、分片映射以及实际的 HTTP 查询副本/协调器来实现这一分离。

```text
已完成搜索 → 仅追加事件 → 时间窗口聚合 → 批量 Worker
                                                       |
                                    带版本的原子快照 + 分片映射
                                                       |
                                      分片副本：Trie + Top-5 节点缓存
                                                       |
客户端 → HTTP 协调器 → 相关分片副本 → 全局排名前 5 条
               |                        |
       当前已发布版本            持久化屏蔽规则 + 修订号
```

## 数据与一致性

已完成搜索事件携带调用方提供的事件 ID、归一化查询串以及 UTC 纪元时间戳。SQLite 事务会拒绝冲突的 ID 重复使用，并且确切的重试仅计数一次。建议查询本身不采集分析数据，调用方需另行记录已完成的搜索。批量聚合采用 `[start, end)` 半开区间，且并列排序是确定性的。

Collector 可按稳定事件 ID 哈希选择约 1/N 的已完成搜索，跨进程重试保持选择一致。
同一日志流应固定采样比例，频次代表实际采样数，不自动推算总体流量。
Store.aggregate 持久化窗口频次、过滤修订号和事件水位，aggregation 可在重启后
读取，build 可复用匹配窗口。文件数据库通过独立 WAL 读取事务固定输入；并发
写入进入下一批。内存数据库不支持 WAL，仅串行化输入读取。Trie 构造和 JSON
编码在存储写锁与缓存全局锁之外完成。

快照生成包含频次记录、按字典序平衡的分片范围以及构建窗口元数据。发布操作在单个事务中提交所有分片数据与当前激活版本。已有读者继续持有上一代不可变 Trie，直到新一代加载完成。无效构建不会切换活动指针。构建票据使代（Generation）ID 单调递增，失败可能留下间隙；较旧构建不能覆盖较新发布，过滤版本变更也会拒绝发布。旧代在途请求结束前仍保持可用。

接受后的事件内容不可变；过滤规则带单调修订号，立即覆盖缓存结果，缓存命中也
在返回前复核修订号。处理中规则变化可能返回不可用供重试。后续快照排除屏蔽词。
HTTP 查询携带协调器的版本号和规则修订号，副本不能服务该组合时返回不可用，
不会合并不同代的结果。
每个 Store 按持久修订号缓存不可变屏蔽集合；跨进程规则变更会触发刷新，热查询
不重复扫描全部屏蔽词，最终校验只读取一条修订元数据。

purge_blocked 是独立维护操作，删除被屏蔽源事件及全部预聚合工件；保留查询摘要
去重凭据，重启和重试不会重新写入被删事件。旧服务快照不修改，继续受实时规则
约束；显式解除屏蔽后仍保留该词的历史快照可能再次显示该词。源清理与历史快照
保留策略需要分别管理。

## Trie 与请求缓存

每条字符边构成前缀；终止节点携带查询和频次，每个节点缓存最佳五条。
常规查找为 O(前缀长度 + k)，其中前缀最多 50 字符，k=5。发布后的节点和子映射
均不可变。过滤补位使用优先队列和排名上界，剪去不可能胜出的分支；大量屏蔽时
仍可能访问整个匹配子树，并有堆操作开销，不保证过滤路径为常量时间。
过滤后的新快照恢复常规缓存路径。

LRU 条目包含版本号、规则修订号和前缀。清理/驱逐缓存不会影响持久化数据。Trie 由序列化后的频次记录重建，而非不可信的 pickle 文件。所有 HTTP 输入均有大小上限。
固定数量的分段锁合并冷加载，读取快照和构造 Trie 不占用全局 LRU 锁，已热查询
可以继续执行。容量按条目计数，不是严格的内存字节或 RSS 上限。

## 分片与副本

按字典序对查询排序，再分成查询条数大致相等的区间。分片映射存储包含的下界和不包含的上界。一个前缀区间可能跨多个分片；协调器仅向重叠分片扇出请求，并合并它们的 Top-5 列表。当排名和过滤规则一致时，从每个分片返回 Top-5 即可覆盖全局 Top-5。

分片查询节点暴露有界 HTTP GET。协调器重试副本，校验版本、规则修订、分片标识
和候选的字典区间归属。任一必要分片无有效副本则返回不可用，避免返回不完整排名。
HTTP 示例运行真实的独立本地进程。

所有未结束分片任务受 concurrency 限制；请求超时后仍执行的 I/O 继续占用槽位，
直到真正退出。总预算覆盖接入等待和副本切换，慢响应头/正文通过关闭套接字中断。
元数据读取也消耗预算，但 SQLite/Store 锁等待和系统 DNS 不能强制中断，可能超时
后才返回。close 拒绝新任务、取消排队工作并等待已有执行结束；HTTP server_close
等待活动处理线程后，CLI 才关闭数据库。

HTTP 使用 no-store。原书一小时浏览器缓存是可选优化，会遮蔽新的移除规则，
因此默认不启用；仅固定快照版本仍不能解决实时过滤失效问题。

## 目录布局与运行限制

`src/search_autocomplete/`：采集、Worker、Trie、存储、服务、HTTP 和 CLI。
`examples/`：本地批量/查询及多进程网络演示。
`tests/`：确定性正确性测试与真实 HTTP 故障切换测试。
`tools/benchmark.py`：可配置的本地延迟测量工具。

本实现基于 Python 标准库，目标为 Python 3.9+。SQLite 由本地进程共享，并非
分布式高可用存储，不应放到任意网络文件系统。生产部署需替换持久层、分散故障域，
增加认证和 TLS。SnapshotWorker 立即构建后通过 stop Event 等待下一周期，默认
窗口和间隔均为七天；SQLite 暂时失败或发布冲突五秒后重试，可选在构建前清理源。
周期状态不是持久分布式调度；重启会重新构建。停止阻止后续工作，当前构建允许
结束。历史事件、快照、聚合和去重凭据需配置保留策略。实时热点、多语言、地域
排名仍是后续扩展。详见 [章节核对](chapter14-review.md) 和 [Trie 核对](trie-review.md)。
