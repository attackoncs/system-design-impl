# 需求说明：分布式键值存储

## 概述

这是一个用 Python 实现的分布式键值存储系统，基于《System Design Interview》第 7 章的设计原则。系统使用一致性哈希（Consistent Hashing）在多个节点间分布数据，通过 Quorum 共识提供可调一致性，利用 Gossip 协议和 Hinted Handoff 处理故障，并采用基于 LSM-Tree 的存储引擎（Commit Log → MemTable → SSTable）实现持久化。节点间通过 gRPC 通信，系统复用本仓库中已有的 `consistent-hashing` 库。

## 功能需求

### FR-1：客户端 API

- **FR-1.1**：系统应提供 `put(key, value)` 操作，用于插入或更新键值对。
- **FR-1.2**：系统应提供 `get(key)` 操作，用于获取与键关联的值。
- **FR-1.3**：系统应提供 `delete(key)` 操作，使用 Tombstone 标记进行删除。
- **FR-1.4**：键应为字符串（最大 256 字节）；值应为不透明字节序列（最大 10 KB）。
- **FR-1.5**：客户端 API 应返回元数据，包括向量时钟版本和冲突状态。

### FR-2：数据分区（一致性哈希）

- **FR-2.1**：系统应使用已有的 `consistent-hashing` 库（`ConsistentHashRing`）进行数据分区。
- **FR-2.2**：每个键应通过在哈希环上顺时针遍历映射到一个主节点。
- **FR-2.3**：系统应支持添加和移除节点，并自动进行数据重分布。
- **FR-2.4**：应使用虚拟节点（Virtual Nodes）实现负载均衡（每个物理节点的虚拟节点数量可配置）。

### FR-3：数据复制

- **FR-3.1**：每个键值对应复制到 N 个节点（可配置，默认 N=3）。
- **FR-3.2**：副本应选择为哈希环上顺时针方向接下来的 N 个不同物理节点（通过 `get_nodes()` 获取）。
- **FR-3.3**：复制应采用异步模式 —— 协调者在收到 W 个确认后即返回。
- **FR-3.4**：在配置为多数据中心模式时，副本应放置在不同的数据中心。

### FR-4：可调一致性（Quorum 共识）

- **FR-4.1**：系统应支持配置 N（副本数）、W（写入 Quorum）和 R（读取 Quorum）参数。
- **FR-4.2**：写入操作在收到来自副本的 W 个确认后即视为成功。
- **FR-4.3**：读取操作应查询 R 个副本，并基于向量时钟比较返回最新值。
- **FR-4.4**：W+R>N仅表示稳定副本集合上的quorum交集；因果冲突、sloppy quorum和成员变化下不保证线性一致。
- **FR-4.5**：默认配置应为 N=3, W=2, R=2（quorum交集）。
- **FR-4.6**：系统应支持最终一致性模式（W=1, R=1），以适用于低延迟场景。

### FR-5：向量时钟与冲突解决

- **FR-5.1**：每个数据项应携带向量时钟（Vector Clock），形式为 `[(server_id, version_counter), ...]`。
- **FR-5.2**：写入时，协调者应在向量时钟中递增其自身条目。
- **FR-5.3**：系统应通过比较向量时钟检测冲突 —— 若两者互不支配，则存在冲突。
- **FR-5.4**：当不存在冲突时（一个版本支配另一个），系统应自动保留较新版本进行解决。
- **FR-5.5**：当存在冲突时（兄弟版本），系统应将所有冲突版本返回给客户端进行解决。
- **FR-5.6**：向量时钟长度应有界（最大条目数可配置，默认 10）；超限时裁剪最旧条目。

### FR-6：Gossip 协议（故障检测）

- **FR-6.1**：每个节点应维护成员列表，包含成员 ID 和心跳计数器。
- **FR-6.2**：每个节点应周期性递增自身的心跳计数器。
- **FR-6.3**：每个节点应周期性将成员列表发送给随机选取的部分对等节点。
- **FR-6.4**：若节点的心跳计数器在可配置超时时间（默认 5 秒）内未增长，则应标记为可疑/下线。
- **FR-6.5**：节点故障检测应通过 Gossip 协议传播至所有节点。
- **FR-6.6**：Gossip 间隔应可配置（默认 1 秒）。

### FR-7：宽松 Quorum 与 Hinted Handoff

- **FR-7.1**：当目标副本节点不可用时，系统应将请求路由到环上的下一个健康节点（宽松 Quorum / Sloppy Quorum）。
- **FR-7.2**：替代节点应存储数据，并附带指示预期接收者的提示（hint）。
- **FR-7.3**：当最初预期的节点恢复后，被提示的数据应被推送回该节点。
- **FR-7.4**：Handoff 成功后，提示数据应从替代节点删除。
- **FR-7.5**：Hinted Handoff 应周期性尝试（间隔可配置，默认 10 秒）。

### FR-8：反熵（Merkle Tree）

- **FR-8.1**：每个节点应在其键空间上维护一棵 Merkle Tree 用于不一致检测。
- **FR-8.2**：键空间应划分为可配置数量的桶（默认 1024 个桶）。
- **FR-8.3**：节点应周期性地与副本比较 Merkle Tree 根以检测不一致。
- **FR-8.4**：检测到不一致时，仅同步有差异的桶。
- **FR-8.5**：反熵同步间隔应可配置（默认 60 秒）。

### FR-9：存储引擎（LSM-Tree）

- **FR-9.1**：写入操作应首先持久化到 Commit Log（WAL）以确保持久性。
- **FR-9.2**：数据随后写入内存中的 MemTable（按键排序）。
- **FR-9.3**：当 MemTable 达到可配置的大小阈值（默认 4 MB）时，应刷新（flush）到磁盘，成为不可变 SSTable。
- **FR-9.4**：SSTable 应存储排序的键值对，并带有序引以实现高效查找。
- **FR-9.5**：系统应支持 SSTable 压缩（Compaction），合并多个 SSTable 并删除已删除条目。

### FR-10：读取路径

- **FR-10.1**：读取操作应首先检查 MemTable。
- **FR-10.2**：若 MemTable 中未找到，系统应查询 Bloom Filter 以确定哪些 SSTable 可能包含该键。
- **FR-10.3**：系统应从最新到最旧搜索候选 SSTable。
- **FR-10.4**：Bloom Filter 应具有可配置的误报率（默认 1%）。

### FR-11：节点通信（gRPC）

- **FR-11.1**：节点应通过 gRPC 使用 Protocol Buffers 序列化进行通信。
- **FR-11.2**：gRPC 服务应支持：Put、Get、Delete、Replicate、GossipExchange、HintedHandoff、MerkleTreeSync 操作。
- **FR-11.3**：每个节点应作为独立进程运行，拥有自己的 gRPC 服务器。
- **FR-11.4**：协调节点应通过 gRPC 客户端调用将请求转发给副本节点。

### FR-12：去中心化架构

- **FR-12.1**：系统应无单点故障 —— 每个节点拥有相同的职责集合。
- **FR-12.2**：任何节点都可以作为任何客户端请求的协调者。
- **FR-12.3**：节点应通过种子节点和 Gossip 协议互相发现。
- **FR-12.4**：系统应支持动态集群成员关系（节点加入和离开）。

## 非功能需求

### NFR-1：性能

- **NFR-1.1**：内存读取（MemTable 命中）应在 1ms 内完成。
- **NFR-1.2**：磁盘读取（带 Bloom Filter 的 SSTable）对单节点操作应在 10ms 内完成。
- **NFR-1.3**：本地持久化（Commit Log + MemTable）的写入操作应在 5ms 内完成。

### NFR-2：持久性

- **NFR-2.1**：所有写入应在确认前持久化到 Commit Log。
- **NFR-2.2**：数据应能在节点重启后通过重放 Commit Log 和加载 SSTable 得以恢复。
- **NFR-2.3**：Commit Log 应在 MemTable 成功 flush 到 SSTable 后进行截断。

### NFR-3：可扩展性

- **NFR-3.1**：系统应支持在不中断服务的情况下通过添加节点进行水平扩展。
- **NFR-3.2**：节点添加/移除时的数据重分布量应为总数据量的 1/N 比例。

### NFR-4：容错性

- **NFR-4.1**：当多达 N-W（或 N-R）个节点下线时，系统应保持读写可用。
- **NFR-4.2**：临时故障应通过宽松 Quorum 透明地处理。
- **NFR-4.3**：永久故障应通过反熵协议检测并修复。

### NFR-5：项目结构

- **NFR-5.1**：项目应使用标准 Python 打包方式（pyproject.toml，hatchling 构建系统）。
- **NFR-5.2**：项目应在所有位置包含类型注解。
- **NFR-5.3**：项目应包含单元测试和基于属性的测试，使用 pytest + hypothesis。
- **NFR-5.4**：项目应提供使用示例和演示脚本。
- **NFR-5.5**：要求 Python >= 3.9。


## 2026-10-27复审验收

W+R>N只表示稳定集合上的quorum交集，不保证线性一致或拓扑共识。
Merkle路径更新、分层元数据/有界分页、root变更中止、过大单条明确失败。
冻结输入，严格字段/int64/有限时间，物理记录时间单调，保留siblings/墓碑。
取消排空本地提交，fsync/原子发布先于截WAL；失败关闭FD、精确payload ACK、
损坏最终表拒绝启动。保留真实RPC、故障/重启和原始对照，不宣称全面提速。
自动供给/安全缩容/拓扑共识、大数据流式/缓存、跨机房运行保障仍未完成。
