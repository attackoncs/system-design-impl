# 需求文档：聊天系统

## 引言

实现仓库本地 `System Design Interview.md` 中的第 13 章 **设计一个聊天系统（Design A Chat System）**。遵循前几章采用的独立 Python 包结构。书中的 5000 万日活跃用户是架构设计目标，并非对这个单进程参考包的吞吐量声明。

## 术语表

- **频道（Channel）**：两人之间的单聊会话，或最多 100 名用户的群组。
- **会话（Session）**：属于某个用户和某个设备的已认证连接。
- **收件箱（Inbox）**：对用户可见的持久化有序消息引用。
- **游标（Cursor）**：设备已成功处理的最大消息 ID。
- **在线状态（Presence）**：是否至少有一台设备的心跳是新鲜的。
- **推送适配器（Push adapter）**：用于通知离线接收者的异步集成。

## 功能需求

### R1：认证与设备会话

**用户故事：** 作为用户，我可以连接多台设备，而不会冒充其他用户。

1. 令牌（Token）应在公开的 WebSocket 协议之外预配。
2. 无效或已吊销的令牌应导致认证失败。
3. 身份应来自已认证的会话，绝不能来自调用方提供的发送者字段。
4. 不同设备应能独立接收消息；同一设备重新连接应替换其旧会话。
5. 已关闭、被替换和已过期的会话应无法发送或检索消息。

### R2：单聊与群聊会话

**用户故事：** 作为参与者，我可以创建私密会话和小型群组。

1. 单聊频道应恰好包含两个不同的用户，且同一对用户应复用既有频道。
2. 群组应拥有 2 至 100 个不同成员（含创建者）。
3. 只有群主才能添加成员；重复添加应是无害的。
4. 只有成员才能发送消息或检索频道历史。
5. 新成员应收到加入之后发送的消息；更早的历史应保持私密。

### R3：文本投递、排序与重试

**用户故事：** 作为发送者，我可以在网络故障后重试，而不会产生重复消息。

1. 消息应包含非空文本，且少于 100,000 个字符。
2. 已提交的消息应有唯一的、递增的 ID 和一个时间戳。
3. 服务应在确认（acknowledgement）之前原子地持久化消息以及每个成员的收件箱条目。
4. 在内容/频道相同的情况下重用发送者的客户端消息 ID，应返回已有消息。
5. 以不同的内容/频道重用该 ID 应失败，且不产生任何变更。
6. 每台已连接设备（包括发送者的其他设备）都应收到实时事件。
7. 设备队列已满时，应关闭该会话并给出明确的重新同步指令。

### R4：持久化历史与设备同步

**用户故事：** 作为回访用户，我可以在重连或服务器重启后取回错过的消息。

1. 基于文件的存储应在重启后保留频道、成员关系、消息和收件箱。
2. 每台设备应提供自己的游标；服务器应返回 ID 更大的可访问消息。
3. 分页应按 ID 排序，且限制在 1–1,000 条消息之间；无效游标应导致失败。
4. 设备游标只有在客户端处理完一个同步分页后才应推进；仅有实时事件到达并不意味着之前所有消息都已处理。

### R5：在线状态

**用户故事：** 作为用户，我可以查看已订阅联系人的状态，且在短暂的网络中断期间不会出现离线闪烁。

1. 在线状态应聚合所有设备，并使用可注入的单调时钟。
2. 心跳缺失超过可配置的超时（默认 30 秒）应使设备过期。
3. 显式登出应立即关闭；传输层意外丢失应保留在线状态直至超时。
4. 客户端最多应订阅 100 个用户 ID，并接收在线/离线转换。
5. 在线状态订阅的授权委托给嵌入应用的联系人策略；本演示不包含社交图谱。

### R6：离线通知

**用户故事：** 作为离线接收者，我能收到新消息的通知。

1. 除发送者以外的离线接收者应针对每条新消息触发一次推送适配器。
2. 重试已有消息不应重复推送调用。
3. 推送失败不应撤销持久化，也不应阻止对发送者的确认；失败应被记录。
4. 默认适配器仅记录调用。真实提供方投递和持久化推送重试属于扩展工作。

### R7：发现与 WebSocket 传输

**用户故事：** 作为集成者，我可以将核心功能通过真实的 WebSocket 连接暴露出去。

1. 参考注册表应优先选择所请求的区域，然后是利用率最低的可用服务器。
2. 已满或已被移除的服务器不应被选中。
3. 可选适配器应通过 JSON 支持登录、心跳、频道创建、成员添加、发送、同步、历史查询、在线状态订阅和登出。
4. 每个请求都应收到带有其请求 ID 的响应；推送事件应与响应可区分。
5. 畸形或未授权的请求应产生受控错误，不暴露令牌或堆栈跟踪。
6. 传输层消息大小、认证超时和心跳清理应设有边界。

## 非功能需求

- Python 3.9+；核心仅使用标准库，可选 `websockets` 传输。
- 独立的 src 布局包，包含英文/中文 README、设计、需求、任务、示例和 pytest 测试。
- SQLite 是本地持久化适配器。另一个基于 Redis 的分布式模式应实现跨服务器路由和共享租约；两种模式都不声称已展示 5000 万用户规模。
- 测试应覆盖持久化重启、授权、重试、并发发送、游标分页、慢客户端、在线状态、推送失败、发现以及真实的 WebSocket 通信。
- 文档应说明仅限本地的默认行为、令牌预配、TLS 部署要求和恢复语义。
- 未经用户后续指示，不得提交（commit）或推送（push）。保留此前将 requirements/tasks 排除在提交之外的规则。

## 分布式扩展（用户要求的范围）

### R8：共享消息存储与消息代理

1. 独立的聊天进程应共享基于 Redis 的频道、成员关系、消息、有序的每用户收件箱以及发送者重试键。
2. 消息写入、收件箱扇出和持久化的消息代理（broker）发布应原子地发生。
3. 来自不同节点的写入应产生唯一且有序的 ID；在另一节点上的重试不应产生重复的消息或通知任务。
4. 每个聊天节点应独立消费持久化事件日志，并将事件路由到其本地已认证的设备；在入队之后持久化其事件游标。
5. Redis 调用应是异步的，使存储 I/O 不会阻塞事件循环。

### R9：共享在线状态、围栏与服务发现

1. 节点注册在租约未续期时应过期，使故障节点自动从发现和在线状态中移除。
2. 在线状态应聚合存活节点上的新鲜设备会话，包括连接到不同服务器的设备。
3. 同一设备在另一节点上重连应对旧连接进行围栏（fence）；旧连接后续的发送/心跳/登出不得影响替换后的会话。
4. 容量检查与会话注册应是原子的。
5. 发现 API 应返回可用的、按区域/容量优先的 WebSocket 端点。
6. 节点故障时，客户端应能发现替代节点、完成认证，并从保存的游标同步。应提供一个可执行的重连客户端。

### R10：持久化的离线通知处理

1. 消息提交应创建持久化的推送候选（push candidates）。独立的工作进程应在投递前检查共享在线状态，并确认已完成的任务。
2. 失败的通知任务在工作进程故障后应可被回收，并以有界延迟重试；耗尽的任务应转入持久化的死信流。
3. 提供一个可正常工作的 HTTP webhook 投递适配器，并使用稳定的幂等键；凭据和提供方端点从外部配置。
4. 默认的记录式投递应将其记录持久化在 Redis 中，并在工作进程重启后仍然保留。
5. 外部投递是至少一次（at-least-once）语义；提供方必须遵守幂等键，以防止在投递与确认之间发生崩溃后出现重复。

### R11：部署与分布式验证

1. 提供可运行的节点、发现、推送工作进程、令牌预配和重连客户端命令，以及带有持久化 Redis 存储的容器编排。
2. 针对真实 Redis 代理验证独立的操作系统进程：跨节点单聊与群聊、设备同步、共享在线状态、并发重试写入、过期会话围栏、租约故障转移、重连恢复以及工作进程重试。
3. 保留所有本地模式测试。记录 Redis 的可用性/持久性以及未经测试的容量限制，不声称具备自动 Redis 主库故障转移。

## 高可用与容量扩展

### R12：自动 Redis 故障转移

1. 后端客户端应可选地通过多个 Sentinel 端点发现可写主库，在晋升后重连，并且绝不从过期的副本读取历史。
2. 提供一个主库、两个启用 AOF 的副本以及三个法定票数（quorum）为 2 的 Sentinel 实例。
3. 可配置的复制确认应在与写入相同的连接上执行；确认超时应返回不确定/不可用的结果，允许使用相同消息幂等键重试。
4. 凭据、频道、成员关系和消息写入都应支持该确认。
5. 验证主库进程终止后真实的自动副本晋升、已确认消息的保留、继续发送，以及恢复后的幂等重试。
6. 记录异步复制的丢失窗口，避免零丢失/强一致性的声明。

### R13：容量与容错验证

1. 提供可配置的真实 WebSocket 负载工具，支持多节点、连接数、消息数、文本大小和并发发布者。
2. 记录实际准入的连接数、成功/错误消息计数、吞吐量、发送确认延迟百分位数、端到端投递百分位数、接收到的消息 ID 以及缺失/重复计数。
3. 负载测试应使用隔离的命名空间、有界队列和有限的请求超时。
4. 容量准入与发现应避免在每次登录或选择时扫描全部会话。
5. 验证在容量上限处的受控拒绝、通过 Redis 主库故障的恢复，以及在没有副本确认时不会出现虚假确认。
6. 报告所测试的硬件/进程布局和实测规模。笔记本电脑上的测试不得被描述为对 5000 万用户生产容量的证明。
