# Requirements: Consistent Hashing

## Overview

A Python consistent hashing library implementing the hash ring algorithm with virtual nodes for balanced key distribution across servers. Supports dynamic server addition/removal with minimal key redistribution, suitable for distributed systems like caches, databases, and load balancers.

## Functional Requirements

### FR-1: Hash Ring Core

- **FR-1.1**: Default SHA-1 uses full160-bit positions; MD5/SHA-256 use128/256 bits. Custom callables return integer positions without an imposed modulus.
- **FR-1.2**: The system shall map server nodes onto the hash ring by hashing their identifiers (e.g., "server-1", "192.168.1.1:8080") to positions on the ring.
- **FR-1.3**: The system shall map keys onto the hash ring by hashing the key string to a position on the ring.
- **FR-1.4**: The system shall resolve key-to-server lookup by traversing clockwise from the key's position until the first server node is found.
- **FR-1.5**: If no server node exists clockwise from the key's position (i.e., the key is past the last server on the ring), the system shall wrap around to the first server node on the ring.

### FR-2: Virtual Nodes

- **FR-2.1**: The system shall support virtual nodes (replicas) where each physical server is represented by multiple positions on the hash ring.
- **FR-2.2**: The number of virtual nodes per server shall be configurable (default: 150).
- **FR-2.3**: Virtual node positions shall be generated by hashing variants of the server identifier (e.g., "server-1#0", "server-1#1", ..., "server-1#149").
- **FR-2.4**: Key lookup shall treat virtual nodes identically to physical nodes — the first virtual node found clockwise maps back to its owning physical server.
- **FR-2.5**: The system shall allow per-server virtual node counts (weighted nodes) to assign more ring space to higher-capacity servers.

### FR-3: Server Management

- **FR-3.1**: The system shall support adding a server to the ring at runtime, placing its virtual nodes on the ring and redistributing only the affected keys.
- **FR-3.2**: The system shall support removing a server from the ring at runtime, removing its virtual nodes and redistributing only the affected keys to the next clockwise server.
- **FR-3.3**: Adding a server with N virtual nodes shall only affect keys that fall between the new virtual node positions and their preceding nodes on the ring.
- **FR-3.4**: Removing a server shall only affect keys that were assigned to that server — they move to the next clockwise server.
- **FR-3.5**: The system shall provide a method to query which keys would be redistributed when adding or removing a server.

### FR-4: Key Distribution and Lookup

- **FR-4.1**: The system shall provide a `get_node(key)` method that returns the server responsible for a given key.
- **FR-4.2**: The system shall provide a `get_nodes(key, count)` method that returns multiple distinct servers for a key (for replication), traversing clockwise and skipping duplicate physical servers.
- **FR-4.3**: The system shall provide a method to retrieve all keys assigned to a specific server.
- **FR-4.4**: The system shall provide statistics on key distribution across servers (count per server, standard deviation, min/max).

### FR-5: Configuration

- **FR-5.1**: The hash function shall be configurable (SHA-1 default, with support for MD5, SHA-256, or custom hash functions).
- **FR-5.2**: The virtual node count shall be configurable at ring creation time and per-server.
- **FR-5.3**: The system shall accept server identifiers as strings (hostnames, IP:port, or arbitrary labels).

### FR-6: Demonstration

- **FR-6.1**: The system shall include an example script demonstrating ring creation, key assignment, server addition/removal, and the resulting key redistribution.
- **FR-6.2**: The example shall print statistics showing distribution balance before and after topology changes.
- **FR-6.3**: The example shall visualize or report which keys moved when servers are added or removed.

## Non-Functional Requirements

### NFR-1: Performance

- **NFR-1.1**: Key lookup (`get_node`) shall complete in O(log N) time where N is the total number of virtual nodes on the ring, using binary search.
- **NFR-1.2**: Use immutable snapshots and copy/publication; report actual sort, mutation and planning costs instead of claiming inapplicable O(K log N).
- **NFR-1.3**: Exercise10000/50000 entries and report time/memory, without promising no scaling degradation.

### NFR-2: Correctness

- **NFR-2.1**: For a stable ring (no topology changes), the same key shall always map to the same server (deterministic).
- **NFR-2.2**: Verify add/remove locality; uniform equal-weight average movement is an expectation, not a hard cap.
- **NFR-2.3**: Measure sampled balance/memory without a universal20% CV bound or monotonic finite-sample improvement.

### NFR-3: Testing

- **NFR-3.1**: The project shall include unit tests using pytest covering all public methods.
- **NFR-3.2**: The project shall include property-based tests using Hypothesis to verify correctness invariants (determinism, minimal redistribution, balanced distribution).
- **NFR-3.3**: Tests shall verify that key redistribution on server add/remove is bounded and minimal.

### NFR-4: Project Structure

- **NFR-4.1**: The project shall follow the same structure as the rate-limiter module (pyproject.toml, src layout, tests, examples, docs).
- **NFR-4.2**: The project shall use standard Python packaging with hatchling.
- **NFR-4.3**: The project shall include type hints throughout.
- **NFR-4.4**: The project shall provide a README with usage instructions and algorithm explanation.
