# 分布式邮件参考设计

## 进程与数据归属

本地实验环境包含九个独立进程：一个 HTTP API 路由器、两个用户分片主库 HTTP 服务器、两个只读副本 HTTP 服务器、一个对象 HTTP 服务器、一个 SMTP 网关（带控制 HTTP 端点和接收处理线程），以及两个发送工作进程。API、副本与工作进程从不打开主库数据库，只通过 HTTP 访问。SMTP 网关与发送工作进程之间使用真实的 TCP SMTP 通信，与对象服务/邮箱主库之间使用 HTTP。只有损坏（corruption）测试会直接修改归属的对象文件。

用户放置规则为 `first_64_bits(SHA256(canonical_JSON(user))) % shard_count`。每个主库拥有独立的 SQLite WAL 数据库。持久化保存的分片/数量/角色元数据会拒绝不一致的启动。实验环境刻意把发送者放在分片 0、接收者放在分片 1，并不假设默认的人类可读账号名会均匀散列。配置定义了静态放置以及每个主库对应一个副本。未实现在线重分片（resharding）与自动提升（promotion）。

元数据包括所有者、不可变描述符、正文/对象键、附件描述符、文件夹、已读标志、版本、删除墓碑（tombstone）以及稳定的邮箱创建序列号。原始字节保存在对象服务中。主库还拥有上传归属引用、持久化发送回执、接收去重回执和出站队列。这些仅主库拥有的控制表不会从副本提升。

## HTTP 发送、对象暂存与持久化队列

客户端持有配置好的用户 Bearer 凭据。上传至多 2 MiB 的附件会创建一个以 SHA256 寻址的不可变对象，然后在用户主库中创建一条属于该用户的上传引用。发送请求接受 1–10 个已配置的本地收件人、一个主题、纯文本正文、至多三个附件上传 ID 以及一个稳定的请求键（request key）。调用者不能附加其他用户的上传。

发送服务先校验请求，并在元数据事务之前暂存正文/RFC MIME 对象。稳定的 `X-Delivery-ID`、Message-ID 和 MIME boundary 由发送者/请求键派生；每次队列重试都复用已保存原始对象中的 MIME 字节。主题中用于头部注入的换行符会被拒绝。SMTP 使用 RFC/MIME 处理的本地子集，而非完整的公网 MTA。经过 base64 膨胀之后，8 MiB 的完整 RFC 消息上限可能比各附件单独上限之和更严格。

已发送文件夹元数据、倒排索引条目（postings）、一个出站任务以及 `(user,request_key)` 回执在同一个 SQLite `BEGIN IMMEDIATE` 事务中提交。相同键/相同内容返回原始已发送 ID；内容变化则以 409 失败。由失败或并发重复提交暂存的对象可能变为无引用；由于对象按内容寻址且可能被共享，因此不做不安全的立即删除。对象 GC 与隐私/回执保留设计属于生产化工作。

每个发送任务都有持久化的尝试次数、到期时间、两秒租约（lease）和随机认领令牌。网络操作发生在元数据写事务之外。成功会将已发送副本更新为 `smtp-accepted`；这只表示网关已接受，**并不**证明每个收件人都已收到消息。失败会持久化错误信息和指数退避重试延迟（按当前指数上限封顶为 6.4 秒）。崩溃工作进程的租约可以被回收；过期令牌无法结算更新的认领。在对应的本地提交完成之前，任何队列回执都不会被确认。

## 本地 SMTP 与接收

发送工作进程只连接到已配置 SMTP 端口上的 `127.0.0.1`。它们使用 Python `smtplib`、带独立内部 SMTP 凭据的 AUTH PLAIN、MAIL/RCPT/DATA 以及持久化保存的 MIME。本地网关实现 EHLO、AUTH PLAIN、MAIL、RCPT、DATA、RSET 和 QUIT、点字符解除填充（dot unstuffing）、消息大小限制和命令顺序检查。它有意不作为生产级 SMTP 服务器：不存在 TLS、公网 MX、DNS、SMTPUTF8、DKIM、SPF、DMARC 或公网中继。发送者与收件人必须是已配置的 `local.test` 账户。CLI 服务器只绑定环回地址。

网关在回复 250 之前，先把原始数据放入对象服务，并持久化一个不可变的投递 ID、原始键、信封（envelope）和指纹。测试控制可以在提交之后回复 451，模拟确认丢失。发送者会重试完全相同的字节；网关接受匹配的重复投递而不创建新的 spool 条目。同一 ID 下内容冲突则失败。去重（Deduplication）使用经过认证的本地投递 ID，而不是任意的互联网 Message-ID 头。

一个由网关独有的接收线程处理其持久化的 spool。它解析有界的 MIME 部分、取回/校验对象、提取纯文本和附件、应用配置的扫描策略，并通过 HTTP 调用每个收件人的主库。收件箱条目 ID 对 `(recipient,delivery_id)` 是确定性的，持久化接收回执保护多收件人部分失败的重放。已删除的收件箱副本保留其回执和墓碑，因此投递重试无法使其复活。只有在所有收件人写入都成功之后，网关才把 spool 条目标记为完成。畸形 MIME/不支持的编码产生一条可检查的已拒绝 spool 行；瞬时的扫描/存储/邮箱故障保持待处理。网关重启会恢复保留的行；多网关写入者/接收循环归属或分布式 spool 故障转移均未提供。

## 扫描与隔离边界

`Scanner` 是一个显式的可替换接口。未配置策略时返回 `folder=quarantine, scan=unscanned, scan_engine=none`。这是配置生成时的默认值。不存在对"无恶意软件投递"的静默声明。

仅供合成测试使用的 `TestMarkerScanner` 在原始和解码后的载荷字节中搜索 `LOCAL_TEST_VIRUS_MARKER` 或 `LOCAL_TEST_SPAM_MARKER`。它报告 `scan_engine=test-markers-only`；其他消息报告 `test-policy-pass`，这**并不**意味着无病毒。第一个标记触发隔离，第二个标记路由到垃圾邮件。它不检查归档文件，也不识别真实的恶意软件/垃圾邮件。仅测试用的扫描器不可用开关会让消息持久化排队等待重试。未集成任何第三方扫描器，也不做任何准确性声明。被隔离的已接收附件无法通过用户 API 下载；未实现自动释放/重新扫描工作流。

## 对象与授权

对象服务以十六进制 SHA256 键存储内容，采用暂存写入、文件 flush/fsync 和原子替换。每次 GET 都会对照键校验存储的字节，HTTP 客户端会再次校验。已存在的损坏对象会直接失败，而不是静默返回被篡改的数据。对象上限 8 MiB，单次上传上限 2 MiB。该服务要求内部 Bearer 令牌。普通用户无法获取任意键：API 首先加载一条未删除且属于该用户的消息、检查隔离策略、选定一个被引用的附件，然后在内部取回。类似路径的键会被拒绝。下载文件名只是元数据，绝不会决定对象文件系统路径。

单一对象服务和 spool 不做复制。因此当对象存储故障时，元数据副本可用并不代表正文/附件可用。没有加密、用户配额、字节范围流式传输、对象复制、归档生命周期或共享对象垃圾回收器。JSON/base64 传输会带来复制开销，在本参考实现中是有界的；大型生产对象路径应当使用字节流。

## 已读标志、分页与搜索

邮件正文不可变。已读状态和删除请求要求精确的当前版本；过期更新返回 409。读到过期副本的客户端必须先刷新主库再重试写入。ID 是不透明的，所有者过滤是每条消息/附件查询的一部分。其他用户收到 404。静态令牌是身份集成边界，不是完整的认证服务。管理员令牌只操作模拟器控制，不会静默冒充邮箱所有者。

邮箱顺序使用稳定的每分片创建序列。`before` 分页至多返回 50 封邮件，且新邮件到达时不会移动更旧的页。游标不是并发编辑的全局快照。支持的文件夹为 inbox、sent、spam 和 quarantine；已读过滤是精确匹配。

倒排索引具有 `(mail,field,term)` 条目以及 field/term 查找索引。Unicode `\w+` 大小写折叠（casefold）分词很简单，不做词干提取、子串匹配或语言感知切分。搜索最多接受五个词项和 100 个查询字符；所有词项必须出现在所选字段中（`all` 则为跨字段任意位置）。一封邮件最多 4096 个唯一的字段-词项对。主题、信封发件人和纯文本正文会被索引。附件内容和 HTML 渲染/搜索不在范围内。主库元数据/索引变更共享同一个事务，包括删除时的索引移除；不存在主库索引更新延迟窗口。副本最终会应用相同的词项和墓碑，因此副本搜索可能滞后。

## 元数据复制与故障转移语义

主库的每次变更都会在与邮件写入相同的事务中追加一条带校验和保护的元数据/索引变更。副本通过 HTTP 拉取某个持久化序列之后的变更。每页至多 100 条条目和大约 2 MiB 的载荷预算（单条条目可能用完整个预算）。副本检查分片分配、来源世系（lineage）、连续序列和校验和；它原子地应用邮件行、词项和自己的检查点。重复项被忽略。缺口、世系变化或损坏会停止推进并暴露错误。没有日志修剪；新副本可以从零重放。

读取会暴露 `lineage`、`position` 以及所选的主库/副本来源。路由器优先读取主库，仅在可用性错误时回退到配置的副本，或者客户端可以请求 `replica=true`。权威的 404/409 响应不会被较旧的副本掩盖。主库不可用时，副本可以继续提供其最后的持久化状态，即使其轮询状态显示错误。这明确允许过期的邮件、已读标志和删除可见性。没有读己之写（read-your-writes）屏障，也不声明线性一致读。写入绝不会故障转移到副本，也没有选举/脑裂提升。

只有邮箱元数据和 postings 会复制；发送队列、上传归属和去重控制表保留在主库上。因此副本无法安全地替代丢失的主库提供写服务。进程重启测试保留全部本地磁盘。生产可靠性需要复制的主库存储/控制表、复制的对象/spool、选举/防护（fencing）协议、隐私生命周期和多主机验证。最初的十亿用户/10 万发送 QPS 目标并未被这个本地实验证明。
