# 设计：分布式消息队列（Distributed Message Queue）

## 角色与安全边界
单个持久化的 HTTP 协调器（coordinator）持有主题元数据、分区 epoch/高水位（high water mark）、生产者回执、消费者租约/游标以及事务可见性。
三个独立的 broker 各自拥有独立的磁盘目录。所有用户操作都经过协调器；broker 仅接受经过认证的内部操作。
协调器通过锁和 SQLite 事务对发布/选举进行串行化。
这使 epoch 与提交元数据具有权威性，而无需假装本参考实现实现了分布式共识（consensus）。协调器不可用会停止读/写；必须恢复其数据库。这是一个有意为之的可用性瓶颈，并非生产级高可用（HA）。

## 分段（Segments）
每个分区代（generation）都拥有只追加（append-only）的编号分段文件。一个帧（frame）包含 magic、负载长度、CRC32 以及规范 JSON 信封，其中含有 offset、时间戳、生产者元数据、正文、键、延迟、前一哈希与 SHA-256 链式哈希。索引旁车文件（index sidecar）记录每个 offset/文件位置，并在打开时从已验证的帧重建。
日志负载按需读取。末尾被撕裂（torn）的帧会被截断；完整的 CRC/哈希校验失败属于损坏，绝不能被静默丢弃。每次被接受的追加都会对分段和索引执行 fsync。epoch/基准检查点与代指针使用原子替换。进程崩溃恢复已测试；不宣称在所有 Windows 文件系统上都具备掉电/目录 fsync 保证。

## 发布与复制
协调器在网络写入之前为每个分区记录一个待处理批次（pending batch）。该日志保证在响应丢失后可以精确重试。leader/follower 对齐到已提交前缀（committed prefix）并追加同一批次。落后的副本将验证过的保留前缀安装到新代中，然后原子地交换其指针。
已追上的副本构成该操作的 ISR（同步副本集合）；在高水位推进之前，需要所有已确认的成员加上配置的多数派。不可达的副本从该操作中排除，但绝不低于多数派。这是基于法定人数（quorum）的参考复制，并非 Kafka 完整的动态 ISR 协议。

leader 选举在协调器已提交的高水位处探测前缀哈希。只有合格的副本才能成为 leader；epoch 递增及随后的同步会隔离（fence）过期请求。未提交的尾部在重用之前会被截断/覆盖。任何 broker 都无法独立发布或确认用户操作，因此被隔离的旧 leader 无法使数据可见。仅 leader 应答意味着已暂存/本地持久化，而非可见或达到 quorum 持久化；一旦 quorum 恢复，后台重试会将其提交。
协调器的待处理日志是一份额外的持久副本，但不做复制。no-ack 是客户端的即发即弃（fire-and-forget）适配器，没有重试/确认契约。

## 消费者与事务
成员关系基于租约（lease），按排序后的成员 ID 进行确定性的轮询（round-robin）分配。
加入/替换/过期一个会话会使组代（group generation）递增，并使投递边界失效。提交要求当前会话、代、所有权、存活的租约，以及不晚于已投递位置的 offset。至少一次（at-least-once）拉取不改变游标；至多一次（at-most-once）在返回之前持久化游标。延迟的首条记录会阻塞同一分区中后续的记录，以保持顺序。

事务处理先暂存输出批次，复制所有批次，然后在同一个 SQLite 事务中原子地推进它们的高水位与源组游标。txid 加请求指纹（fingerprint）对该操作去重。协调器崩溃后，未完成的事务阶段会被中止并保持不可见；broker 上未提交的尾部将在下一次写入时修复。这保证的是本参考实现内部的原子可见性，而非任意的数据库/邮件副作用。重试与死信辅助工具使用这同一边界；归档回放有意分配新的 offset，并不是恰好一次（exactly-once）的恢复协议。

## 保留与运维
默认保留 14 天，可选保留字节上限。offset 下限仅随已提交记录推进；物理删除会移除完整的旧分段，活跃分段可能保留更久。链检查点随下限一起推进。
过期的消费者收到 410 并显式重置；不会静默跳过。低于下限的回执行会被移除，同时生产者序列水位（watermark）防止旧重试再次生产。租约、待处理复制与清理在活跃期间运行。
共享客户端凭据是面向可信客户端的实验室简化。生产环境需要 TLS、按主题的 ACL、配额、共识元数据、增量追赶、有界的待处理日志/回执、可观测性、备份以及持续的负载/混沌验证。
