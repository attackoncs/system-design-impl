# 22 广告点击事件聚合

随着 Facebook、YouTube、TikTok 以及网络媒体经济的兴起，数字广告在广告总支出中所占的份额越来越大。因此，跟踪广告点击事件至关重要。本章将探讨如何设计一个达到 Facebook 或 Google 规模的广告点击事件聚合系统。

在深入技术设计之前，我们先了解在线广告的核心概念，以便更好地理解这个主题。在线广告的一大核心优势是其效果可以衡量，而实时数据使这种衡量能够量化。

数字广告有一个称为实时竞价（Real-Time Bidding，RTB）的核心流程，用于买卖数字广告资源。图1展示了在线广告流程的运作方式。

![程序化广告生态的简化示意图，展示需求方与供给方主要参与者之间的信息流。左侧为“需求方”，广告主发起流程，并与需求方平台 DSP（Demand Side Platform）交互，由 DSP 帮助购买广告资源。DSP 将广告请求发送至广告交易平台，后者是买卖广告资源的中心市场。右侧为“供给方”，媒体发布方提供广告资源，并连接供给方平台 SSP（Supply Side Platform），由 SSP 管理广告资源的销售。SSP 将广告资源报价发送至广告交易平台。广告交易平台作为枢纽，将 DSP 的广告请求与 SSP 提供的广告资源相匹配，最终决定向用户展示哪些广告。箭头表示各组件之间的信息传递方向。](https://bytebytego.com/images/courses/system-design-interview/ad-click-event-aggregation/figure-1-rtb-process-5E2OUEKS.svg)

图1　实时竞价流程

实时竞价流程的速度非常重要，因为整个过程通常要在不到一秒内完成。

数据的准确性同样非常重要。广告点击事件聚合对于衡量在线广告效果至关重要，而广告效果实质上决定了广告主需要支付多少费用。根据点击聚合结果，广告投放负责人可以控制预算或调整竞价策略，例如更改目标受众群体、关键词等。在线广告使用的关键指标，包括点击率（click-through rate，CTR）\[1\] 和转化率（conversion rate，CVR）\[2\]，都依赖聚合后的广告点击数据。

## 第1步：理解问题，明确设计范围

下面这些问题有助于澄清需求并缩小设计范围。

**候选人**：输入数据是什么格式？

**面试官**：数据是分布在不同服务器上的日志文件，最新的点击事件不断追加到日志末尾。事件具有以下属性：_ad\_id、click\_timestamp、user\_id、ip_ 和 _country_。

**候选人**：数据量有多大？

**面试官**：每天10亿次广告点击，广告总数为200万条。广告点击事件量每年增长30%。

**候选人**：需要支持哪些最重要的查询？

**面试官**：系统需要支持以下3类查询：

-   返回某条广告在最近 _M_ 分钟内的点击事件数。
    
-   返回过去1分钟内点击次数最多的100条广告。这两个参数都应可配置。每分钟执行一次聚合。
    
-   对上述两类查询，支持按 _ip_、_user\_id_ 或 _country_ 进行数据筛选。
    

**候选人**：需要考虑边界情况吗？我能想到以下几种：

-   有些事件的到达时间可能晚于预期。
-   事件可能重复。
-   系统的不同部分可能随时发生故障，因此需要考虑系统恢复。

**面试官**：这些情况列得很好。是的，需要将它们纳入考虑。

**候选人**：对延迟有什么要求？

**面试官**：端到端延迟为几分钟。请注意，实时竞价与广告点击聚合的延迟要求很不一样。由于实时竞价需要快速响应，延迟通常必须低于一秒；广告点击事件聚合主要用于广告计费和报表，因此几分钟的延迟是可以接受的。

根据以上信息，我们可以整理出功能需求与非功能需求。

### 功能需求

-   聚合某个 _ad\_id_ 在最近 _M_ 分钟内的点击次数。
    
-   每分钟返回点击次数最多的100个 _ad\_id_。
    
-   支持按不同属性对聚合数据进行筛选。
    
-   数据集达到 Facebook 或 Google 的规模，详细的系统规模要求见下文的粗略估算。
    

### 非功能需求

-   聚合结果的正确性很重要，因为这些数据将用于实时竞价和广告计费。
    
-   妥善处理延迟到达或重复的事件。
    
-   健壮性。系统应能承受局部故障。
    
-   延迟要求。端到端延迟最多为几分钟。
    

### 粗略估算

我们先做一些估算，了解系统规模以及需要解决的潜在挑战。

-   日活跃用户数（DAU）为10亿。
    
-   假设每位用户平均每天点击1条广告，则每天产生10亿条广告点击事件。
    
-   广告点击 QPS = 10^9 条事件 / 每天约10^5秒 = 10,000。
    
-   假设广告点击峰值 QPS 为平均值的5倍，则峰值为50,000 QPS。
    
-   假设单条广告点击事件占用0.1 KB存储空间，则每天需要的存储空间为0.1 KB \* 10亿 = 100 GB；每月约为3 TB。
    

## 第2步：提出总体设计，达成共识

本节将讨论查询 API 设计、数据模型和总体设计。

### 查询 API 设计

API 设计的目的是让客户端与服务端就交互方式达成约定。在面向消费者的应用中，客户端通常是使用产品的最终用户。而在我们的场景中，客户端是通过仪表盘向聚合服务发起查询的用户，例如数据科学家、产品经理、广告主等。

为了更好地设计 API，我们先回顾一下功能需求：

-   聚合某个 _ad\_id_ 在最近 _M_ 分钟内的点击次数。
    
-   返回最近 _M_ 分钟内点击次数最多的前 _N_ 个 _ad\_ids_。
    
-   支持按不同属性对聚合数据进行筛选。
    

只需两个 API 就能支持这三种用例，因为最后一项筛选需求可以通过在请求中添加查询参数实现。

应该存储原始数据还是聚合数据？我们的建议是两者都存。下面说明原因。

-   保留原始数据很有价值。如果出现问题，可以用原始数据进行调试。如果某个严重缺陷破坏了聚合数据，修复缺陷后就能根据原始数据重新计算聚合结果。
    
-   聚合数据也应存储。原始数据量非常大，直接查询原始数据效率很低。为缓解这个问题，我们对聚合数据执行读取查询。
    
-   原始数据用作备份。通常只有在需要重新计算时才会查询原始数据。较旧的原始数据可以迁移到冷存储中，以降低成本。
    
-   聚合数据是日常使用的活跃数据，会针对查询性能进行优化。
    

#### 选择合适的数据库

选择数据库时，需要评估以下问题：

-   数据是什么样的？是关系型数据、文档，还是二进制大对象（blob）？
    
-   工作负载是读密集型、写密集型，还是两者兼有？
    
-   是否需要事务支持？
    
-   查询是否依赖 SUM、COUNT 等大量联机分析处理（OLAP）函数 \[3\]？
    

先看原始数据。虽然正常运行时不必查询原始数据，但数据科学家或机器学习工程师可以利用它研究用户响应预测、行为定向、相关性反馈等问题 \[4\]。

根据粗略估算，平均写入 QPS 为10,000，峰值可达50,000，因此系统是写密集型的。在读取方面，原始数据主要用于备份和重新计算，因此理论上读取量较低。

关系型数据库也能完成任务，但扩展写入能力可能比较困难。Cassandra、InfluxDB 等 NoSQL 数据库针对写入和时间范围查询做了优化，因此更加合适。

另一种选择是采用 ORC \[5\]、Parquet \[6\] 或 AVRO \[7\] 等列式数据格式，将数据存入 Amazon S3。可以限制每个文件的大小，例如10 GB；负责写入原始数据的流处理器在达到上限时切换到新文件。考虑到许多读者可能不熟悉这种配置，本设计以 Cassandra 为例。

聚合数据本质上是时间序列数据，其工作负载同时具有读密集和写密集的特点。这是因为需要每分钟查询数据库，向客户展示每条广告最新的聚合计数。这项功能有助于自动刷新仪表盘，或及时触发告警。由于广告总数为200万条，因此读取负载很重。聚合服务每分钟还要聚合并写入数据，所以写入负载也很重。可以采用同一类型的数据库来存储原始数据和聚合数据。

查询 API 和数据模型已经讨论完毕，接下来将它们组合成总体设计。

### 总体设计

在实时大数据 \[8\] 处理中，数据通常以无界数据流的形式流入和流出处理系统。聚合服务的工作方式也是如此：输入是原始数据，即无界数据流，输出是聚合结果，见图2。

![数据处理流水线。最左侧为输入阶段，其中的日志监视器将数据推送至处理阶段的数据聚合服务。该服务对数据进行聚合，计算并输出两种指标：每分钟聚合的广告计数，以及每分钟聚合的点击次数最多的100条广告。输出阶段将这些聚合指标写入数据库。最后，展示阶段的查询服务查询数据库，读取并展示聚合数据。数据沿从左到右的方向单向流动，虚线将输入、处理、输出和展示阶段分隔开。](https://bytebytego.com/images/courses/system-design-interview/ad-click-event-aggregation/figure-2-aggregation-workflow-ILOBUVRV.svg)

#### 异步处理

当前设计采用同步处理，这并不理想，因为生产者和消费者的处理能力不总是相等。考虑这样一种情况：流量突然增加，生成的事件数远超消费者的处理能力，消费者可能出现内存不足错误，或意外关闭。同步链路中只要有一个组件故障，整个系统就会停止工作。

常见的解决方案是引入消息队列，例如 Kafka，将生产者与消费者解耦。这样，整个流程就变成异步处理，生产者和消费者也能够独立扩容。

结合前面的讨论，可以得到图3所示的总体设计。两个消息队列将日志监视器、聚合服务和数据库解耦。数据库写入器从消息队列轮询数据，将其转换成数据库要求的格式，然后写入数据库。

图6　Map 操作

你可能想问，为什么需要 Map 节点？另一种办法是配置 Kafka 分区或标签，让聚合节点直接订阅 Kafka。这种办法可行，但输入数据可能需要清洗或规范化，这些操作可以由 Map 节点完成。另外一个原因是，我们未必能够控制数据的生成方式，因此具有相同 _ad\_id_ 的事件可能落入不同的 Kafka 分区。

**Aggregate 节点**

Aggregate 节点每分钟在内存中按 _ad\_id_ 统计广告点击事件。在 MapReduce 模型中，Aggregate 节点属于 Reduce 阶段。因此，map-aggregate-reduce 实际上意味着 map-reduce-reduce。

**Reduce 节点**

Reduce 节点将所有 Aggregate 节点的聚合结果归并为最终结果。例如，图7中有三个聚合节点，每个节点都保存自己内部点击次数最多的3条广告。Reduce 节点将这些结果归并，最终只保留点击次数最多的3条广告。

![用于找出最近一分钟点击次数最多的3条广告的数据处理流水线。流程始于 Aggregate 阶段的三个方框，分别包含广告标识及点击计数：第一个为 ad1:12、ad3:5、ad2:3，第二个为 ad7:9、ad10:4、ad8:3，第三个为 ad13:8、ad11:4、ad15:3。三个方框通过箭头连接到 Reduce 阶段，由其合并数据。Reduce 方框中的结果为 ad1:12、ad7:9、ad13:8，即点击计数最高的三项。随后箭头指向 Output 阶段，其中写明：最近一分钟点击次数最多的3条广告是 ad1、ad7、ad13。Aggregate 阶段左侧明确标有任务“取前3名”。](https://bytebytego.com/images/courses/system-design-interview/ad-click-event-aggregation/figure-7-reduce-node-7MQQ64OQ.svg)

图7　Reduce 节点

DAG 模型描述了广为人知的 MapReduce 模型。其设计目标是利用并行分布式计算，将海量数据转化为较小或常规规模的数据。

在 DAG 模型中，中间数据可以存放在内存里。运行在不同进程中的节点通过 TCP 通信，运行在不同线程中的节点则可以通过共享内存通信。

-   返回最近 \_M_ 分钟内点击次数最多的前 _N_ 个 ad_ids。
    
-   数据筛选。

### 流处理与批处理

图3提出的总体架构属于流处理系统。表17对比了三类系统 \[12\]：

| **服务（在线系统）** | **批处理系统（离线系统）** | **流处理系统（近实时系统）**           |
| ---------------------------- | --------------------------------- | ------------------------------------------------------ |
| **响应性**           | 快速响应客户端     | 不需要向客户端返回响应                       |
| **输入**                    | 用户请求                     | 有限大小的有界输入，数据量较大 |
| **输出**                   | 返回给客户端的响应              | 物化视图、聚合指标等           |
| **性能衡量指标**  | 可用性，                     |                                                        |
| 延迟                      | 吞吐量                        | 吞吐量、延迟                                    |
| **示例**                  | 在线购物                   | MapReduce                                              |

表17　三类系统的对比

本设计同时使用流处理和批处理。数据一到达，就通过流处理以近实时的方式生成聚合结果；历史数据备份则采用批处理。

如果一个系统同时具有批处理与流处理两条处理路径，这种架构就称为 Lambda 架构 \[14\]。Lambda 架构的缺点在于，需要维护两条处理路径，也就意味着需要维护两套代码。Kappa 架构 \[15\] 将批处理和流处理合并为一条处理路径，解决了这个问题。其核心思想是，使用同一个流处理引擎处理实时数据，并持续重新处理已有数据。图10对比了 Lambda 架构和 Kappa 架构。

![Lambda 与 Kappa 两种数据处理架构的对比。上半部分为 Lambda 架构：从文件摄取原始数据，经表示摄取层的大圆柱后分为两条并行路径，一条进入批处理层的批处理引擎，另一条进入流处理层的实时引擎。两条路径最终为服务层中的服务后端提供数据，由服务后端响应查询请求。两路处理结果存入结果数据库，原始数据也单独保存。下半部分为更简单的 Kappa 架构，只使用流处理层：原始数据被摄取后，由流处理层的实时引擎处理，再直接进入服务层的服务后端响应查询。处理后的数据存入结果数据库，原始数据另行保存。两种架构都通过数据存储组件保存原始和处理后的数据。主要区别在于，Lambda 同时使用批处理与实时处理来改善延迟及容错，Kappa 则只依靠实时处理，以追求速度和简洁。](https://bytebytego.com/images/courses/system-design-interview/ad-click-event-aggregation/figure-10-lambda-and-kappa-architectures-QONSAGXY.svg)

有时必须重新计算聚合数据，这也称为历史数据重放。例如，如果发现聚合服务存在严重缺陷，就需要从引入该缺陷的时刻开始，根据原始数据重新计算聚合结果。图11展示了重新计算的流程：

2.  将读取的数据发送到专用聚合服务，以免历史数据重放影响实时处理。

### 时间

聚合需要使用时间戳。时间戳可以在两个不同的位置生成：

-   事件时间：广告点击实际发生的时刻。
    
-   处理时间：处理点击事件的聚合服务器的系统时间。
    

由于网络延迟以及异步环境的影响，数据需要经过消息队列，事件时间与处理时间之间可能相差很大。如图12所示，事件1很晚才到达聚合服务，晚了5小时。

![系统中事件时间与处理时间的对比。图中有两条水平时间轴，分别标注事件时间与处理时间。事件时间线上，事件1、2、3分别发生于第30、60、90秒。处理时间线上也显示相同事件，但存在延迟：事件1在事件发生的同一时刻被处理，事件2从第60秒开始处理，事件3从第90秒开始处理。垂直虚线在两条时间轴上标出30、60、90秒位置，实线箭头表示时间前进。在主时间轴结束5小时之后，还有一个单独的浅粉色圆圈标为1，通过虚线箭头相连，表示某个处理事件可能是批处理，在最初事件发生很久之后才进行。](https://bytebytego.com/images/courses/system-design-interview/ad-click-event-aggregation/figure-12-late-events-XK3WSQ7H.svg)

图12　迟到事件

如果采用事件时间聚合，就必须处理迟到事件；如果采用处理时间聚合，结果则可能不准确。没有完美的解决方案，因此需要权衡。

| **优点**        | **缺点**                                                     |
| --------------- | ------------------------------------------------------------ |
| 事件时间      | 聚合结果更准确，因为客户端确切知道广告被点击的时刻 |
| 处理时间 | 服务器时间戳更可靠                            |

### 交付保证

由于聚合结果用于计费，数据准确性和完整性至关重要。系统需要能够回答以下问题：

-   如何避免重复处理事件？
    
-   如何确保所有事件都得到处理？
    

Kafka 等消息队列通常提供三种交付语义：至多一次（at-most-once）、至少一次（at-least-once）和恰好一次（exactly-once）。

**应该选择哪种交付方式？**

在大多数场景中，如果可以接受少量重复，至少一次处理就足够了。

但我们的系统并非如此。数据中几个百分点的差异，就可能导致数百万美元的金额偏差。因此，建议本系统采用恰好一次交付。如果想了解真实广告聚合系统的更多细节，可以参考 Yelp 的实现 \[17\]。

### 数据去重

数据重复是最常见的数据质量问题之一，其来源多种多样。本节讨论其中两种常见来源。

-   客户端。例如，客户端可能多次发送同一个事件。对于恶意发送的重复事件，最好由广告反欺诈或风控组件处理。有兴趣可以阅读参考资料 \[18\]。
    
-   服务器故障。如果聚合服务节点在聚合过程中宕机，而上游服务尚未收到确认，相同的事件就可能被重新发送并再次聚合。下面具体分析。
    

图17展示了聚合服务节点 Aggregator 故障如何引入重复数据。Aggregator 通过在上游 Kafka 中保存偏移量，管理数据消费状态。

![数据聚合系统的时序图，包含上游、Aggregator 聚合器、下游三个主要组件。上游以“1. 轮询事件”消息启动流程，聚合器随后通过“2. 消费数据”消息向上游获取数据，再执行“3. 聚合事件”，内部可能进行循环。完成后，聚合器通过“4. 发送聚合结果”将结果送到下游；下游以“5. 返回确认”确认接收，聚合器再通过“6. 确认上游消费”通知上游。步骤6旁的叉号表示该处可能发生数据丢失或需要错误处理，底部的“数据重复”文字提示冗余数据问题。组件之间的虚线表示异步通信。](https://bytebytego.com/images/courses/system-design-interview/ad-click-event-aggregation/figure-17-duplicate-data-3OV4V7EK.svg)

图17　重复数据

如果第6步失败，例如聚合器宕机，那么偏移量100到110之间的事件虽然已经发送给下游，但新的偏移量110尚未持久化到上游 Kafka。此时，新聚合器仍会从偏移量100开始消费，导致已经处理过的事件被再次处理，从而产生重复数据。

最直接的解决办法是使用 HDFS 或 S3 等外部文件存储记录偏移量，如图18所示。但该方案仍然有问题。

![上游、聚合器、HDFS/S3 和下游四个组件的数据交互时序图。上游先发送“1. 轮询事件”，聚合器通过“2. 消费数据”获取数据。接着，聚合器与 HDFS/S3 交互执行“3.1 校验偏移量”，然后执行“3. 聚合事件”，内部可能循环，再通过“3.2 保存偏移量”将状态写入 HDFS/S3；图中特别突出显示了保存偏移量可能导致消息问题。聚合器随后执行“4. 发送聚合结果”，下游返回“5. 确认”，最后聚合器向上游发送“6. 确认消费”。虚线表示异步通信，带箭头的实线表示消息方向；红色文字突出关键步骤，尤其是保存偏移量时可能产生的问题。](https://bytebytego.com/images/courses/system-design-interview/ad-click-event-aggregation/figure-18-record-the-offset-S65QC3DH.svg)

图18　记录偏移量

在第3步中，只有外部存储记录的最新偏移量为100时，聚合器才会处理偏移量100到110之间的事件。如果外部存储记录的偏移量已经是110，聚合器就忽略偏移量110之前的事件。

但这个设计存在严重问题：在向下游发送聚合结果之前，就先将偏移量保存到了 HDFS/S3，即第3.2步。如果聚合器宕机导致第4步失败，新启动的聚合节点就永远不会处理偏移量100到110之间的事件，因为外部存储记录的偏移量已经是110。

为了避免数据丢失，需要在收到下游确认之后再保存偏移量。更新后的设计如图19所示。

![上游、聚合器、HDFS/S3 和下游之间的数据流时序图。上游先发送“1. 轮询事件”，聚合器通过“2. 消费数据”接收数据，随后与 HDFS/S3 交互执行“3.1 校验偏移量”。校验后，聚合器执行“3. 聚合事件”，内部以循环表示处理操作，再通过“4. 发送聚合结果”将结果送至下游。下游返回“5. 确认”，聚合器这时才在 HDFS/S3 保存更新后的偏移量，即“5.1 保存偏移量”，最后向上游发送“6. 确认消费”。虚线代表异步通信，实线箭头指示消息及其流向。](https://bytebytego.com/images/courses/system-design-interview/ad-click-event-aggregation/figure-19-save-offset-after-receiving-ack-ISTJJLCH.svg)

图19　收到确认后保存偏移量

在这个设计中，如果聚合器在执行第5.1步之前宕机，偏移量100到110之间的事件仍会被再次发送给下游。为了实现恰好一次处理，需要将第4步到第6步之间的操作放进同一个分布式事务。分布式事务是跨多个节点执行的事务；只要其中某个操作失败，整个事务都要回滚。

![事件处理系统的数据流时序图，包含上游、聚合器、HDFS/S3 和下游四个组件。流程从上游向聚合器发送“轮询事件”开始，聚合器再向上游请求消费数据。接着，聚合器在 HDFS/S3 校验偏移量（3.1），聚合事件（3）后，在分布式事务中向下游发送聚合结果（4），并将偏移量保存到 HDFS/S3（5）。下游向聚合器返回确认，聚合器最终向上游确认消费。虚线表示异步通信，实线表示同步交互，图中展示了各组件在事件处理中的职责与数据流。](https://bytebytego.com/images/courses/system-design-interview/ad-click-event-aggregation/figure-20-distributed-transaction-7V2ITRYZ.svg)

图20　分布式事务

可见，在大规模系统中进行数据去重并不容易。实现恰好一次处理是一个进阶主题，详细内容可以参考资料 \[19\]。

### 系统扩展

根据粗略估算，业务每年增长30%，流量大约每3年翻倍。如何应对这种增长？下面逐项分析。

本系统包含消息队列、聚合服务、数据库三个独立组件。由于这些组件已经解耦，可以分别扩展。

#### **扩展消息队列**

“分布式消息队列”一章已详细讨论如何扩展消息队列，这里只简要介绍几个要点。

**生产者**。生产者实例数量不受限制，因此很容易扩展生产者。

**消费者**。在消费者组内，可以通过增删节点和再均衡机制扩展消费者。如图21所示，增加两个消费者后，每个消费者只需处理一个分区的事件。

![消息队列消费者组再均衡的前后对比。左侧初始状态中，一个主题分为分区0、1、2、3，两个消费者各消费多个分区：消费者0负责分区0和1，消费者1负责分区2和3。中间标为“再均衡”的大箭头将前后状态分开。右侧仍是相同主题及四个分区，但现在消费者0、1、2、3各自只消费一个分区；粉色高亮用于突出增加两个新消费者后的状态。分区与消费者之间的箭头指示各分区向所分配消费者的数据流。](https://bytebytego.com/images/courses/system-design-interview/ad-click-event-aggregation/figure-21-add-consumers-BXUUD54I.svg)

图21　增加消费者

当系统中有数百个 Kafka 消费者时，消费者再均衡可能相当缓慢，耗时几分钟甚至更长。因此，如果需要增加消费者，尽量选择非高峰时段，以降低影响。

**Broker**

-   **哈希键**
    
    > 使用 _ad\_id_ 作为 Kafka 分区的哈希键，使同一个 _ad\_id_ 的事件存入同一 Kafka 分区。这样，聚合服务只需订阅一个分区，就能获取该 _ad\_id_ 的所有事件。
    
-   **分区数量**
    
    > 如果分区数量发生变化，同一个 _ad\_id_ 的事件可能被映射到不同分区。因此，建议预先分配足够的分区，避免在生产环境中动态增加分区数。
    
-   **主题的物理分片**
    
    > 通常仅有一个主题是不够的。可以按地理区域拆分数据，例如 topic\_north\_america、topic\_europe、topic\_asia；也可以按业务类型拆分，例如 topic\_web\_ads、topic\_mobile\_ads。
    
    -   优点：将数据拆分到不同主题有助于提高系统吞吐量。每个主题的消费者减少后，消费者组再均衡的耗时也会缩短。
        
    -   缺点：会引入额外复杂性，并增加维护成本。

#### 热点问题

如果某个分片或服务接收的数据远多于其他分片或服务，就称其为热点。大公司可能有数百万美元的广告预算，其广告被点击得更频繁。由于事件按 _ad\_id_ 分区，某些聚合服务节点收到的广告点击事件可能远超其他节点，进而导致服务器过载。

可以为热门广告分配更多聚合节点来缓解这一问题。下面看图25中的例子，假设每个聚合节点最多只能处理100条事件。

1.  由于原聚合节点收到了300条事件，已经超过节点处理能力，因此向资源管理器申请额外资源。
    
2.  资源管理器分配更多资源，例如再增加两个聚合节点，使原节点不至于过载。
    
3.  原聚合节点将事件拆成3组，每个聚合节点处理100条。
    
4.  将结果写回原聚合节点。
    

![采用类似 MapReduce 架构的数据处理流水线。输入进入 Map 组件，再将“ad1，300条事件”送至 Aggregate 组件。该聚合组件资源不足，在步骤1向资源管理器申请资源，并在步骤2获得额外资源。随后在步骤3中，将300条事件拆分给三个 Aggregate 组件，每个处理100条事件；三者的结果送入 Reduce 组件，并在步骤4归并后回传给最初的 Aggregate 组件。最后，初始聚合组件再连接另一个 Reduce，生成聚合输出。虚线框突出显示三个聚合组件并行处理、再归并的过程，展示通过分发负载扩展大规模数据处理的方式。](https://bytebytego.com/images/courses/system-design-interview/ad-click-event-aggregation/figure-25-allocate-more-aggregation-nodes-KLEMMHRW.svg)

### 容错

下面讨论聚合服务的容错。由于聚合在内存中进行，聚合节点宕机时，聚合结果也会丢失。可以通过重放上游 Kafka Broker 中的事件重建计数。

从 Kafka 的起点重放数据很慢。较好的做法是将上游偏移量等系统状态保存为快照，并从最新保存的状态恢复。本设计中的系统状态不只有上游偏移量，还需要保存最近 _M_ 分钟内点击次数最多的前 _N_ 条广告等数据。

图26用一个简单示例展示了快照中的数据。

### 数据监控与正确性

如前所述，聚合结果可以用于实时竞价和计费。监控系统健康状况并确保结果正确至关重要。

#### 持续监控

可以考虑监控以下指标：

-   延迟。各阶段都可能引入延迟，因此在事件流经系统不同部分时记录时间戳非常有价值。不同时间戳的差值可以作为延迟指标暴露出来。
    
-   消息队列大小。如果队列大小突然增加，可能需要增加聚合节点。注意，Kafka 是以分布式提交日志实现的消息队列，因此应监控 records-lag，即记录积压指标。
    
-   聚合节点的系统资源，例如 CPU、磁盘、JVM 等。
    

#### 对账

对账是比较不同数据集，以确保数据完整性。银行业可以将自身记录与银行记录进行核对，而广告点击聚合没有第三方结果可供核对。

可以在每天结束时运行批处理任务，按事件时间对每个分区的广告点击事件排序，再将计算结果与实时聚合结果核对。如果准确性要求更高，可以采用更小的聚合窗口，例如一小时。请注意，不论使用哪种聚合窗口，批处理任务的结果都可能与实时聚合结果不完全一致，因为某些事件可能延迟到达，详见“时间”一节。

![数据聚合与报表系统架构。日志监视器把数据送入消息队列，数据聚合服务消费队列，每分钟聚合广告计数和点击最多的100条广告，并将结果交给数据库写入器，由其写入原始数据数据库。消息队列还连接另一个专门执行重新计算的数据聚合服务；该服务与重新计算服务交互，重新计算服务和原始数据数据库一起为对账组件提供数据。聚合数据库保存汇总后的数据，由查询服务（仪表盘）读取并生成报表。聚合数据库同时接收初始数据库写入器和重新计算服务的数据，以保证数据一致性与准确性。](https://bytebytego.com/images/courses/system-design-interview/ad-click-event-aggregation/figure-28-final-design-Z676QMSA.svg)

### 另一种设计方案

## 第4步：总结

本章介绍了如何设计一个达到 Facebook 或 Google 规模的广告点击事件聚合系统，涵盖以下内容：

-   数据模型与 API 设计。
    
-   使用 MapReduce 模型聚合广告点击事件。
    
-   扩展消息队列、聚合服务和数据库。

-   持续监控系统。
    
-   通过对账确保结果正确。
    
-   容错。
