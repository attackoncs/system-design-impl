# 18 附近的朋友

本章为移动应用的新功能“附近的朋友”设计一个可扩展的后端系统。用户主动开启该功能并授权访问位置后，移动客户端会显示地理位置相近的朋友列表。若想了解现实案例，可参考介绍 Facebook 类似功能的文章 \[1\]。

图1　Facebook 的“附近的朋友”功能

如果读过“邻近服务”一章，可能会疑惑：两者看起来相似，为什么还要专门设计“附近的朋友”？仔细分析就会发现关键区别：邻近服务中的商家地址是静态的，位置不会变化；而“附近的朋友”数据更动态，用户位置会频繁变化。

## 第1步：理解问题，明确设计范围

Facebook 规模的后端系统都很复杂。开始设计之前，需要通过提问澄清需求，缩小设计范围。

**候选人**：地理位置多近才算“附近”？

**面试官**：5英里，这个数值应该可配置。

**候选人**：能否假设距离是两个用户之间的直线距离？现实中，两人之间可能隔着河流，实际通行距离会更长。

**面试官**：可以，这个假设合理。

**候选人**：应用有多少用户？能否假设总用户数为10亿，其中10%使用“附近的朋友”？

**面试官**：可以，这个假设合理。

**候选人**：是否需要保存位置历史？

**面试官**：需要。位置历史可以用于机器学习等多种用途。

**候选人**：能否假设朋友超过10分钟不活跃，就从附近朋友列表中消失？还是需要显示最后已知位置？

**面试官**：可以假设不再显示不活跃的朋友。

**候选人**：需要考虑隐私及 GDPR、CCPA 等数据法规吗？

**面试官**：问得好。为了简化问题，这里暂不考虑。

### 功能需求

-   用户能够在移动应用中查看附近的朋友。列表中的每一项都包含距离和时间戳，时间戳表示距离最近一次更新的时间。
    
-   每隔几秒更新附近朋友列表。
    

### 非功能需求

-   低延迟。应及时收到朋友的位置更新，避免过长延迟。
    
-   可靠性。系统整体需要可靠，但可以接受偶尔丢失个别数据点。
    
-   最终一致性。位置存储不需要强一致性，不同副本之间的位置数据延迟几秒可以接受。
    

### 粗略估算

先进行粗略估算，确定方案需要应对的规模与挑战。约束及假设如下：

-   “附近的朋友”指位于5英里半径范围内的朋友。
    
-   位置刷新间隔为30秒。人的步行速度较慢，平均每小时3至4英里，30秒内移动的距离不会显著影响该功能。
    
-   平均每天有1亿用户使用“附近的朋友”。
    
-   假设并发用户占日活跃用户的10%，因此并发用户数为1000万。
    
-   用户平均有400位朋友，假设这些朋友都使用该功能。
    
-   应用每页显示20位附近的朋友，可按请求加载更多。
    

| **计算 QPS**     |
| --------------------- |
| -   > 日活跃用户1亿 |

-   > 并发用户数：10% \* 1亿 = 1000万。
    
-   > 用户每30秒报告一次位置。
    
-   > 位置更新 QPS = 1000万 / 30 ≈ 334,000|

## 第2步：提出总体设计，达成共识

本节讨论以下内容：

-   总体设计。
    
-   API 设计。
    
-   数据模型。
    

其他章节通常先讨论 API 和数据模型，再介绍总体设计。但本题需要向所有朋友推送位置数据，客户端与服务端之间未必只使用简单的 HTTP 协议。不了解总体设计，就很难确定 API 的形式，因此先讨论总体设计。

### 总体设计

从总体上看，本题需要高效传递消息。用户希望收到每位活跃且在附近的朋友的位置更新。理论上可以完全采用点对点方式：用户与附近每一位活跃朋友都保持持久连接，如图2所示。

![七部手机构成的网状网络拓扑图。每部手机以圆圈内的简单图标表示，连线代表通信链路。手机没有按特定几何图形排列，而以不规则、去中心化的方式互联，每部手机都与网络中多部其他手机建立连接。图中没有标签、URL或参数，重点展示网状网络的多对多连接特征，各设备可以直接或经多条路径彼此通信。](https://bytebytego.com/images/courses/system-design-interview/nearby-friends/figure-2-peer-to-peer-TDFPCCFK.svg)

图2　点对点通信

移动设备的连接有时不稳定，功耗预算也很紧张，因此这种方案并不实用，但它为总体设计提供了方向。

更实际的方案是使用共享后端，如下所示：

![用户通过后端与朋友A、朋友B、朋友C交互的简化架构图。云形图标代表后端，每位用户由圆圈中的手机图标表示。发起者标为用户，接收者分别标为朋友A、B、C。箭头显示用户将信息发送到后端，后端再将其分发给三位朋友，体现从用户经后端到朋友的单向广播或分发机制。](https://bytebytego.com/images/courses/system-design-interview/nearby-friends/figure-3-shared-backend-JI6MRFAF.svg)

图3　共享后端

图3中的后端有哪些职责？

-   接收所有活跃用户的位置更新。
    
-   每次位置更新时，找出所有应接收更新的活跃朋友，并转发到他们的设备。
    
-   两位用户间的距离超过阈值时，不向接收方设备转发更新。
    

这听起来很简单，问题在哪里？要做到大规模并不容易。系统有1000万活跃用户，每人每30秒更新一次位置，即每秒334K次更新。若平均每人有400位朋友，并假设其中约10%在线且在附近，那么后端每秒需要转发334K \* 400 \* 10% ≈ 1400万次位置更新。转发量非常大。

#### 设计方案

先提出一个适用于较小规模的后端总体设计，再在深入设计中进行扩展优化。

图4展示了能满足功能需求的基本方案，下面逐一介绍其组件。

![移动应用系统架构。移动用户通过 HTTP 和 WebSocket（WS）连接负载均衡器，由其将请求分发到 WebSocket 服务器或 API 服务器。WebSocket 服务器处理双向位置信息，与 Redis 发布/订阅系统及位置缓存通信，并直接访问位置历史数据库。API 服务器负责用户管理、朋友关系管理及身份验证，连接用户数据库。两类服务器都使用位置缓存提升性能。箭头表示数据方向和交互类型，例如双向位置信息。用户数据库和位置历史数据库保存持久数据，位置缓存则加速访问常用信息。](https://bytebytego.com/images/courses/system-design-interview/nearby-friends/figure-4-high-level-design-35BO5JE4.svg)

图4　总体设计

#### 负载均衡器

负载均衡器位于 RESTful API 服务器和有状态、双向通信的 WebSocket 服务器之前，将流量均匀分配到这些服务器。

#### RESTful API 服务器

这是一个无状态 HTTP 服务器集群，负责典型的请求/响应流量，API 请求流程见图5。该层处理增删朋友、更新用户资料等辅助任务。这些都是常见功能，不再详细展开。

![移动应用系统架构。移动用户经 HTTP 与 WebSocket 连接负载均衡器，连接箭头编号为1；负载均衡器在步骤2分发至 WebSocket 或 API 服务器。WebSocket 服务器处理双向位置信息，通过 Redis 发布/订阅进行实时更新，并访问位置缓存和位置历史数据库。API 服务器负责用户、朋友关系及身份验证，在步骤3访问用户数据库。原说明将位置缓存和用户数据库都描述为保存持久数据。图中展示各组件之间的信息流，以及负载均衡提升扩展性、缓存优化性能的作用。](https://bytebytego.com/images/courses/system-design-interview/nearby-friends/figure-5-restful-api-request-flow-SL4EZ27Z.svg)

图5　RESTful API 请求流程

#### WebSocket 服务器

这是一个有状态服务器集群，处理朋友位置的近实时更新。每个客户端与其中一台服务器保持一条持久 WebSocket 连接。搜索半径内的朋友位置发生变化时，系统通过这条连接把更新发送给客户端。

WebSocket 服务器的另一项重要职责是处理“附近的朋友”的客户端初始化，向移动端提供所有附近在线朋友的初始位置。后文将详细讨论。

本章中，“WebSocket 连接”与“WebSocket 连接处理器”两个术语可以互换使用。

#### Redis 位置缓存

使用 Redis 保存每个活跃用户的最近位置，缓存条目都设置生存时间（TTL）。TTL 到期，用户视为不再活跃，位置数据从缓存清除。每次位置更新都会刷新 TTL，也可以采用其他支持 TTL 的键值存储。

#### 用户数据库

用户数据库保存用户信息和朋友关系，可以使用关系型数据库或 NoSQL 数据库。

#### 位置历史数据库

该数据库保存用户的历史位置数据，与“附近的朋友”功能没有直接关系。

#### Redis 发布/订阅服务器

Redis 发布/订阅（Pub/Sub）\[2\] 是一种轻量级消息总线，其频道创建成本很低。一台配备数GB内存的现代 Redis 服务器可以容纳数百万个频道，也称主题。图6展示了 Redis Pub/Sub 的工作方式。

![Redis 发布/订阅模型架构图，分为三个部分。左侧“用户发布位置更新”包含发布者1、发布者2，二者将更新发送到中央 Redis Pub/Sub 中的各自频道：发布者1发送到用户1频道，发布者2发送到用户2频道。右侧“朋友”包含订阅者1、2、3。用户1频道向订阅者1发送数据；用户2频道向订阅者2和3发送数据，表示同一频道可以有多个订阅者。箭头展示从发布者到频道、再到订阅者的单向位置更新流。](https://bytebytego.com/images/courses/system-design-interview/nearby-friends/figure-6-redis-pub-sub-KDAMADYD.svg)

图6　Redis Pub/Sub

本设计将 WebSocket 服务器收到的位置更新发布到该用户在 Redis Pub/Sub 中的专属频道。每位活跃朋友都有一个专用 WebSocket 连接处理器订阅该频道。位置更新时，触发 WebSocket 处理函数，逐一为每位活跃朋友重新计算距离。如果新距离在搜索半径内，就通过 WebSocket 连接把新位置和时间戳发送给朋友的客户端。也可以采用其他支持轻量级频道的消息总线。

了解各组件的职责后，下面从系统角度看用户位置变化时会发生什么。

### 周期性位置更新

移动客户端通过持久 WebSocket 连接定期发送位置更新，流程如图7所示。

![移动应用架构。移动用户通过 HTTP 与 WebSocket 连接负载均衡器，后者将请求分配到 WebSocket 服务器和 API 服务器。WebSocket 服务器标有7，处理双向位置信息，并与负载均衡器（2）、Redis Pub/Sub（6）、位置缓存（4）交互。API 服务器管理用户、朋友关系及身份验证，并连接用户数据库。两类服务器都能访问位置历史数据库（3）。编号箭头表示组件间信息流，例如1连接移动用户与负载均衡器，7连接 WebSocket 服务器与 Redis Pub/Sub。位置缓存用于提高系统性能。](https://bytebytego.com/images/courses/system-design-interview/nearby-friends/figure-7-periodic-location-update-KBIO53BB.svg)

图7　周期性位置更新

1.  移动客户端将位置更新发送给负载均衡器。
    
2.  负载均衡器沿该客户端的持久连接，将更新转发到对应 WebSocket 服务器。
    
3.  WebSocket 服务器将位置数据保存到位置历史数据库。
    
4.  WebSocket 服务器更新位置缓存并刷新 TTL，同时将新位置保存到该用户连接处理器的变量中，供后续计算距离。
    
5.  WebSocket 服务器将新位置发布到 Redis Pub/Sub 中该用户的频道。第3至5步可以并行执行。
    
6.  Redis Pub/Sub 收到某频道的位置更新后，向其所有订阅者，也就是 WebSocket 连接处理器广播。这里的订阅者是发送更新的用户的所有在线朋友，每位朋友对应的处理器都会收到该用户的位置更新。
    
7.  收到消息后，连接处理器所在的 WebSocket 服务器计算发送方用户与订阅者之间的距离。发送方位置在消息中，订阅者位置则保存在其连接处理器的变量里。
    
8.  图中未画出这一步。如果距离不超过搜索半径，就将新位置和最近更新时间戳发送给订阅者客户端；否则丢弃本次更新。
    

理解这个流程非常重要，下面通过图8的具体例子再看一遍。先作如下假设：

-   用户1的朋友是用户2、用户3、用户4。
    
-   用户5的朋友是用户4、用户6。
    

![使用 WebSocket 和 Redis Pub/Sub 实时分享朋友位置的系统架构。顶部手机图标表示用户1和用户5，分别将位置发送到 WebSocket 服务器层的用户1连接、用户5连接，图中位置信息标注为“用户1的位置”。这些连接把位置发布至 Redis Pub/Sub 中各自的用户频道。其他用户2、3、4、6订阅相应频道，通过服务器层中各自的 WebSocket 连接接收“朋友位置更新”，从而实现实时位置分享。发布、订阅连线标明消息方向，虚线框分别将 WebSocket 服务器和 Redis Pub/Sub 组件分组。](https://bytebytego.com/images/courses/system-design-interview/nearby-friends/figure-8-send-location-update-to-friends-DUUPBXZN.svg)

图8　向朋友发送位置更新

1.  用户1的位置变化后，将更新发送到持有用户1连接的 WebSocket 服务器。
    
2.  将位置发布到 Redis Pub/Sub 中用户1的频道。
    
3.  Redis Pub/Sub 向所有订阅者广播位置更新。这里的订阅者是用户1朋友的 WebSocket 连接处理器。
    
4.  如果发送方用户1与订阅者用户2的距离不超过搜索半径，就将新位置发送给用户2的客户端。
    

对频道中的每位订阅者都要重复计算。平均每人有400位朋友，假设其中10%在线且在附近，那么每次用户位置更新，约需向40位朋友转发更新。

### API 设计

总体设计已经确定，下面列出所需 API。

**WebSocket**：用户通过 WebSocket 协议收发位置更新，至少需要以下 API。

**1\. 周期性位置更新**

请求：客户端发送纬度、经度和时间戳。

响应：无。

**2\. 客户端接收位置更新**

发送的数据：朋友的位置数据和时间戳。

**3\. WebSocket 初始化**

请求：客户端发送纬度、经度和时间戳。

响应：客户端收到朋友的位置数据。

**4\. 订阅新朋友**

请求：WebSocket 服务器发送朋友的标识符。

响应：该朋友最新的纬度、经度和时间戳。

**5\. 取消订阅朋友**

请求：WebSocket 服务器发送朋友的标识符。

响应：无。

**HTTP 请求**：API 服务器处理增删朋友、更新用户资料等任务。这些功能很常见，不再展开。

### 数据模型

另一个重要方面是数据模型。总体设计已介绍用户数据库，下面重点讨论位置缓存和位置历史数据库。

#### 位置缓存

位置缓存保存所有已开启该功能的活跃用户的最新位置，采用 Redis 实现。缓存键值如表1所示。

| **键**  | **值**                        |
| -------- | -------------------------------- |
| user\_id | {latitude, longitude, timestamp} |

表1　位置缓存

**为什么不使用数据库保存位置数据？**

“附近的朋友”只关心用户的**当前位置**，因此每人只需保存一条位置。Redis 读写速度很快，非常适合；其 TTL 能自动从缓存清除不再活跃的用户。当前位置不需要持久保存。如果 Redis 实例宕机，可以用全新的空实例替换，并随着新位置更新到来重新填充。缓存预热期间，活跃用户可能错过一两个更新周期内的朋友位置，这一权衡可以接受。深入设计部分将讨论如何减轻更换缓存对用户的影响。

#### 位置历史数据库

位置历史数据库保存用户的历史位置，表结构如下：

| user\_id | latitude | longitude | timestamp |
| -------- | -------- | --------- | --------- |

需要一种擅长处理大量写入且能水平扩展的数据库，Cassandra 是合适选择。也可以使用关系型数据库，但历史数据无法放入单个实例，需要分片。最基本的方案是按用户标识分片，使负载均匀分布到各分片，运维也较简单。

## 第3步：深入设计

上一节的总体方案在多数情况下可行，但很可能无法支撑目标规模。本节随着规模增加逐步识别瓶颈，并提出消除瓶颈的方案。

### 各组件的扩展能力如何？

#### API 服务器

RESTful API 层的扩展方法已经很成熟。这些服务器无状态，可以依据 CPU 使用率、负载或 I/O 等指标，以多种方式自动扩展集群，这里不再展开。

#### WebSocket 服务器

WebSocket 集群按使用量自动扩展并不困难。但它是有状态的，移除已有节点时必须谨慎。删除节点前，应允许现有连接逐步排空。可以在负载均衡器中将该节点标记为 draining，不再向其路由新连接；等所有原有连接关闭，或等待足够长时间后，再移除服务器。

在 WebSocket 服务器上发布新版本应用时，也需要同样谨慎。

有状态服务器的有效自动扩展，有赖于良好的负载均衡器。多数云负载均衡器都能很好地处理这项工作。

**客户端初始化**

移动客户端启动时，与某台 WebSocket 服务器建立持久连接。每条连接都长期存在，多数现代编程语言能以较小的内存开销维持大量长连接。

WebSocket 初始化时，客户端发送用户初始位置，服务器在连接处理器中执行以下任务。

1.  更新位置缓存中的用户位置。
    
2.  将位置保存到连接处理器变量中，供后续计算。
    
3.  从用户数据库读取该用户的全部朋友。
    
4.  批量请求位置缓存，取得所有朋友的位置。因为缓存条目的 TTL 与不活跃超时时长一致，不活跃朋友的位置不会保留在缓存里。
    
5.  对缓存返回的每个位置，计算用户与该朋友的距离。若在搜索半径内，通过 WebSocket 返回朋友资料、位置和最近更新时间戳。
    
6.  对每位朋友，在 Redis Pub/Sub 中订阅其频道，后文会进一步说明。创建频道成本很低，因此无论朋友是否活跃都予以订阅。不活跃朋友占用少量内存，但上线前不会消耗 CPU 或 I/O，因为没有发布更新。
    
7.  将用户当前位置发送到其自身的 Redis Pub/Sub 频道。
    

#### 用户数据库

用户数据库保存两类数据：用户资料，包括标识、用户名、资料 URL 等，以及朋友关系。目标规模下，这些数据很可能无法放入一个关系型数据库实例。好在可以按用户标识分片，实现水平扩展；关系型数据库分片是一项常见技术。

另外，在这种规模下，用户和朋友关系数据通常由专门团队管理，并通过内部 API 提供。此时 WebSocket 服务器通过内部 API 而非直接查询数据库获取这些信息。采用 API 或直接查询，在功能和性能上没有太大差别。

#### 位置缓存

采用 Redis 缓存全部活跃用户的最新位置。如前所述，每个键设有 TTL，每次位置更新都会续期，从而限制最大内存使用量。峰值1000万活跃用户，每条位置不超过100字节，一台配有数GB乃至更多内存的现代 Redis 服务器就能轻松容纳全部位置。

不过，1000万活跃用户大约每30秒更新一次，Redis 每秒需要处理334K次更新，对高端现代服务器也可能偏高。好在缓存易于分片：各用户的位置独立，可以按用户标识将负载均匀分散到多台 Redis 服务器。

为提高可用性，可以将每个分片的位置数据复制到备用节点；主节点故障后，快速提升备用节点，以缩短停机时间。

#### Redis 发布/订阅服务器

发布/订阅服务器充当路由层，把某用户的位置更新转给所有在线朋友。选择 Redis Pub/Sub，是因为创建频道十分轻量：有人订阅时才创建频道，没有订阅者时，发布的消息直接丢弃，服务器负载很低。创建频道时，Redis 用少量内存维护哈希表与链表 \[3\] 来跟踪订阅者。用户离线、频道没有更新时，频道创建后不再消耗 CPU。设计利用这些特点：

1.  为每个使用该功能的用户分配唯一频道。应用初始化时，订阅每位朋友的频道，无论朋友是否在线。这样，后端不必在朋友上线时新增订阅，也不必在其不活跃时取消订阅，简化了设计。
    
2.  代价是内存占用增加。但如下文所示，内存不太可能成为瓶颈，因此以更多内存换取更简单架构是值得的。
    

**需要多少台 Redis Pub/Sub 服务器？**

下面估算内存和 CPU 使用量。

**内存使用量**

假设每个使用该功能的用户分配一个频道，共需1亿个频道，即10亿 \* 10%。假设平均每个用户有100位使用该功能的活跃朋友，包含附近及较远的朋友；内部哈希表和链表用约20字节指针跟踪每个订阅者，则全部频道约需200 GB：1亿 \* 20字节 \* 100位朋友 / 10^9 = 200 GB。若每台现代服务器有100 GB内存，大约需要2台 Redis Pub/Sub 服务器。

**CPU 使用量**

根据前面的估算，发布/订阅服务器每秒向订阅者推送约1400万次更新。不做实际基准测试，很难准确估计现代 Redis 服务器每秒能推送多少消息，但可以确定单台无法承受这一负载。保守假设，一台配备千兆网络的现代服务器，每秒可向订阅者推送约100,000条消息。考虑到位置消息很小，这个估值可能较保守。于是需要1400万 / 100,000 = 140台 Redis 服务器分担负载。再次强调，该估值可能过于保守，实际服务器数量可能少得多。

根据估算，可以得出：

-   Redis Pub/Sub 的瓶颈是 CPU，而非内存。
    
-   为支撑目标规模，需要分布式 Redis Pub/Sub 集群。
    

##### 分布式 Redis Pub/Sub 服务器集群

如何把频道分布到数百台 Redis 服务器？好在频道之间相互独立，因此容易按发布者的用户标识分片，分散到多台发布/订阅服务器。但数百台服务器难免经常故障，还需要更具体地说明如何保持可运维性。

在设计中引入服务发现组件。可选方案很多，etcd \[4\] 和 ZooKeeper \[5\] 是常见选择。我们的需求很基础，只需要两项功能：

1.  在服务发现组件中维护服务器列表，并提供简单界面或 API 更新它。从根本上说，服务发现是保存配置的小型键值存储。以图9为例，哈希环的键值可如下所示：
    
    键：/config/pub\_sub\_ring
    
    值：\[ “p\_1”, “p\_2”, “p\_3”, “p\_4”\]
    
2.  客户端，也就是这里的 WebSocket 服务器，能够订阅该值，即 Redis Pub/Sub 服务器列表的任何更新。
    

在第1项所述键下，服务发现组件保存所有活跃 Redis Pub/Sub 服务器构成的哈希环。哈希环的细节可参考《System Design Interview》第一卷的一致性哈希章节或资料 \[6\]。发布者与订阅者都通过该环，确定每个频道应连接哪台服务器。例如，图9中的频道2位于 Redis Pub/Sub 服务器1。

##### Redis Pub/Sub 服务器的扩展考虑

应该如何扩展 Redis Pub/Sub 集群？是否每天根据流量规律动态扩缩容？无状态服务器常这样做，因为风险低且节省成本。要回答这些问题，先看该集群的特性。

1.  发布/订阅频道中的消息不会持久保存在内存或磁盘；发给全部订阅者后立即移除。如果没有订阅者，就直接丢弃。从这个角度，频道中流动的数据是无状态的。
    
2.  但服务器仍保存频道状态，尤其是每个频道的订阅者列表。服务器被替换，或者哈希环增删节点时，频道可能迁移。所有相关订阅者都必须获知迁移，取消旧服务器上的订阅，再订阅新服务器上的替代频道。从这个角度，发布/订阅服务器是有状态的，需要协调其全部订阅者，尽量缩短服务中断。
    

因此，应该把 Redis Pub/Sub 更像存储集群那样，视为有状态集群。有状态集群扩缩容有运维成本和风险，必须仔细规划。通常会预留富余容量，保证能承受每日峰值，并留出足够余量，避免不必要的规模调整。

确实需要扩缩容时，要注意以下问题：

-   调整集群规模会使许多频道迁往哈希环上的其他服务器。服务发现通知所有 WebSocket 服务器更新环后，将出现大量重新订阅请求。
    
-   大规模重新订阅期间，客户端可能遗漏位置更新。虽然设计允许偶尔遗漏，也应尽量减少。
    
-   考虑到可能中断，应在一天中使用量最低时调整规模。
    

实际操作很简单，按以下步骤进行：

-   确定新的环规模；如果扩容，先准备足够的新服务器。
    
-   用新内容更新哈希环配置键。
    
-   监控仪表盘，WebSocket 集群的 CPU 使用率应该会出现短暂峰值。
    

以图9的哈希环为例，若增加 p\_5、p\_6 两个节点，配置更新如下：

原配置：\[ “p\_1”, “p\_2”, “p\_3”, “p\_4”\]

新配置：\[ “p\_1”, “p\_2”, “p\_3”, “p\_4”, “p\_5”, “p\_6”\]

##### Redis Pub/Sub 服务器的运维考虑

替换已有 Redis Pub/Sub 服务器的运维风险小得多，不会导致大量频道迁移，只需处理被替换服务器上的频道。服务器难免故障并需要定期更换，因此这一点很重要。

发布/订阅服务器故障时，监控软件应通知值班人员。具体健康检查方法超出本章范围，不再介绍。值班人员更新服务发现中的哈希环键，用新的备用节点替换故障节点。WebSocket 服务器收到通知后，再通知连接处理器到新服务器重新订阅。每个处理器都保存自己订阅的频道列表，接到通知后逐个依据哈希环检查是否需要在新服务器上重订阅。

以图9为例，如果 p\_1 故障并被 p1\_new 替换，哈希环更新如下：

原配置：\[ “p\_1”, “p\_2”, “p\_3”, “p\_4”\]

新配置：\[ “p\_1\_new”, “p\_2”, “p\_3”, “p\_4”\]

### 添加和移除朋友

用户添加或移除朋友时，客户端应如何处理？新增朋友后，需要通知服务端该客户端的 WebSocket 连接处理器，订阅新朋友的频道。

由于该功能属于更大应用生态的一部分，可以假设移动端能注册新增朋友时的回调。回调触发后，向 WebSocket 服务器发消息，订阅新朋友的频道；如果新朋友活跃，服务器还返回其最新位置和时间戳。

类似地，移除朋友时也可以由应用触发回调，向 WebSocket 服务器发送取消订阅的消息。

朋友选择开启或关闭位置更新时，也可以复用这些订阅、取消订阅回调。

### 拥有大量朋友的用户

值得讨论：朋友特别多的用户是否会形成性能热点？假设朋友数量有硬上限，例如 Facebook 最多允许5000位朋友。朋友关系是双向的，这里讨论的不是名人拥有数百万关注者的单向关注模型。

即使有数千位朋友，订阅者也分散在集群众多 WebSocket 服务器上，位置更新负载由它们分担，不太可能形成热点。

这类用户会使自身频道所在的发布/订阅服务器承受更多负载。但有超过100台服务器，这些“巨鲸”用户会分散其间，增加的负载应不至于压垮单台服务器。

### Redis Pub/Sub 的替代方案

是否有合适的方案替代作为路由层的 Redis Pub/Sub？当然有。Erlang \[8\] 非常适合这一问题，甚至可以说比上面的 Redis Pub/Sub 方案更好。不过 Erlang 较为小众，优秀程序员难招。如果团队具备相关经验，它会是很好的选择。

为什么选择 Erlang？它是面向高度分布式、并发应用的通用编程语言与运行环境。这里的 Erlang 特指整个生态，包含语言 Erlang 或 Elixir \[9\]，以及运行环境和库：BEAM 虚拟机 \[10\]、OTP 运行库 \[11\]。

Erlang 的优势是轻量级进程。Erlang 进程运行在 BEAM 虚拟机上，创建成本比 Linux 进程低几个数量级。最小进程约占300字节，一台现代服务器可运行数百万个；没有任务时，进程不消耗 CPU。因此，将设计中的1000万活跃用户各建模为一个 Erlang 进程，成本极低。

Erlang 也容易分布到多台服务器，运维开销较低，还具备安全调试线上问题的优秀工具，部署工具同样强大。

在本设计中，可以用 Erlang 实现 WebSocket 服务，并以一个分布式 Erlang 应用替换整个 Redis Pub/Sub 集群。每个用户建模为 Erlang 进程；客户端位置变化后，该进程从 WebSocket 服务器接收更新，也订阅朋友进程的更新。Erlang/OTP 原生支持订阅，易于构建，从而形成高效的连接网，把某个用户的位置更新路由给众多朋友。

## 第4步：总结

本章设计了支持“附近的朋友”的系统，核心目标是高效地将用户位置更新传递给朋友。

核心组件包括：

-   WebSocket：客户端与服务器之间的实时通信。
    
-   Redis：快速读写位置数据。
    
-   Redis Pub/Sub：作为路由层，将用户位置更新传递给全部在线朋友。
