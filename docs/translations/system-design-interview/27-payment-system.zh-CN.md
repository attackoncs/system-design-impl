# 27 支付系统

本章中，我们设计一个支付系统。近年来，电子商务在全球范围内迅速普及。每一笔交易的背后，都有一个支付系统在支撑。可靠、可扩展且灵活的支付系统至关重要。

什么是支付系统？根据维基百科的定义，“支付系统是通过转移货币价值来结算金融交易的任何系统，其中包括使价值交换得以实现的机构、工具、人员、规则、流程、标准和技术” \[1\]。

支付系统表面上很容易理解，但许多开发者在实际开发时仍会望而却步。一个小小的失误就可能造成重大收入损失，并摧毁用户的信任。不过，不必担心！本章将揭开支付系统的神秘面纱。

## 第 1 步：理解问题并确定设计范围

不同的人对支付系统的理解可能截然不同。有些人想到的是 Apple Pay 或 Google Pay 这样的数字钱包，另一些人想到的则是 PayPal 或 Stripe 这样的支付后端系统。在面试开始时明确具体需求非常重要。你可以向面试官提出以下问题：

**候选人**：我们要构建哪一种支付系统？

**面试官**：假设你要为 Amazon.com 这样的电商应用构建支付后端。当客户在 Amazon.com 下单时，支付系统负责处理与资金流转有关的一切事务。

**候选人**：支持哪些支付方式？信用卡、PayPal、银行卡等吗？

**面试官**：实际的支付系统应该支持所有这些方式。不过，在这次面试中，我们可以以信用卡支付为例。

**候选人**：信用卡支付由我们自己处理吗？

**面试官**：不是，我们使用 Stripe、Braintree、Square 等第三方支付处理机构。

**候选人：** 我们会在系统中存储信用卡数据吗？

**面试官：** 由于安全与合规要求极高，我们不会在系统中直接存储卡号。我们依靠第三方支付处理机构来处理敏感的信用卡数据。

**候选人**：这是一个全球性的应用吗？我们需要支持不同币种和国际支付吗？

**面试官**：问得很好。是的，这个应用面向全球，但在这次面试中，我们假设只使用一种货币。

**候选人**：每天有多少笔支付交易？

**面试官**：每天 100 万笔交易。

**候选人**：我们需要支持出款流程吗？例如，Amazon 这样的电商网站每个月都会通过这种流程向卖家付款。

**面试官**：是的，需要支持。

**候选人**：我想我已经收集完所有需求了。还有什么需要注意的吗？

**面试官**：有。支付系统会与许多内部服务（会计、分析等）和外部服务（支付服务提供商）交互。当某个服务发生故障时，各个服务之间可能会出现状态不一致。因此，我们需要进行对账并修复所有不一致。这也是一项需求。

通过这些问题，我们明确了功能需求和非功能需求。在这次面试中，我们重点设计一个支持以下需求的支付系统。

### 功能需求

-   入款流程：支付系统代表卖家收取客户的款项。
    
-   出款流程：支付系统向世界各地的卖家付款。
    

### 非功能需求

-   可靠性与容错能力。必须谨慎处理支付失败的情况。
    
-   需要在内部服务（支付系统、会计系统）与外部服务（支付服务提供商）之间执行对账流程。该流程以异步方式验证这些系统中的支付信息是否一致。
    

### 粗略估算

系统每天需要处理 100 万笔交易，即 1,000,000 笔交易 / 10^5 秒 = 每秒 10 笔交易（TPS）。对于一般的数据库来说，10 TPS 并不高，这意味着这道系统设计面试题的重点在于如何正确处理支付交易，而非追求高吞吐量。

## 第 2 步：提出总体设计并达成共识

从总体上看，为了体现资金的流转方式，支付流程分为两个步骤：

-   入款流程
    
-   出款流程
    

以电商网站 Amazon 为例。买家下单后，资金流入 Amazon 的银行账户，这就是入款流程。虽然资金在 Amazon 的银行账户中，但 Amazon 并不拥有全部资金。其中很大一部分属于卖家，Amazon 只是收取费用、代为保管资金。之后，当商品送达、款项可以释放时，扣除费用后的余额会从 Amazon 的银行账户流入卖家的银行账户。这就是出款流程。图 1 展示了简化的入款和出款流程。

**支付服务**

支付服务接收用户的支付事件，并协调支付流程。它通常首先执行风险检查，评估支付是否符合 AML/CFT \[2\] 等法规要求，以及是否存在洗钱或恐怖主义融资等犯罪活动的迹象。支付服务只处理通过风险检查的支付。由于风险检查极其复杂且专业性很强，风险检查服务通常使用第三方提供商。

**支付执行器**

支付执行器通过支付服务提供商（PSP）执行单笔支付订单。一个支付事件可能包含多笔支付订单。

**支付服务提供商（PSP）**

PSP 将资金从账户 A 转移到账户 B。在这个简化示例中，PSP 将资金从买家的信用卡账户中划出。

**银行卡组织**

银行卡组织是处理信用卡业务的机构。知名的银行卡组织包括 Visa、MasterCard、Discovery 等。银行卡组织的生态系统非常复杂 \[3\]。

**账本**

账本保存支付交易的财务记录。例如，当用户向卖家支付 1 美元时，我们将其记为用户账户借记 1 美元、卖家账户贷记 1 美元。账本系统对于支付后的分析非常重要，例如计算电商网站的总收入，或预测未来收入。

**钱包**

钱包保存商家的账户余额。它也可以记录某个用户的累计支付金额。

如图 2 所示，典型的入款流程如下：

1.  用户点击“下单”按钮时，会生成一个支付事件，并将其发送给支付服务。
    
2.  支付服务将支付事件存入数据库。
    
3.  有时，一个支付事件可能包含多笔支付订单。例如，在一次结账过程中，你可能选择了多个卖家的商品。如果电商网站将这次结账拆分成多笔支付订单，支付服务就会针对每笔支付订单调用支付执行器。
    
4.  支付执行器将支付订单存入数据库。
    
5.  支付执行器调用外部 PSP，处理信用卡支付。
    
6.  支付执行器成功处理支付后，支付服务更新钱包，记录相应卖家拥有的金额。
    
7.  钱包服务器将更新后的余额信息存入数据库。
    
8.  钱包服务成功更新卖家的余额信息后，支付服务调用账本进行更新。
    
9.  账本服务将新的账本信息追加到数据库中。
    

#### 支付服务的 API

支付服务采用 RESTful API 设计规范。

**POST /v1/payments**

此端点执行一个支付事件。如前所述，一个支付事件可能包含多笔支付订单。请求参数如下：

| **字段**          | **说明**                                              | **类型** |
| ------------------ | ------------------------------------------------------------ | -------- |
| buyer\_info        | 买家信息                                 | json     |
| checkout\_id       | 此次结账的全局唯一 ID                       | string   |
| credit\_card\_info | 可以是加密后的信用卡信息，也可以是支付令牌。具体取值取决于 PSP。 | json     |
| payment\_orders    | 支付订单列表                                 | list     |

表 1 API 请求参数（执行一个支付事件）

_payment\_orders_ 如下所示：

| **字段**          | **说明**                       | **类型**                |
| ------------------ | ------------------------------------- | ----------------------- |
| seller\_account    | 收款的卖家   | string                  |
| amount             | 该订单的交易金额  | string                  |
| currency           | 该订单的货币            | string (ISO 4217 \[4\]) |
| payment\_order\_id | 此笔支付的全局唯一 ID | string                  |

表 2 payment\_orders

注意，_payment\_order\_id_ 是全局唯一的。当支付执行器向第三方 PSP 发送支付请求时，PSP 使用 _payment\_order\_id_ 作为去重 ID，也称为幂等键。

你可能已经注意到，“amount”字段的数据类型是“string”，而不是“double”。Double 并不是好的选择，原因如下：

1.  不同协议、软件和硬件在序列化与反序列化时，支持的数值精度可能不同。这种差异可能导致意料之外的舍入误差。
    
2.  数值可能极大（例如，日本在 2020 日历年的 GDP 约为 5x10<sup>14</sup> 日元），也可能极小（例如，比特币的 1 聪为 10<sup>-8</sup>）。
    

建议在传输和存储时，以字符串格式保存数值。只有在显示或计算时，才将它们解析为数字。

**GET /v1/payments/{:id}**

此端点根据 _payment\_order\_id_ 返回单笔支付订单的执行状态。

上述支付 API 与一些知名 PSP 的 API 类似。如果你希望更全面地了解支付 API，可以查看 Stripe 的 API 文档 \[5\]。

#### 支付服务的数据模型

支付服务需要两张表：支付事件表和支付订单表。为支付系统选择存储方案时，性能通常并非最重要的因素。我们更关注以下几点：

1.  经过验证的稳定性。该存储系统是否已被其他大型金融机构使用多年（例如超过 5 年），并获得正面反馈。
    
2.  配套工具是否丰富，例如监控工具和排查工具。
    
3.  数据库管理员（DBA）人才市场的成熟度。能否招到经验丰富的 DBA，是一个非常重要的考量因素。
    

通常，相比 NoSQL/NewSQL，我们更倾向于选择支持 ACID 事务的传统关系型数据库。

支付事件表包含详细的支付事件信息，其结构如下：

| **名称**           | **类型**                     |
| ------------------ | ---------------------------- |
| checkout\_id       | string **PK**                |
| buyer\_info        | string                       |
| seller\_info       | string                       |
| credit\_card\_info | 取决于发卡机构 |
| is\_payment\_done  | boolean                      |

表 3 支付事件

支付订单表保存每笔支付订单的执行状态，其结构如下：

| **名称**               | **类型**      |
| ---------------------- | ------------- |
| payment\_order\_id     | String **PK** |
| buyer\_account         | string        |
| amount                 | string        |
| currency               | string        |
| checkout\_id           | string **FK** |
| payment\_order\_status | string        |
| ledger\_updated        | boolean       |
| wallet\_updated        | boolean       |

表 4 支付订单

在深入讨论这些表之前，我们先了解一些背景信息。

-   _checkout\_id_ 是外键。一次结账会创建一个支付事件，该事件可能包含多笔支付订单。
    
-   当我们调用第三方 PSP，从买家的信用卡扣款时，资金并不会直接转给卖家，而是转入电商网站的银行账户。这个过程称为入款。当满足出款条件（例如商品已送达）时，卖家发起出款。此时，资金才会从电商网站的银行账户转入卖家的银行账户。因此，在入款流程中，我们只需要买家的银行卡信息，而不需要卖家的银行账户信息。
    

在支付订单表（表 4）中，_payment\_order\_status_ 是一个枚举类型（enum），用于保存支付订单的执行状态。执行状态包括 _NOT\_STARTED, EXECUTING, SUCCESS, FAILED_。其更新逻辑如下：

1.  _payment\_order\_status_ 的初始状态是 _NOT\_STARTED_。
    
2.  支付服务将支付订单发送给支付执行器时，_payment\_order\_status_ 为 _EXECUTING_。
    
3.  支付服务根据支付执行器的响应，将 _payment\_order\_status_ 更新为 _SUCCESS_ 或 _FAILED_。
    

当 _payment\_order\_status_ 变为 _SUCCESS_ 后，支付服务会调用钱包服务更新卖家余额，并将 _wallet\_updated_ 字段更新为 _TRUE_。为简化设计，这里假设钱包更新总能成功。

完成后，支付服务的下一步是调用账本服务更新账本数据库，并将 _ledger\_updated_ 字段更新为 _TRUE_。

当同一 _checkout\_id_ 下的所有支付订单都处理成功后，支付服务会将支付事件表中的 _is\_payment\_done_ 更新为 TRUE。通常会有一个定时任务，按固定间隔监控正在处理的支付订单状态。当支付订单未能在规定时间内完成时，它会发出告警，以便工程师排查。

#### 复式记账系统

账本系统中有一项非常重要的设计原则：复式记账原则（也称复式会计/簿记 \[6\]）。复式记账系统是任何支付系统的基础，也是准确记账的关键。它将每笔支付交易以相同金额记录到两个独立的账本账户中：一个账户借记，另一个账户贷记，金额相等（表 5）。

| 账户 | 借方 | 贷方 |
| ------- | ----- | ------ |
| 买家   | $1    |        |
| 卖家  | $1    |        |

表 5 复式记账系统

复式记账系统规定，所有交易分录之和必须为 0。一方少了 1 分钱，就意味着另一方多了 1 分钱。它提供端到端的可追溯性，并确保整个支付周期的一致性。关于复式记账系统实现的更多内容，请参阅 Square 关于不可变复式记账数据库服务的工程博客 \[7\]。

#### 托管支付页面

### 出款流程

出款流程的组件与入款流程非常相似。其中一个区别是：入款流程使用 PSP，将资金从买家的信用卡转入电商网站的银行账户；而出款流程使用第三方出款服务提供商，将资金从电商网站的银行账户转入卖家的银行账户。

通常，支付系统使用 Tipalti \[9\] 这样的第三方应付账款服务提供商处理出款。出款同样涉及大量记账和监管要求。

## 第 3 步：深入设计

本节重点讨论如何让系统更快、更稳健、更安全。在分布式系统中，错误和故障不仅不可避免，而且十分常见。例如，如果客户多次点击“支付”按钮，会发生什么？他们会被多次扣款吗？由网络连接不佳导致的支付失败应该如何处理？本节将深入探讨几个关键主题。

-   PSP 集成
    
-   对账
    
-   处理支付处理延迟
    
-   内部服务之间的通信
    
-   处理失败的支付
    
-   恰好一次交付
    
-   一致性
    
-   安全性
    

### PSP 集成

如果支付系统可以直接连接银行，或者 Visa、MasterCard 这样的银行卡组织，就可以不通过 PSP 完成支付。这种直接连接并不常见，而且专业性很强，通常只有规模极大、足以证明这种投入合理的公司才会采用。大多数公司的支付系统会通过以下两种方式之一与 PSP 集成：

1.  如果公司能够安全地存储敏感支付信息，并且选择这样做，就可以通过 API 集成 PSP。公司负责开发支付网页、采集和存储敏感支付信息。PSP 则负责连接银行或银行卡组织。
    
2.  如果公司出于复杂法规和安全方面的顾虑，选择不存储敏感支付信息，PSP 就会提供托管支付页面，采集银行卡支付信息，并将其安全地存储在 PSP 中。这是大多数公司采用的方式。
    

我们用图 4 详细说明托管支付页面的工作原理。

1.  用户在客户端浏览器中点击“结账”按钮。客户端携带支付订单信息调用支付服务。
    
2.  支付服务收到支付订单信息后，向 PSP 发送支付注册请求。该注册请求包含金额、货币、支付请求过期时间和重定向 URL 等支付信息。由于一笔支付订单只能注册一次，因此请求中包含一个 UUID 字段，以确保恰好一次注册。这个 UUID 也称为 nonce \[10\]。通常，这个 UUID 就是支付订单的 ID。
    
3.  PSP 向支付服务返回一个令牌。令牌是 PSP 侧的 UUID，用于唯一标识这次支付注册。之后，我们可以使用这个令牌查看支付注册信息和支付执行状态。

5.  令牌持久化后，客户端显示 PSP 托管的支付页面。移动应用通常通过集成 PSP 的 SDK 实现这项功能。这里以 Stripe 的网页集成为例（图 5）。Stripe 提供一个 JavaScript 库，用于显示支付界面、采集敏感支付信息，并直接调用 PSP 完成支付。敏感支付信息由 Stripe 采集，始终不会进入我们的支付系统。托管支付页面通常需要两项信息：
    
    -   第 4 步中收到的令牌。PSP 的 JavaScript 代码使用该令牌，从 PSP 后端获取支付请求的详细信息。其中一项重要信息是需要收取的金额。
        
    -   另一项重要信息是重定向 URL。这是支付完成时所访问的网页 URL。当 PSP 的 JavaScript 完成支付后，会将浏览器重定向到该 URL。通常，重定向 URL 指向一个显示结账状态的电商网页。注意，重定向 URL 与第 9 步中的 webhook \[11\] URL 不同。

7.  PSP 返回支付状态。
    
8.  网页现在被重定向到重定向 URL。第 7 步收到的支付状态通常会附加在 URL 中。例如，完整的重定向 URL 可能是 \[12\]：`https://your-company.com/?tokenID=JIOUIQ123NSF&payResult=X324FSa`
    
9.  PSP 通过 webhook，异步调用支付服务并传入支付状态。webhook 是支付系统侧的一个 URL，在最初配置 PSP 时向 PSP 注册。支付系统通过 webhook 收到支付事件后，会提取支付状态，并更新支付订单数据库表中的 _payment\_order\_status_ 字段。
    

到目前为止，我们解释了托管支付页面一切顺利时的流程。实际上，网络连接可能并不可靠，上述 9 个步骤都有可能失败。有没有系统性的方法来处理失败情况？答案是对账。

### 对账

当系统组件以异步方式通信时，无法保证消息一定送达，也无法保证一定收到响应。这在支付业务中十分常见，因为支付业务经常使用异步通信来提高系统性能。PSP 或银行等外部系统也更倾向于异步通信。那么，在这种情况下，如何确保正确性？

答案是对账。这是一种定期比较相关服务状态、验证它们是否一致的做法，通常是支付系统的最后一道防线。

每晚，PSP 或银行都会向客户发送结算文件。结算文件包含银行账户余额，以及当天该银行账户发生的全部交易。对账系统解析结算文件，并将其中的明细与账本系统进行比较。下面的图 6 展示了对账流程在系统中的位置。

![图中展示了简化的支付处理系统架构。“支付事件”启动流程，触发“支付服务”。支付服务与以数据库形式表示的“账本”和“钱包”交互，二者可能分别保存交易信息和用户余额信息。随后，支付服务将支付请求传递给“支付执行器”，后者与外部支付网关交互；图中明确展示了 PayPal、Stripe 和 Adyen，以及表示所支持卡种的 VISA 和 MasterCard 标志。还有一个数据库接收支付执行器的数据。文档图标表示支付系统报表，它流入粉色的“对账”模块，表明该模块负责验证和匹配不同系统之间的交易。最后，一条弯曲箭头将账本和钱包数据库经由文档图标连接到对账模块，表示这些数据库的数据会用于对账流程。](https://bytebytego.com/_next/image?url=%2Fimages%2Fcourses%2Fsystem-design-interview%2Fpayment-system%2Ffigure-6-reconciliation-HZKEQ3KA.png&w=3840&q=75)

图 6 对账

对账也用于验证支付系统内部是否一致。例如，账本和钱包中的状态可能出现分歧，我们可以使用对账系统检测任何差异。

对于对账中发现的不匹配，我们通常依靠财务团队进行人工调整。不匹配及相应调整通常分为三类：

1.  可以对不匹配进行归类，并且可以自动调整。在这种情况下，我们知道不匹配的原因和修复方法，而且编写程序自动调整在成本上是划算的。工程师可以同时实现不匹配归类和调整的自动化。
    
2.  可以对不匹配进行归类，但无法自动调整。在这种情况下，我们知道不匹配的原因和修复方法，但编写自动调整程序的成本太高。因此，将不匹配放入任务队列，由财务团队人工修复。
    
3.  无法对不匹配进行归类。在这种情况下，我们不知道不匹配是如何发生的。将不匹配放入专门的任务队列，由财务团队人工调查。
    

### 处理支付处理延迟

如前所述，端到端的支付请求会流经许多组件，并涉及内部和外部参与方。虽然大多数支付请求会在几秒内完成，但在某些情况下，请求会停滞，可能需要数小时甚至数天才会完成或被拒绝。以下是一些支付请求耗时可能超出常规的例子：

-   PSP 认为某笔支付请求风险较高，需要人工审核。
    
-   信用卡要求使用 3D Secure 身份验证 \[13\] 等额外保护机制，需要持卡人提供更多信息来验证购买行为。
    

支付服务必须能够处理这些耗时较长的支付请求。如果购买页面由外部 PSP 托管——这种情况如今很常见——PSP 会通过以下方式处理这些长时间运行的支付请求：

-   PSP 向我们的客户端返回待处理状态，客户端将其展示给用户。客户端还会提供一个页面，供客户查看当前支付状态。
    
-   PSP 代我们跟踪待处理的支付，并通过支付服务向 PSP 注册的 webhook，将任何状态更新通知支付服务。
    

支付请求最终完成时，PSP 会调用上述已注册的 webhook。支付服务更新内部系统，并完成向客户发货。

也有一些 PSP 不会通过 webhook 更新支付服务，而是要求支付服务主动轮询 PSP，获取待处理支付请求的状态更新。

### 内部服务之间的通信

内部服务采用两种通信模式：同步通信和异步通信。下面分别介绍。

**同步通信**

HTTP 这样的同步通信很适合小规模系统，但随着规模扩大，其缺点就会显现。它形成了一个依赖许多服务的漫长请求与响应周期。这种方式的缺点如下：

-   性能较低。如果调用链中的任何一个服务表现不佳，整个系统都会受到影响。
    
-   故障隔离能力差。如果 PSP 或任何其他服务发生故障，客户端就无法再收到响应。
    
-   耦合紧密。请求发送方需要知道接收方。
    
-   难以扩展。如果没有队列作为缓冲，就不容易扩展系统以应对突增的流量。
    

**异步通信**

异步通信可以分为两类：

-   单接收方：每个请求（消息）由一个接收方或服务处理，通常通过共享消息队列实现。消息队列可以有多个订阅者，但消息一经处理，就会从队列中移除。来看一个具体例子。在图 7 中，服务 A 和服务 B 都订阅了共享消息队列。当 m1 和 m2 分别被服务 A 和服务 B 消费后，两条消息都会从队列中移除，如图 8 所示。

![图中的系统架构图展示了消息队列向两个服务分发消息。圆柱形的消息队列中包含四条消息，分别标为 m1、m2、m3 和 m4，每条消息用信封图标表示。从消息队列发出的箭头表示消息流向。其中一条箭头指向标为“服务 A”的矩形框，另一条指向标为“服务 B”的矩形框。这说明队列中的消息被路由到服务 A 和服务 B，暗示一种发布订阅或扇出式消息分发模式。图中没有说明消息内容或服务性质，只展示了它们与中央消息队列之间的交互。](https://bytebytego.com/images/courses/system-design-interview/payment-system/figure-7-message-queue-7BXIY252.svg)

-   多接收方：每个请求（消息）由多个接收方或服务处理。Kafka 很适合这种场景。消费者收到消息后，消息不会从 Kafka 中移除。同一条消息可以由不同的服务处理。这种模型很适合支付系统，因为同一个请求可能触发多种后续操作，例如发送推送通知、更新财务报表、分析等。图 9 展示了一个例子。支付事件发布到 Kafka，并由支付系统、分析服务和计费服务等不同服务消费。

一般来说，同步通信的设计更简单，但无法让服务保持自主性。随着依赖关系图扩大，整体性能会下降。异步通信用设计简洁性和一致性换取可扩展性与故障恢复能力。对于业务逻辑复杂、依赖大量第三方的大规模支付系统，异步通信是更好的选择。

### 处理失败的支付

每个支付系统都必须处理失败的交易。可靠性与容错能力是关键需求。下面介绍一些应对这些挑战的技术。

#### 跟踪支付状态

在支付周期的每个阶段，都有明确的支付状态至关重要。发生任何故障时，我们都可以确定支付交易的当前状态，并判断是否需要重试或退款。支付状态可以持久化到只追加的数据库表中。

#### 重试队列与死信队列

为妥善处理故障，我们使用重试队列与死信队列，如图 10 所示。

-   重试队列：瞬时错误等可以重试的错误被路由到重试队列。
    
-   死信队列 \[14\]：如果一条消息反复失败，最终会进入死信队列。死信队列有助于调试，也能将有问题的消息隔离出来供检查，以确定它们未能成功处理的原因。
    

![图中的流程图展示了系统在支付处理过程中如何处理故障。流程从表示初始错误的“故障”圆圈开始。标有“？”的判断菱形检查故障“是否可重试”。如果是（标为“1a）是”），流程进入编号为“2”的圆柱形“重试队列”，随后流向“支付系统”方框。支付系统之后的另一个“故障”圆圈表示仍可能存在问题。第二个判断菱形再次检查“是否可重试”。如果是（标为“3a）是”），这个循环可能重复；如果否（标为“3b）否”），则进入圆柱形“死信队列”。如果初始故障被判定为不可重试（标为“1b）否”），流程则分支到圆柱形“数据库”，用于记录日志或进一步处理。整张图展示了带死信队列的重试机制，用于处理无法恢复的错误，并通过数据库记录不可重试的故障。](https://bytebytego.com/images/courses/system-design-interview/payment-system/figure-10-handle-failed-payments-ZFR5VAJK.svg)

图 10 处理失败的支付

1.  检查故障是否可以重试。
    
    1a. 可重试的故障被路由到重试队列。
    
    1b. 对于输入无效等不可重试的故障，将错误存入数据库。
    
2.  支付系统从重试队列消费事件，并重试失败的支付交易。
    
3.  如果支付交易再次失败：
    
    3a. 如果重试次数未超过阈值，则将事件路由到重试队列。

### 恰好一次交付

支付系统可能遇到的最严重问题之一，就是重复向客户扣款。我们的设计必须保证支付系统恰好执行一次支付订单 \[16\]。

乍看之下，恰好一次交付似乎很难实现，但如果把问题分成两部分，就容易解决得多。从数学上说，当一个操作满足以下条件时，它就被恰好执行一次：

1.  至少执行一次。
    
2.  同时，至多执行一次。
    

我们将说明如何通过重试实现至少一次，以及如何通过幂等性检查实现至多一次。

#### 重试

有时，由于网络错误或超时，我们需要重试支付交易。重试提供至少一次保证。例如，图 11 中，客户端尝试支付 10 美元，但网络连接不佳，支付请求不断失败。在这个例子中，网络最终恢复，请求在第 4 次尝试时成功。

![图中的时序图展示了客户端与支付系统之间的交互。两条竖线分别表示客户端和支付系统，水平箭头表示信息流向。客户端发起四次支付尝试，每次金额为 10 美元，以从客户端指向支付系统、标为“支付 10 美元”的箭头表示。前三次尝试都支付失败，以红色“X”和支付系统发回客户端的“支付失败”消息表示。客户端每次都会重试，由“重试”标签标示。第四次尝试成功，“支付 10 美元”旁有蓝色勾号，且“支付成功”消息返回客户端。该图直观展示了持续重试直至支付处理成功的机制。](https://bytebytego.com/images/courses/system-design-interview/payment-system/figure-11-retry-SUMHMG67.svg)

图 11 重试

确定适当的重试间隔非常重要。以下是几种常见的重试策略。

-   立即重试：客户端立即重新发送请求。
    
-   固定间隔：支付失败后等待固定时间，再次尝试重试。
    
-   递增间隔：客户端在首次重试前等待较短时间，之后每次重试的等待时间逐步增加。
    
-   指数退避 \[17\]：每次重试失败后，将重试之间的等待时间翻倍。例如，请求第一次失败时，1 秒后重试；第二次失败时，等待 2 秒后再次重试；第三次失败时，等待 4 秒后再重试。
    
-   取消：客户端可以取消请求。当故障是永久性的，或者重复请求不太可能成功时，通常采用这种做法。
    

确定合适的重试策略并不容易，没有“一招通吃”的方案。一般而言，如果网络问题不太可能在短时间内解决，就使用指数退避。过于激进的重试策略会浪费计算资源，并可能造成服务过载。一种良好做法是在返回错误码时带上 Retry-After 头。

重试的一个潜在问题是重复支付。来看两个场景。

**场景 1**：支付系统通过托管支付页面与 PSP 集成，客户端点击了两次支付按钮。

**场景 2**：PSP 已成功处理支付，但由于网络错误，响应未能到达我们的支付系统。用户再次点击“支付”按钮，或者客户端重试支付。

为避免重复支付，支付操作必须至多执行一次。这种至多一次保证也称为幂等性。

#### 幂等性

幂等性是确保至多一次保证的关键。根据维基百科的定义，“幂等性是数学和计算机科学中某些操作的一种性质：这些操作可以多次应用，而结果与第一次应用之后的结果相比不会发生变化” \[18\]。从 API 的角度看，幂等性意味着客户端可以反复发起相同的调用，并得到相同的结果。

对于客户端（网页和移动应用）与服务器之间的通信，幂等键通常是由客户端生成、在一定时间后过期的唯一值。UUID 常用作幂等键，Stripe \[19\]、PayPal \[20\] 等许多科技公司也推荐这种做法。要执行幂等的支付请求，需要在 HTTP 头中添加幂等键：_<idempotency-key: key\_value>_。

了解了幂等性的基础知识后，我们来看看它如何帮助解决上述重复支付问题。

**场景 1：如果客户快速点击两次“支付”按钮，会怎样？**

图 12 中，当用户点击“支付”时，幂等键作为 HTTP 请求的一部分发送到支付系统。在电商网站中，幂等键通常是结账前购物车的 ID。

第二个请求会被视为一次重试，因为支付系统已经见过这个幂等键。当我们在请求头中携带先前指定过的幂等键时，支付系统会返回前一个请求的最新状态。

![图中的时序图展示了支付系统中的幂等性。虚线将图分为两部分，表示重试场景。上半部分展示客户端通过带有幂等键（一个 UUID）的 POST 请求，向“支付系统”发起“首次请求”。支付系统处理请求，并向客户端返回“扣款成功”消息。下半部分描绘重试场景。标为“重试”的客户端使用相同的幂等键，再次向“支付系统”发送 POST 请求。这一次，支付系统识别出幂等键，返回“返回之前的消息”，表示请求已经处理过，从而避免重复处理。支付系统旁的注释说明，它已经见过该幂等键，不会再次处理该请求。箭头表示客户端和支付系统之间的信息流向。](https://bytebytego.com/images/courses/system-design-interview/payment-system/figure-12-idempotency-DC3RCILB.svg)

图 12 幂等性

如果检测到多个带相同幂等键的并发请求，系统只处理其中一个，其余请求会收到 _“429 Too Many Requests”_ 状态码。

为支持幂等性，我们可以使用数据库的唯一键约束。例如，将数据库表的主键用作幂等键。工作原理如下：

1.  支付系统收到一笔支付时，会尝试向数据库表中插入一行。
    
2.  插入成功，说明我们之前没有见过这笔支付请求。
    
3.  如果因为相同主键已存在而插入失败，说明我们之前见过这笔支付请求。第二个请求不会被处理。
    

**场景 2：PSP 已成功处理支付，但由于网络错误，响应未能到达我们的支付系统。随后用户再次点击“支付”。**

如图 4 的第 2 步和第 3 步所示，支付服务向 PSP 发送 nonce，PSP 返回对应的令牌。nonce 唯一表示支付订单，令牌又与 nonce 一一对应。因此，令牌与支付订单一一对应。

当用户再次点击“支付”按钮时，支付订单相同，因此发送给 PSP 的令牌也相同。由于 PSP 侧将令牌用作幂等键，PSP 能识别出重复支付，并返回上一次执行的状态。

### 一致性

执行一次支付会调用多个有状态服务：

1.  支付服务保存 nonce、令牌、支付订单、执行状态等与支付有关的数据。
    
2.  账本保存所有会计数据。
    
3.  钱包保存商家的账户余额。
    
4.  PSP 保存支付执行状态。
    
5.  为提高可靠性，数据可能会在不同的数据库副本之间复制。
    

在分布式环境中，任意两个服务之间的通信都可能失败，进而导致数据不一致。下面介绍一些解决支付系统中数据不一致问题的技术。

要维护内部服务之间的数据一致性，确保恰好一次处理非常重要。

要维护内部服务与外部服务（PSP）之间的数据一致性，我们通常依靠幂等性和对账。如果外部服务支持幂等性，我们应在支付重试操作中使用相同的幂等键。即使外部服务支持幂等 API，仍然需要对账，因为我们不应该假设外部系统始终正确。

如果数据存在复制，复制延迟可能导致主数据库与副本之间数据不一致。通常有两种解决办法：

1.  所有读写都仅由主数据库处理。这种方式容易配置，但明显的缺点是可扩展性有限。副本用于保证数据可靠性，却不承载任何流量，因而浪费资源。
    
2.  确保所有副本始终保持同步。我们可以使用 Paxos \[21\]、Raft \[22\] 等共识算法，也可以使用 YugabyteDB \[23\] 或 CockroachDB \[24\] 这样的基于共识的分布式数据库。
    

### 支付安全

支付安全非常重要。在本次系统设计的最后一部分，我们简要介绍几种应对网络攻击和银行卡盗用的技术。

## 第 4 步：总结

本章探讨了入款流程和出款流程，并深入讨论了重试、幂等性和一致性。章节最后还介绍了支付错误处理和安全性。

支付系统极其复杂。虽然我们已经讨论了许多主题，但还有更多值得一提。下面列出了一些具有代表性的相关主题，但并未穷尽所有内容。

-   监控。监控关键指标是任何现代应用的重要组成部分。借助全面监控，我们可以回答“某种支付方式的平均受理成功率是多少？”“服务器的 CPU 使用率是多少？”等问题。我们可以创建这些指标，并在仪表盘上展示。
    
-   告警。当发生异常时，及时向值班开发者告警很重要，以便他们迅速响应。
    
-   调试工具。“为什么支付失败？”是一个常见问题。为了方便工程师和客服人员排查，必须开发相应工具，让工作人员能够查看某笔支付交易的交易状态、处理服务器的历史记录、PSP 记录等信息。
    
-   货币兑换。在为国际用户设计支付系统时，货币兑换是一个重要考量因素。
    
-   地域差异。不同地区使用的支付方式可能完全不同。
    
-   现金支付。在印度、巴西和其他一些国家，现金支付非常普遍。Uber \[28\] 和 Airbnb \[29\] 都发表过详细的工程博客，介绍它们如何处理基于现金的支付。
