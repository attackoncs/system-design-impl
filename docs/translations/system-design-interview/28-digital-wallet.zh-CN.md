假设我们被要求设计一个支持跨钱包余额转账操作的数字钱包应用后端。在面试开始时，我们会提出澄清问题，以明确需求。

## 第 1 步：理解问题并确定设计范围

**候选人：** 我们只需要关注两个数字钱包之间的余额转账操作吗？需要考虑其他功能吗？

**面试官**：我们只关注余额转账操作。

**候选人**：系统需要支持每秒多少笔交易（TPS）？

**面试官**：假设是 1,000,000 TPS。

**候选人**：数字钱包对正确性有严格要求。我们可以假设事务保证 \[1\] 足以满足要求吗？

**面试官**：可以。

**候选人**：我们需要证明正确性吗？

**面试官**：这是个好问题。通常只有在交易完成后，才能验证正确性。一种验证方法是将内部记录与银行对账单进行比较。对账的局限在于，它只能显示差异，无法说明差异是如何产生的。因此，我们希望设计一个具有可重现性的系统，即始终可以从最开始重放数据，重建历史余额。

**候选人**：可以假设可用性要求为 99.99% 吗？

**面试官**：可以。

**候选人**：需要考虑外汇兑换吗？

**面试官**：不需要，这不在本次范围内。

总而言之，我们的数字钱包需要支持以下要求：

-   支持两个数字钱包之间的余额转账操作。
    
-   支持 1,000,000 TPS。
    
-   可靠性至少为 99.99%。
    
-   支持事务。
    
-   支持可重现性。
    

### 粗略估算

讨论 TPS 时，我们隐含了使用事务型数据库的前提。如今，运行在普通数据中心节点上的关系型数据库，每秒可以支持几千笔事务。例如，参考资料 \[2\] 给出了一些流行事务型数据库服务器的性能基准测试。假设一个数据库节点可以支持 1,000 TPS。要达到 100 万 TPS，就需要 1,000 个数据库节点。

不过，这个计算略有偏差。每条转账命令需要两个操作：从一个账户扣款，再向另一个账户入账。要支持每秒 100 万次转账，系统实际上需要处理高达 200 万 TPS，这意味着需要 2,000 个节点。

表 1 展示了“单节点 TPS”（单个节点可以处理的 TPS）变化时所需的节点总数。假设硬件保持不变，单个节点每秒能处理的事务越多，所需节点总数就越少，硬件成本也就越低。因此，我们的设计目标之一是提高单个节点可以处理的事务数量。

| 单节点 TPS | 节点数量 |
| ------------ | ----------- |
| 100          | 20,000      |
| 1,000        | 2,000       |
| 10,000       | 200         |

### API 设计

我们采用 RESTful API 规范。在这次面试中，只需要支持一个 API：

| **API**                           | **详情**                                  |
| --------------------------------- | ------------------------------------------- |
| POST /v1/wallet/balance\_transfer | 将余额从一个钱包转移到另一个钱包 |

请求参数如下：

| **字段**       | **说明**           | **类型**                |
| --------------- | ------------------------- | ----------------------- |
| from\_account   | 借记账户         | string                  |
| to\_account     | 贷记账户        | string                  |
| amount          | 金额       | string                  |
| currency        | 货币类型         | string (ISO 4217 \[3\]) |
| transaction\_id | 用于去重的 ID | uuid                    |

响应体示例：

```
{
"Status": "success"
"Transaction_id": "01589980-2664-11ec-9621-0242ac130002"
}
```

值得一提的是，“amount”字段的数据类型是“string”，而不是“double”。我们已在“支付系统”一章解释过原因。

在实践中，许多人仍然选择使用 float 或 double 表示数字，因为几乎所有编程语言和数据库都支持它们。只要理解精度丢失的潜在风险，这也是一种合适的选择。

### 内存分片方案

钱包应用为每个用户账户维护账户余额。适合表示这种 <user,balance> 关系的数据结构是映射，也称哈希表（map）或键值存储。

Redis 是一种流行的内存存储选择。单个 Redis 节点不足以处理 100 万 TPS。我们需要搭建 Redis 节点集群，并将用户账户均匀分布到这些节点上。这个过程称为分区或分片。

要将键值数据分布到 _N_ 个分区中，可以计算键的哈希值，再除以 _N_。余数就是目标分区。下面的伪代码展示了分片过程：

```
String accountID = "A";
Int partitionNumber = 7;
Int myPartition = accountID.hashCode() % partitionNumber;
```

分区数量和所有 Redis 节点的地址可以存储在一个集中位置。我们可以使用 Zookeeper \[4\] 作为高可用的配置存储方案。

这个方案的最后一个组件是处理转账命令的服务，我们称之为钱包服务。它有几项关键职责。

1.  接收转账命令。
    
2.  验证转账命令。
    
3.  如果命令有效，就更新转账所涉及的两个用户的账户余额。在集群中，这两个账户余额很可能位于不同的 Redis 节点上。
    

钱包服务是无状态的，容易进行水平扩展。图 3 展示了内存方案。

图 3 内存方案

在这个例子中，我们有 3 个 Redis 节点，以及 A、B、C 三个客户端。它们的账户余额均匀分布在这三个 Redis 节点上。示例中还有两个钱包服务节点，负责处理余额转账请求。当其中一个钱包服务节点收到从客户端 A 向客户端 B 转账 1 美元的命令时，它会向两个 Redis 节点发出两条命令。对于保存客户端 A 账户的 Redis 节点，钱包服务从该账户扣除 1 美元；对于客户端 B，钱包服务向该账户增加 1 美元。

**候选人**：在这个设计中，账户余额分布在多个 Redis 节点上，Zookeeper 用来维护分片信息。无状态的钱包服务利用分片信息定位客户端对应的 Redis 节点，并更新相应的账户余额。

**面试官**：这个设计能运行，但不满足正确性要求。每次转账，钱包服务都要更新两个 Redis 节点，而我们无法保证两次更新都会成功。例如，如果钱包服务节点在第一次更新成功后、第二次更新完成前崩溃，就会造成转账未完成。这两次更新需要放在同一个原子事务中。

### 分布式事务

#### 数据库分片

如何使两个不同存储节点上的更新具备原子性？第一步是将每个 Redis 节点替换为支持事务的关系型数据库节点。图 4 展示了这种架构。这一次，客户端 A、B、C 被分区到 3 个关系型数据库中，而非 3 个 Redis 节点中。

![图中展示了钱包转账功能的系统设计。两个用圆圈表示的“转账命令”输入启动转账流程，每条命令都指向各自的“钱包服务”矩形框，作为处理单元。这些钱包服务与三个独立的“关系型数据库”圆柱体交互，每个数据库都包含“ID”和“余额”列的数据（示例数据为 ID A、B、C，各自的余额为 1）。钱包服务访问并更新这些数据库中的余额信息。关键在于，两个钱包服务都与标有“分区信息”的“Zookeeper”数据库圆柱体通信，表示这是一个由 Zookeeper 管理三个关系型数据库间数据分区的分布式系统架构。钱包服务和关系型数据库之间的连接表明，每个钱包服务都可以跨这三个数据库访问和修改数据，暗示系统具备分担负载或处理数据冗余的机制。](https://bytebytego.com/images/courses/system-design-interview/digital-wallet/figure-4-relational-database-L3DEQYTB.svg)

图 4 关系型数据库

使用支持事务的数据库只解决了一部分问题。如上一节所述，一条转账命令很可能需要更新两个不同数据库中的两个账户，无法保证两次更新操作恰好同时处理。如果钱包服务刚更新完第一个账户余额就重启了，如何确保第二个账户也会得到更新？

#### 分布式事务：两阶段提交

在分布式系统中，一个事务可能涉及多个节点上的多个进程。要使事务具有原子性，分布式事务可能就是答案。实现分布式事务有两种方式：底层方案和上层方案。下面分别介绍。

底层方案依赖数据库本身。最常用的算法称为两阶段提交（2PC）。顾名思义，它有两个阶段，如图 5 所示。

![图中展示了一个分布式事务的两阶段提交协议，参与方包括协调者（标为“协调者（钱包服务）”）和两个数据库（标为“数据库 A”和“数据库 C”）。横轴表示时间，图中展示了事件的先后顺序。协调者向两个数据库发送“写入数据”请求，以启动事务。随后，每个数据库锁定各自的数据（以“锁定 A”和“锁定 C”表示），再向协调者返回“ok”确认。这构成第 1 阶段（“准备”）。协调者收到两个数据库的“ok”后，进入第 2 阶段（“提交”），发出提交信号。每个数据库收到提交信号后写入数据，以表示实际数据写入的红线标示，然后释放各自的锁（“解锁 A”和“解锁 C”），再向协调者返回“ok”，确认成功完成。整个流程使用圆圈表示事务的不同阶段，并用箭头表示协调者与数据库之间消息和数据的流转。](https://bytebytego.com/images/courses/system-design-interview/digital-wallet/figure-5-two-phase-commit-W3HB4IJO.svg)

图 5 两阶段提交（来源 \[5\]）

1.  协调者（在我们的例子中就是钱包服务）像平常一样在多个数据库上执行读写操作。如图 5 所示，数据库 A 和 C 都被加锁。
    
2.  应用即将提交事务时，协调者要求所有数据库准备提交事务。
    
3.  在第二阶段，协调者收集所有数据库的回复，并执行以下操作：
    
    1.  如果所有数据库都回复“是”，协调者就要求所有数据库提交它们收到的事务。
        
    2.  如果任何一个数据库回复“否”，协调者就要求所有数据库中止事务。
        

这是一个底层方案，因为准备步骤需要对数据库事务进行特殊修改。例如，X/Open XA \[6\] 标准可以协调异构数据库，以实现两阶段提交。两阶段提交最大的问题是性能不佳，因为等待其他节点的消息时，锁可能会被持有很长时间。两阶段提交的另一个问题是协调者可能成为单点故障，如图 6 所示。

![图中的简化系统架构图展示了一个分布式事务，参与方包括协调者（标为“协调者（钱包服务）”）和两个数据库（标为“数据库 A”和“数据库 C”）。协调者依次向两个数据库发起写入操作。箭头表示数据流向。协调者首先向数据库 A 发送“写入数据”请求，并收到“ok”确认。随后，对数据库 C 重复这一过程。虚线标示了一个时间点。初始写入之后，协调者进入标注为“准备”的阶段。然而，准备阶段尚未完成，协调者就发生崩溃，以红色的“X 已崩溃”标记。崩溃后，两个数据库分别对隐含的准备阶段请求返回“是”，表示它们已准备好提交事务。时间轴展示了事件的发展，“X”标记表示协调者故障，以及随后数据库各自返回的响应。该图直观展示了分布式事务中一种潜在的故障场景，以及数据库随后对该场景的处理情况（或未能处理的情况）。](https://bytebytego.com/images/courses/system-design-interview/digital-wallet/figure-6-coordinator-crashes-MTPFFNSD.svg)

#### 分布式事务：尝试—确认/取消（TC/C）

TC/C 是一种补偿事务 \[7\]，包含两个步骤：

1.  在第一阶段，协调者要求所有数据库为该事务预留资源。
    
2.  在第二阶段，协调者收集所有数据库的回复：
    
    1.  如果所有数据库都回复“是”，协调者就要求所有数据库确认操作，这就是尝试—确认（Try-Confirm）流程。
        
    2.  如果任何一个数据库回复“否”，协调者就要求所有数据库取消操作，这就是尝试—取消（Try-Cancel）流程。
        

需要注意，两阶段提交的两个阶段包含在同一个事务中，而在 TC/C 中，每个阶段都是独立的事务。

**TC/C 示例**

使用实际例子会更容易说明 TC/C 的工作原理。假设要从账户 A 向账户 C 转账 1 美元。表 2 概括了 TC/C 在各个阶段如何执行。

| 阶段  | 操作           | A                   | C                   |
| ------ | ------------------- | ------------------- | ------------------- |
| 1      | 尝试                 | 余额变化：-$1 | 不做任何操作          |
| 2      | 确认             | 不做任何操作          | 余额变化：+$1 |
| 取消 | 余额变化：+$1 | 不做任何操作          |                     |

表 2 TC/C 示例

假设钱包服务是 TC/C 的协调者。分布式事务开始时，账户 A 的余额为 1 美元，账户 C 的余额为 0 美元。

**第一阶段：尝试**

在尝试阶段，作为协调者的钱包服务向两个数据库发送两条事务命令：

1.  对于包含账户 A 的数据库，协调者启动一个本地事务，将 A 的余额减少 1 美元。
    
2.  对于包含账户 C 的数据库，协调者向其发送 NOP（无操作）。为了让示例适用于其他场景，我们假设协调者向这个数据库发送一条 NOP 命令。数据库对 NOP 命令不做任何操作，并始终向协调者回复成功消息。
    

图 7 展示了尝试阶段。粗线表示事务持有锁。

**第二阶段：确认**

如果两个数据库都回复“是”，钱包服务就启动接下来的确认阶段。

账户 A 的余额已在第一阶段更新，因此钱包服务无需再修改其余额。不过，在第一阶段，账户 C 尚未收到来自账户 A 的 1 美元。在确认阶段，钱包服务必须向账户 C 的余额增加 1 美元。

**第二阶段：取消**

如果最初的尝试阶段失败了，会怎样？在上面的例子中，我们假设针对账户 C 的 NOP 操作总能成功，但实际上它也可能失败。例如，账户 C 可能是一个非法账户，监管机构已要求禁止该账户的任何资金流入或流出。在这种情况下，必须取消分布式事务，并执行清理。

由于账户 A 的余额已在尝试阶段的事务中更新，钱包服务不可能取消一个已经完成的事务。它能做的是启动另一个事务，撤销尝试阶段事务的效果，也就是向账户 A 加回 1 美元。

由于账户 C 在尝试阶段未被更新，钱包服务只需向账户 C 所在的数据库发送一个 NOP 操作。

**两阶段提交与 TC/C 的比较**

表 3 表明，两阶段提交和 TC/C 有许多相似之处，但也存在差异。在两阶段提交中，第二阶段开始时，所有本地事务尚未完成（仍然持有锁）；而在 TC/C 中，第二阶段开始时，所有本地事务均已完成（锁已释放）。换句话说，两阶段提交的第二阶段用于完成尚未结束的事务，例如中止或提交；而 TC/C 的第二阶段则在发生错误时，使用逆向操作抵消前一个事务的结果。下表概括了它们的差异。

| **第一阶段** | **第二阶段：成功**                                    | **第二阶段：失败**                                      |
| --------------- | ------------------------------------------------------------ | ----------------------------------------------------------- |
| 2PC             | 本地事务尚未完成                          | 提交所有本地事务 取消所有本地事务 |
| TC/C            | 所有本地事务均已完成，已提交或已取消 | 如有必要，执行新的本地事务                    |

表 3 两阶段提交与 TC/C 的比较

TC/C 也称为基于补偿的分布式事务。它属于上层方案，因为补偿（也称“撤销”）是在业务逻辑中实现的。这种方式的优点是与数据库无关。只要数据库支持事务，TC/C 就能工作。缺点是我们必须在应用层的业务逻辑中管理分布式事务的细节，并处理其复杂性。

**阶段状态表**

我们仍未回答之前的问题：如果钱包服务在 TC/C 执行过程中重启，会怎样？重启后，先前所有操作历史都可能丢失，系统可能不知道如何恢复。

解决办法很简单。我们可以将 TC/C 的进度以阶段状态的形式存入事务型数据库。阶段状态至少包含以下信息。

-   分布式事务的 ID 和内容。
    
-   每个数据库在尝试阶段的状态。状态可以是“尚未发送”“已发送”和“已收到响应”。
    
-   第二阶段的名称，可以是“确认”或“取消”，并可根据尝试阶段的结果计算得出。
    
-   第二阶段的状态。
    
-   乱序标记（稍后在“乱序执行”一节中解释）。
    

阶段状态表应该放在哪里？通常，我们会将阶段状态存储在包含出款钱包账户的数据库中。图 10 展示了更新后的架构图。

**不平衡状态**

你有没有注意到，在尝试阶段结束时，少了 1 美元（图 11）？

假设一切顺利，尝试阶段结束时，账户 A 被扣除了 1 美元，而账户 C 保持不变。账户 A 和 C 的余额之和为 0 美元，小于 TC/C 开始时的总额。这违反了一项基本会计规则：交易前后的总额应该保持不变。

好消息是，TC/C 仍然维持了事务保证。TC/C 由多个独立的本地事务组成。由于 TC/C 由应用驱动，应用本身可以看到这些本地事务之间的中间结果。相比之下，数据库事务或采用两阶段提交的分布式事务由数据库维护，其过程对上层应用不可见。

分布式事务在执行期间，总会出现数据差异。我们可能察觉不到这些差异，因为数据库等底层系统已经修复了它们。否则，就需要我们自行处理（例如 TC/C）。

尝试阶段有三种选择：

| 尝试阶段的选择 | 账户 A | 账户 C |
| ----------------- | --------- | --------- |
| 选择 1          | \-$1      | NOP       |
| 选择 2          | NOP       | +$1       |
| 选择 3          | \-$1      | +$1       |

表 4 尝试阶段的选择

这三种选择看起来都合理，但其中有些并不可行。

对于选择 2，如果账户 C 的尝试阶段成功，而账户 A 的尝试阶段（NOP）失败，钱包服务就需要进入取消阶段。这时可能恰好有其他操作介入，将账户 C 中的 1 美元转走。之后，钱包服务尝试从账户 C 扣除 1 美元时，会发现已经没有余额，从而违反分布式事务的事务保证。

对于选择 3，如果从账户 A 扣除 1 美元与向账户 C 增加 1 美元并发执行，会带来许多复杂情况。例如，账户 C 已经增加了 1 美元，但账户 A 扣款失败。这时该怎么办？

因此，选择 2 和选择 3 都存在缺陷，只有选择 1 是可行的。

**乱序执行**

TC/C 的一个副作用是乱序执行。用例子说明会更容易理解。

我们沿用上面的例子，从账户 A 向账户 C 转账 1 美元。如图 12 所示，在尝试阶段，针对账户 A 的操作失败，并向钱包服务返回失败结果。钱包服务随后进入取消阶段，向账户 A 和账户 C 都发送取消操作。

假设处理账户 C 的数据库发生了一些网络问题，它先收到取消指令，后收到尝试指令。此时，没有任何操作可供取消。

图 12 展示了乱序执行。

![图中的系统设计图展示了涉及协调者（标为“协调者（钱包服务）”）和两个数据库（标为“数据库 A”和“数据库 C”）的两阶段操作。第一阶段展示了协调者发起“尝试”操作，向数据库 A 发送请求。数据库 A 处理请求，并将其转发给数据库 A 内部的另一个组件。第一阶段以“X 失败”标记结束。第二阶段标为“第二阶段：取消”，展示协调者尝试取消之前的操作，向数据库 A 和数据库 C 都发送“取消”请求。然而，数据库 C 在收到“取消”操作*之后*才收到协调者发出的“尝试”操作，图中用“乱序：取消操作先于尝试操作到达”突出说明这一乱序到达情况。数据库 C 对尝试操作的响应标为“尝试”，而数据库 A 接收并处理两个“取消”请求。图中以圆圈表示处理点，以箭头表示组件之间请求和响应的流转，竖直虚线将两个阶段分开。](https://bytebytego.com/images/courses/system-design-interview/digital-wallet/figure-12-out-of-order-execution-OSSZ5U7M.svg)

图 12 乱序执行

为处理乱序操作，我们增强现有逻辑，使每个节点都可以在尚未收到尝试指令时取消一个 TC/C，具体更新如下：

-   乱序的取消操作在数据库中留下一个标记，表示已经见过取消操作，但尚未见过尝试操作。
    
-   增强尝试操作，使其始终检查是否存在乱序标记；如果存在，就返回失败。
    

这就是我们在“阶段状态表”一节中为阶段状态表添加乱序标记的原因。

#### 分布式事务：Saga 事务

**线性顺序执行**

另一种流行的分布式事务方案称为 Saga 事务 \[8\]。Saga 事务是微服务架构中的事实标准，其思路很简单：

1.  所有操作按顺序排列。每个操作都是各自数据库上的独立事务。
    
2.  操作从第一个执行到最后一个。一个操作完成后，触发下一个操作。
    
3.  某个操作失败时，整个流程会使用补偿事务，从当前操作开始，按逆序一直回滚到第一个操作。因此，如果一个分布式事务有 _n_ 个操作，就需要准备 2_n_ 个操作：正常情况下的 _n_ 个操作，以及回滚时另外 _n_ 个补偿事务操作。

如何协调这些操作？有两种方式：

1.  协同。在微服务架构中，参与 Saga 分布式事务的所有服务，都通过订阅其他服务的事件来执行各自的工作。因此，这是一种完全去中心化的协调方式。
    
2.  编排。由单一协调者指示所有服务按正确顺序执行各自的工作。
    

选择哪种协调模型取决于业务需求和目标。协同方案的挑战在于，服务之间完全以异步方式通信，因此每个服务都必须维护内部状态机，才能知道其他服务发出事件时应该做什么。服务数量较多时，这会变得难以管理。编排方案能够很好地处理复杂性，因此通常是数字钱包系统中的首选方案。

实际中该选哪一种？答案取决于延迟要求。如表 5 所示，Saga 事务中的操作必须按线性顺序执行，而 TC/C 中的操作可以并行执行。因此，选择取决于以下几个因素：

1.  如果没有延迟要求，或者涉及的服务很少，例如我们的转账示例，那么两者都可以。如果想顺应微服务架构的趋势，就选择 Saga 事务。
    
2.  如果系统对延迟敏感，并且包含许多服务或操作，TC/C 可能是更好的选择。

**面试官**：做得很好！分布式事务方案可行，但某些情况下可能表现不佳。例如，用户可能在应用层输入错误的操作，此时指定的金额可能不正确。我们需要一种方法，能够追溯问题根因，并审计所有账户操作。如何做到这一点？

### 事件溯源

#### 背景

在现实中，数字钱包提供商可能需要接受审计。外部审计人员可能提出一些颇具挑战性的问题，例如：

1.  我们知道任意时刻的账户余额吗？
    
2.  我们如何知道历史和当前账户余额都是正确的？
    
3.  代码变更后，如何证明系统逻辑仍然正确？
    

一种能够系统性回答这些问题的设计思想是事件溯源，它是领域驱动设计（DDD）\[9\] 中发展出来的一项技术。

#### 定义

事件溯源有四个重要术语。

1.  命令
    
2.  事件
    
3.  状态
    
4.  状态机
    

**命令**

命令是外部世界希望执行的操作。例如，如果要从客户端 A 向客户端 C 转账 1 美元，这笔转账请求就是一条命令。

在事件溯源中，让所有内容都有明确顺序非常重要。因此，命令通常放入 FIFO（先进先出）队列。

**事件**

命令表达的是意图，而不是事实，因为有些命令可能无效，无法执行。例如，如果转账后账户余额会变成负数，转账操作就会失败。

在对命令执行任何操作之前，必须先进行验证。一旦命令通过验证，它就是有效的，且必须执行。执行的结果称为事件。

命令与事件有两个主要区别。

1.  事件必须执行，因为它们代表已验证的事实。在实践中，我们通常用过去时来描述事件。如果命令是“从 A 向 C 转账 1 美元”，对应的事件就是“**已**从 A 向 C 转账 1 美元”。
    
2.  命令可能包含随机性或 I/O，但事件必须具有确定性。事件代表历史事实。
    

事件生成过程有两个重要性质。

1.  一条命令可以生成任意数量的事件，可能为零，也可能为多个。
    
2.  事件生成可能包含随机性，也就是说，无法保证一条命令始终生成相同的事件。事件生成可能包含外部 I/O 或随机数。我们会在本章接近结尾时，更详细地讨论这一性质。
    

事件顺序必须遵循命令顺序。因此，事件也存储在 FIFO 队列中。

**状态**

状态是应用事件时将会发生变化的内容。在钱包系统中，状态是所有客户账户的余额，可以用映射数据结构表示。键是账户名称或 ID，值是账户余额。通常使用键值存储保存映射数据结构。关系型数据库也可以看作键值存储，其中键是主键，值是表中的行。

**状态机**

状态机驱动事件溯源过程，它有两项主要功能。

1.  验证命令并生成事件。
    
2.  应用事件以更新状态。
    

事件溯源要求状态机的行为具有确定性。因此，状态机本身绝不能包含任何随机性。例如，它绝不应该通过 I/O 从外部读取任何随机内容，也不应该使用随机数。将一个事件应用于一个状态时，它应始终生成相同的结果。

图 14 展示了事件溯源架构的静态视图。状态机负责将命令转换为事件，并应用事件。由于状态机有两项主要功能，我们通常将它画成两个状态机：一个负责验证命令，另一个负责应用事件。

4.  读取下一个事件。

#### 可重现性

事件溯源相对于其他架构，最重要的优势就是可重现性。

在前面提到的分布式事务方案中，钱包服务将更新后的账户余额（状态）保存到数据库，很难知道账户余额为什么发生变化。同时，更新操作会丢失历史余额信息。在事件溯源设计中，所有变更首先被保存为不可变的历史记录。数据库只用于提供任意给定时刻余额情况的最新视图。

我们始终可以从头重放事件，重建历史余额状态。由于事件列表不可变，状态机逻辑又具有确定性，因此能够保证每次重放生成的历史状态相同。

可重现性有助于回答审计人员在本节开头提出的难题。这里再次列出这些问题。

1.  我们知道任意时刻的账户余额吗？
    
2.  我们如何知道历史和当前账户余额都是正确的？
    
3.  代码变更后，如何证明系统逻辑仍然正确？
    

对于第一个问题，我们可以从最开始重放事件，一直重放到需要知道账户余额的那个时刻，从而得到答案。

对于第二个问题，我们可以根据事件列表重新计算账户余额，以验证其正确性。

对于第三个问题，我们可以使用不同版本的代码处理这些事件，并验证结果是否一致。

由于具备审计能力，事件溯源常常成为钱包服务的事实标准方案。

#### 命令查询职责分离（CQRS）

到目前为止，我们设计的钱包服务能够高效地在账户之间转移资金。不过，客户端仍然不知道账户余额是多少。需要一种方法发布状态（余额信息），使事件溯源框架之外的客户端可以获知状态。

直观来看，可以创建数据库（历史状态）的只读副本，并将其提供给外部世界。事件溯源对这个问题的回答略有不同。

事件溯源发布所有事件，而不是发布状态（余额信息）。外部世界可以自行重建任何定制的状态。这种设计思想称为 CQRS \[11\]。

在 CQRS 中，一个状态机负责状态的写入部分，但可以有许多只读状态机负责构建状态视图。这些视图可以用于查询。

这些只读状态机可以从事件队列中派生出不同的状态表示。例如，客户可能想知道自己的余额，一个只读状态机可以将状态存入数据库，以提供余额查询。另一个状态机可以构建特定时间段内的状态，帮助调查可能的重复扣款等问题。这些状态信息构成审计轨迹，有助于财务记录对账。

只读状态机会有一定程度的滞后，但最终总会追上。这种架构设计具有最终一致性。

## 第 3 步：深入设计

本节将深入探讨实现高性能、可靠性和可扩展性的技术。

### 高性能事件溯源

在前面的例子中，我们使用 Kafka 存储命令和事件，使用数据库存储状态。下面探索一些优化方法。

#### 基于文件的命令列表和事件列表

第一项优化是将命令和事件保存到本地磁盘，而不是 Kafka 这样的远程存储中。这可以避免跨网络传输所需的时间。事件列表使用只追加的数据结构。追加是一种顺序写入操作，通常非常快。即使是机械硬盘，这种方式也表现良好，因为操作系统针对顺序读写进行了大量优化。根据这篇 ACM Queue 文章 \[12\]，在某些情况下，磁盘顺序访问可能比内存随机访问更快。

第二项优化是在内存中缓存最近的命令和事件。如前所述，我们在命令和事件持久化后立即处理它们。可以将它们缓存在内存中，节省从本地磁盘重新加载的时间。

下面探讨一些实现细节。一种称为 mmap \[13\] 的技术非常适合实现上述优化。Mmap 可以在写入本地磁盘的同时，将最近的内容缓存在内存中。它将磁盘文件以数组形式映射到内存。操作系统会将文件的某些部分缓存在内存中，以加速读写操作。对于只追加的文件操作，几乎可以保证所有数据都保存在内存中，因此速度很快。

#### 快照

当所有内容都改为基于文件之后，我们来考虑如何加速状态重现过程。最初介绍可重现性时，状态机每次都必须从最开始处理事件。可以进行的一项优化是定期暂停状态机，并将当前状态保存到文件中，这就称为快照。

快照是历史状态的不可变视图。保存快照后，状态机便不必再从最开始恢复。它可以从快照读取数据，确定上次处理到哪里，再从那里继续处理。

对于钱包服务这样的金融应用，财务团队往往要求在 00:00 生成快照，以便核验当天发生的所有交易。最初介绍事件溯源的 CQRS 时，解决办法是建立一个只读状态机，从头读取直到指定时刻。有了快照，只读状态机只需要加载包含相应数据的一个快照。

快照是一个巨大的二进制文件，常见做法是将其保存在 HDFS \[16\] 这样的对象存储方案中。

### 可靠的高性能事件溯源

在解释解决方案之前，先来看看系统中哪些部分需要可靠性保证。

#### 可靠性分析

从概念上说，节点所做的一切都围绕两个概念：数据和计算。只要数据能够持久保存，就很容易在另一个节点上运行相同代码，恢复计算结果。这意味着我们只需关注数据的可靠性，因为数据一旦丢失，就再也无法找回。系统可靠性主要取决于数据可靠性。

系统中有四类数据。

1.  基于文件的命令。
    
2.  基于文件的事件。
    
3.  基于文件的状态。
    
4.  状态快照。
    

我们来详细看看如何确保每类数据的可靠性。

状态和快照始终可以通过重放事件列表重新生成。要提高状态和快照的可靠性，只需确保事件列表具有很强的可靠性。

现在来考察命令。表面上看，事件由命令生成，我们可能会认为，只需为命令提供很强的可靠性保证就足够了。乍看似乎正确，但这里忽略了一个重要问题：事件生成不保证具有确定性，也可能包含随机数、外部 I/O 等随机因素。因此，命令无法保证事件的可重现性。

现在该仔细考察事件了。事件代表会引起状态（账户余额）变化的历史事实。事件不可变，可以用于重建状态。

通过上述分析，我们得出结论：只有事件数据需要高可靠性保证。下一节将解释如何实现。

#### 共识

要提供高可靠性，我们需要将事件列表复制到多个节点。在复制过程中，必须保证以下性质。

1.  不丢失数据。
    
2.  日志文件内数据的相对顺序在各节点上保持一致。
    

为实现这些保证，基于共识的复制非常适合。共识算法确保多个节点就事件列表的内容达成共识。下面以 Raft \[17\] 共识算法为例。

Raft 算法保证，只要超过半数节点在线，它们的只追加列表就拥有相同数据。例如，如果我们有 5 个节点，并使用 Raft 算法同步数据，只要至少 3 个（超过半数）节点正常运行，如图 23 所示，系统作为一个整体仍能正常工作：

![图中是一个简单示意图，展示的概念可能与系统状态或可用性有关。图中有五个水平排列的圆形节点。前三个节点填充为浅绿色，每个圆圈下方都标为“正常”，表示运行中或活跃状态。后两个节点没有填充（为白色），每个圆圈下方都标为“宕机”，表示不活跃或故障状态。节点之间没有明确绘制连接，整体排列只是展示了一个状态不同的元素序列或元素组。整张图直观表达了系统组件的健康情况：三个组件正常，两个组件宕机。](https://bytebytego.com/images/courses/system-design-interview/digital-wallet/figure-23-raft-YUKRLGJR.svg)

图 23 Raft

在 Raft 算法中，节点可以有三种不同角色。

1.  领导者。
    
2.  候选者。
    
3.  跟随者。
    

Raft 算法的实现可以在 Raft 论文中找到。这里仅介绍总体概念，不深入细节。在 Raft 中，集群至多有一个领导者节点，其余节点是跟随者。领导者负责接收外部命令，并在集群节点之间可靠地复制数据。

使用 Raft 算法时，只要多数节点正常运行，系统就是可靠的。例如，集群有 3 个节点时，可以容忍 1 个节点发生故障；有 5 个节点时，可以容忍 2 个节点发生故障。

#### 可靠性方案

通过复制，基于文件的事件溯源架构就不再存在单点故障。下面来看实现细节。图 24 展示了具有可靠性保证的事件溯源架构。

![图中的系统架构图展示了使用 Raft 共识的分布式数据库系统。一个大矩形框包围了 Raft 节点组，组内有水平的三层结构。最上层和最下层为浅青色，标为“跟随者”，各自包含一个“事件”方框、一个表示 Raft 共识算法的圆形“Raft”组件，以及一个数据库圆柱体。中间一层为浅粉色，标为“命令”，其中包含一个“事件”方框、一个圆形“Raft”组件，以及一个数据库圆柱体。左侧的用户图标通过实线箭头，将命令发送到中间层的“命令”方框。命令方框处理这些命令，并通过其内部的 Raft 组件将它们发送到事件方框，事件方框再流向另一个圆形 Raft 组件，最终写入数据库圆柱体。虚线表示三层结构中的 Raft 组件之间的通信。Raft 节点组外的右侧，还有两个数据库圆柱体，每个前方都有一个圆形 Raft 组件。它们通过虚线接收组内 Raft 组件的数据。右侧的用户图标通过标为“查询”的实线箭头与系统交互，读取外部数据库圆柱体中的数据。底部的水平箭头将从左向右的数据流标为“写入”，将从右向左的数据流标为“读取”，概括了系统内的整体数据流向。](https://bytebytego.com/images/courses/system-design-interview/digital-wallet/figure-24-raft-node-group-EFJORSSU.svg)

图 24 Raft 节点组

图 24 中，我们部署了 3 个事件溯源节点。这些节点使用 Raft 算法可靠地同步事件列表。

领导者接收外部用户传入的命令请求，将其转换为事件，并将事件追加到本地事件列表。Raft 算法将新增事件复制给跟随者。

包括跟随者在内的所有节点都会处理事件列表，并更新状态。Raft 算法确保领导者和跟随者拥有相同的事件列表，而事件溯源保证：只要事件列表相同，所有状态就相同。

可靠的系统需要妥善处理故障，下面探讨如何处理节点崩溃。

如果领导者崩溃，Raft 算法会自动从其余健康节点中选出新领导者。新当选的领导者负责接收外部用户的命令。这保证了某个节点宕机时，整个集群仍能持续提供服务。

领导者崩溃时，命令列表可能尚未转换为事件。在这种情况下，客户端会通过超时或收到错误响应发现问题。客户端需要向新当选的领导者重新发送相同命令。

相比之下，跟随者崩溃更容易处理。如果跟随者崩溃，发给它的请求会失败。Raft 会无限重试来处理这种故障，直到崩溃节点重启，或由新节点替代它。

**候选人**：在这个设计中，我们使用 Raft 共识算法，将事件列表复制到多个节点。领导者接收命令，并将事件复制到其他节点。

**面试官**：是的，系统更可靠，也更能容忍故障。不过，要处理 100 万 TPS，一台服务器还不够。如何让系统更容易扩展？

### 分布式事件溯源

上一节解释了如何实现可靠的高性能事件溯源架构。它解决了可靠性问题，但有两个局限。

1.  数字钱包更新时，我们希望立即收到更新结果。但在 CQRS 设计中，请求与响应的流程可能较慢。这是因为客户端不知道数字钱包究竟何时更新，可能需要依靠定期轮询。
    
2.  单个 Raft 组的容量有限。达到一定规模后，我们需要对数据分片，并实现分布式事务。
    

下面看看如何解决这两个问题。

#### 拉取与推送

在拉取模型中，外部用户定期从只读状态机轮询执行状态。这种模型不具备实时性，如果轮询频率设置过高，还可能导致钱包服务过载。图 25 展示了拉取模型。

#### 分布式事务

一旦每个事件溯源节点组都采用同步执行，就可以复用 TC/C 或 Saga 事务这类分布式事务方案。假设我们对键的哈希值除以 2，以此对数据进行分区。

![图中的系统架构图展示了一个使用 Raft 达成共识、并处理命令和事件的分布式系统。系统分为“分区 1（账户 A）”和“分区 2（账户 C）”两部分，每个分区都包含一个 Raft 节点组。每个 Raft 组由三个节点组成：两个跟随者和一个领导者（以双圆圈表示）。在每个分区内，Raft 组处理命令（在粉色矩形中显示为从左向右流动）和事件（浅蓝色矩形）。命令由领导者节点处理，事件则复制到所有节点。“TCC/Saga 协调者”与系统交互，发送命令（红色箭头）并接收响应（蓝色箭头）。协调者还维护一张“阶段状态表”。“反向代理”充当中间层，接收各分区 Raft 节点组推送的实时状态更新（浅蓝色箭头）。虚线表示 Raft 组内部的数据流，实线箭头表示组件间的交互。系统通过 Raft 共识机制实现高可用性与容错能力。](https://bytebytego.com/images/courses/system-design-interview/digital-wallet/figure-28-final-design-36NRH5KI.svg)

图 28 最终设计

下面看看资金转账如何在最终的分布式事件溯源架构中工作。为便于理解，我们使用 Saga 分布式事务模型，只解释一切顺利、不发生任何回滚的流程。

转账包含两个分布式操作：A-$1 和 C+$1。Saga 协调者按图 29 所示协调执行：

1.  用户 A 向 Saga 协调者发送一个分布式事务，其中包含 A-$1 和 C+$1 两个操作。
    
2.  Saga 协调者在阶段状态表中创建一条记录，以跟踪事务状态。
    
3.  Saga 协调者检查操作顺序，确定需要先处理 A-$1。协调者将 A-$1 作为命令发送到包含账户 A 信息的分区 1。
    
4.  分区 1 的 Raft 领导者收到 A-$1 命令，并将其存入命令列表，然后验证该命令。如果有效，就将其转换为事件。系统使用 Raft 共识算法，在不同节点之间同步数据。同步完成后，执行该事件（从 A 的账户余额中扣除 1 美元）。
    
5.  事件同步后，分区 1 的事件溯源框架使用 CQRS，将数据同步到读取路径。读取路径重建状态和执行状态。
    
6.  分区 1 的读取路径将状态推送回事件溯源框架的调用方，即 Saga 协调者。
    
7.  Saga 协调者收到来自分区 1 的成功状态。
    
8.  Saga 协调者在阶段状态表中创建一条记录，表明分区 1 中的操作已成功。
    
9.  由于第一个操作成功，Saga 协调者开始执行第二个操作 C+$1。协调者将 C+$1 作为命令发送到包含账户 C 信息的分区 2。
    
10.  分区 2 的 Raft 领导者收到 C+$1 命令，并将其保存到命令列表。如果有效，就将其转换为事件。系统使用 Raft 共识算法，在不同节点之间同步数据。同步完成后，执行该事件（向 C 的账户增加 1 美元）。
    
11.  事件同步后，分区 2 的事件溯源框架使用 CQRS，将数据同步到读取路径。读取路径重建状态和执行状态。
    
12.  分区 2 的读取路径将状态推送回事件溯源框架的调用方，即 Saga 协调者。
    
13.  Saga 协调者收到来自分区 2 的成功状态。
    
14.  Saga 协调者在阶段状态表中创建一条记录，表明分区 2 中的操作已成功。
    
15.  此时，所有操作均已成功，分布式事务完成。Saga 协调者向调用方返回结果。


![图中的系统架构图展示了使用 TCC/Saga 和 Raft 共识的分布式事务处理系统。图中有两个分区：分区 1（账户 A）和分区 2（账户 C），每个分区都包含一个 Raft 节点组。每个 Raft 组由三个节点组成：两个跟随者和一个领导者（以带粗边框的圆形表示）。Raft 组中的每个节点都有“事件”和“命令”组件。“TCC/Saga 协调者”（1）通过“反向代理”与各分区交互。命令（3、9）从协调者发送到各分区 Raft 组的领导者节点中的命令组件（4、10）。事件（4、5、10、11）在各个 Raft 组内生成并传播。每个分区领导者节点的事件组件将最新状态实时推送到反向代理（6、12）。反向代理收到各分区的响应（7、13）。协调者使用一张“阶段状态表”（14）。编号 1 至 15 标示组件和数据流。虚线表示异步通信，实线表示同步通信。系统采用先写后读模式：写入发生在 Raft 组内，成功复制后再从数据库（以圆柱体表示）读取。](https://bytebytego.com/images/courses/system-design-interview/digital-wallet/figure-29-final-design-in-a-numbered-sequence-RLSHN3GF.svg)

## 第 4 步：总结

本章设计了一个每秒能够处理超过 100 万条支付命令的钱包服务。经过粗略估算，我们得出结论：需要几千个节点才能支撑这样的负载。

在第一个设计中，我们提出了使用 Redis 等内存键值存储的方案。这种设计的问题在于，数据不具备持久性。

在第二个设计中，我们将内存缓存替换为事务型数据库。为了支持多个节点，提出了两阶段提交、TC/C 和 Saga 事务等不同事务协议。基于事务的方案的主要问题是，不容易进行数据审计。

接下来介绍了事件溯源。我们首先使用外部数据库和队列实现事件溯源，但性能不佳。通过将命令、事件和状态存储在本地节点上，我们提高了性能。

单个节点意味着单点故障。为了提高系统可靠性，我们使用 Raft 共识算法，将事件列表复制到多个节点。

最后一项改进是采用事件溯源的 CQRS 特性。我们添加反向代理，让异步的事件溯源框架对外部用户呈现为同步框架，并使用 TC/C 或 Saga 协议协调跨多个节点组的命令执行。
