# 25 类似 S3 的对象存储

本章将设计一个类似 Amazon Simple Storage Service（S3）的对象存储服务。S3 是 Amazon Web Services（AWS）提供的一项服务，通过基于 RESTful API 的接口提供对象存储。下面是 AWS S3 的一些发展情况：

-   于 2006 年 6 月推出。
    
-   2010 年，S3 增加了版本控制、存储桶策略和分段上传支持。
    
-   2011 年，S3 增加了服务端加密、批量对象删除和对象过期功能。
    
-   Amazon 报告称，截至 2013 年，S3 存储的对象已达 2 万亿个。
    
-   2014 年和 2015 年陆续引入了生命周期策略、事件通知和跨区域复制支持。
    
-   Amazon 报告称，截至 2021 年，S3 存储的对象已超过 100 万亿个。
    

在深入了解对象存储之前，我们先回顾一下存储系统的基础知识，并明确一些术语。

## 存储系统基础

从总体上看，存储系统可以分为三大类：

-   块存储
    
-   文件存储
    
-   对象存储
    

**块存储**

块存储最早出现于 20 世纪 60 年代。通过物理方式连接到服务器的常见存储设备，例如机械硬盘（HDD）和固态硬盘（SSD），都属于块存储。

块存储以卷的形式向服务器呈现原始数据块。这是最灵活、用途最广泛的存储形式。服务器可以将原始数据块格式化为文件系统，也可以将这些数据块的控制权交给应用程序。一些应用程序，例如数据库或虚拟机引擎，会直接管理这些数据块，以尽可能榨取每一分性能。

块存储并不局限于物理直连的存储。它也可以通过高速网络，或光纤通道（Fibre Channel，FC）\[1\]、iSCSI \[2\] 等行业标准连接协议接入服务器。从概念上说，通过网络连接的块存储仍然呈现原始数据块。对服务器而言，它的工作方式与物理直连的块存储相同。

**文件存储**

文件存储构建在块存储之上，通过更高层次的抽象简化文件和目录的处理。数据以文件形式存储在层次化的目录结构中。文件存储是最常见的通用存储方案。借助 SMB/CIFS \[3\]、NFS \[4\] 等常见的文件级网络协议，大量服务器可以访问同一套文件存储。访问文件存储的服务器无须处理数据块管理、卷格式化等复杂问题。文件存储简单易用，非常适合在组织内部共享大量文件和文件夹。

**对象存储**

对象存储出现得较晚。它明确选择牺牲性能，以换取高持久性、超大规模和低成本。它主要面向相对“冷”的数据，常用于归档和备份。对象存储采用扁平结构，将所有数据存储为对象，没有层次化的目录结构。数据通常通过 RESTful API 访问。与其他存储类型相比，它的速度相对较慢。大多数公有云服务提供商都有对象存储产品，例如 AWS S3、Google 对象存储和 Azure Blob 存储。

### 术语

要设计类似 S3 的对象存储，我们首先需要理解对象存储的一些核心概念。本节将概述对象存储相关的术语。

**存储桶（Bucket）**。对象的逻辑容器。存储桶名称在全局范围内唯一。要将数据上传到 S3，必须先创建存储桶。

**对象（Object）**。对象是存放在存储桶中的一份独立数据，由对象数据（也称为负载）和元数据组成。对象数据可以是任意需要存储的字节序列。元数据则是一组描述对象的名称—值对。

**版本控制（Versioning）**。在同一个存储桶中保留某个对象多个版本的功能，在存储桶级别启用。借助这一功能，用户可以恢复意外删除或覆盖的对象。

**统一资源标识符（Uniform Resource Identifier，URI）**。对象存储提供 RESTful API，用于访问存储桶和对象等资源。每个资源都通过其 URI 唯一标识。

**服务等级协议（Service-level agreement，SLA）**。服务等级协议是服务提供商与客户之间的契约。例如，Amazon S3 Standard-Infrequent Access 存储类别提供以下 SLA \[7\]：

-   设计目标是在多个可用区之间提供 99.999999999% 的对象持久性。
    
-   即使整个可用区被毁，数据仍然能够得到保护。
    
-   设计目标为 99.9% 的可用性。

### 粗略估算

对象存储的瓶颈很可能出现在磁盘容量或每秒磁盘 I/O 操作次数（IOPS）上。下面来看一看。

-   磁盘容量。假设对象大小的分布如下：
    
    -   20% 的对象是小对象（小于 1MB）。
        
    -   60% 的对象是中等大小的对象（1MB ~ 64MB）。
        
    -   20% 的对象是大对象（大于 64MB）。
    
-   IOPS。假设一块硬盘（SATA 接口、7200 rpm）每秒能够进行 100~150 次随机寻道（100-150 IOPS）。
    

基于这些假设，可以估算系统能够持久存储的对象总数。为简化计算，取各类对象大小的中位数：小对象为 0.5MB，中等对象为 32MB，大对象为 200MB。当存储空间使用率为 40% 时，可得：

-   100 PB = 100\*1000\*1000\*1000 MB = 10^11 MB
    
-   10^11\*0.4/( 0.2\*0.5MB + 0.6 \*32MB + 0.2\*200MB) = 0.68 billion objects.
    
-   假设每个对象的元数据大小约为 1KB，那么存储所有元数据信息需要 0.68 TB 空间。
    

即使后续未必会用到这些数字，对系统规模和约束有一个大致认识也是有益的。

## 第 2 步：提出总体设计并达成共识

在开始设计之前，先来了解对象存储的几个有趣特性，因为它们可能会影响设计。

**对象不可变性**。对象存储与另外两类存储系统的主要区别之一是，其中存储的对象不可变。可以删除对象，也可以用新版本完整替换对象，但不能进行增量修改。

**键值存储**。可以使用对象 URI 获取对象数据（代码清单 1）。对象 URI 是键，对象数据是值。

```
Request:
GET /bucket1/object1.txt HTTP/1.1

Response:
HTTP/1.1 200 OK
Content-Length: 4567

[4567 bytes of object data]
```

代码清单 1 使用对象 URI 获取对象数据

**一次写入，多次读取**。对象数据的访问模式是一次写入、多次读取。根据 LinkedIn 的研究，95% 的请求是读操作 \[9\]。

**同时支持小对象和大对象**。对象大小可能各不相同，我们需要同时支持这两类对象。

对象存储的设计思想与 UNIX 文件系统十分相似。在 UNIX 中，将文件保存到本地文件系统时，文件名和文件数据不会存放在一起。文件名存储在称为“inode”的数据结构中 \[10\]，文件数据则存储在磁盘的不同位置。inode 包含一组文件块指针，指向文件数据所在的磁盘位置。访问本地文件时，首先读取 inode 中的元数据，再沿着文件块指针找到实际磁盘位置，读取文件数据。

对象存储的工作方式与此类似。inode 对应元数据存储，保存所有对象的元数据；硬盘对应数据存储，保存对象数据。在 UNIX 文件系统中，inode 使用文件块指针记录数据在硬盘上的位置。在对象存储中，元数据存储通过对象 ID 发起网络请求，从数据存储中查找对应的对象数据。图 2 展示了 UNIX 文件系统和对象存储。

图 4 总体设计

下面逐一介绍这些组件。

**负载均衡器**。将 RESTful API 请求分发到多台 API 服务器。

**API 服务**。协调对身份和访问管理服务、元数据服务及数据存储的远程过程调用。该服务无状态，因此可以水平扩展。

**身份和访问管理（IAM）**。集中处理身份验证、授权和访问控制。身份验证确认你是谁，授权则根据你的身份确认你可以执行哪些操作。

**数据存储**。存储和获取实际数据。所有与数据相关的操作均基于对象 ID（UUID）执行。

**元数据存储**。保存对象的元数据。

请注意，元数据存储和数据存储只是逻辑组件，可以采用不同方式实现。例如，Ceph 的 Rados Gateway \[11\] 没有独立的元数据存储。包括对象存储桶在内的所有内容，都会以一个或多个 Rados 对象的形式持久化。

-   上传对象。
    
-   下载对象。
    
-   对象版本控制，以及列出存储桶中的对象。这些内容将在“深入设计”部分介绍。

对象必须存放在存储桶中。在这个例子中，我们先创建名为“bucket-to-share”的存储桶，再向其中上传名为“script.txt”的文件。图 5 通过 7 个步骤解释了这一流程。

1.  客户端发送 HTTP PUT 请求，创建名为“bucket-to-share”的存储桶。请求被转发到 API 服务。
    
2.  API 服务调用 IAM，确保用户已获授权并具有 WRITE 权限。
    
3.  API 服务调用元数据存储，在元数据数据库中创建一条包含存储桶信息的记录。记录创建完成后，向客户端返回成功消息。
    
4.  存储桶创建完成后，客户端发送 HTTP PUT 请求，创建名为“script.txt”的对象。
    
5.  API 服务验证用户身份，确保用户对该存储桶具有 WRITE 权限。
    
6.  验证成功后，API 服务将 HTTP PUT 负载中的对象数据发送给数据存储。数据存储将负载作为对象持久化，并返回对象的 UUID。
    
7.  API 服务调用元数据存储，在元数据数据库中创建一条新记录，其中包含 object\_id（UUID）、bucket\_id（对象所属的存储桶）、object\_name 等重要元数据。表 2 展示了一条示例记录。

如前所述，数据存储不保存对象名称，只支持通过 object\_id（UUID）操作对象。因此，下载对象时，首先需要将对象名映射到 UUID。下载对象的流程如下：

1.  客户端向负载均衡器发送 HTTP GET 请求：GET /bucket-to-share/script.txt
    
2.  API 服务查询 IAM，确认用户具有该存储桶的 READ 访问权限。
    
3.  验证通过后，API 服务从元数据存储中获取相应对象的 UUID。
    
4.  随后，API 服务根据 UUID 从数据存储中获取对象数据。
    
5.  API 服务在 HTTP GET 响应中将对象数据返回给客户端。

**数据路由服务**

数据路由服务提供 RESTful 或 gRPC \[12\] API，用于访问数据节点集群。它是无状态服务，可以通过增加服务器来扩展。该服务承担以下职责：

-   查询放置服务，找到最适合存储数据的数据节点。
    
-   从数据节点读取数据，并返回给 API 服务。
    
-   向数据节点写入数据。
    

**放置服务**

放置服务决定应选择哪些数据节点（主节点及副本节点）来存储对象。它维护一份虚拟集群映射，描述集群的物理拓扑。虚拟集群映射包含每个数据节点的位置信息，放置服务利用这些信息确保副本在物理上相互隔离。这种隔离是实现高持久性的关键，详见后面的“持久性”一节。图 9 展示了虚拟集群映射的一个示例。

![图中展示了分层的系统架构。最上层是“Root”节点，向下连接“Default”节点。“Default”再分出两条分支，连接代表两个数据中心的“DC-1”和“DC-2”。每个数据中心进一步连接多个“Host”节点：DC-1 下有 Host-1 和 Host-2，DC-2 下有 Host-3 和 Host-4。每个 Host 节点再连接多个“Partition”节点，代表该主机上的数据分区。连线表示父子关系，体现上层节点管理或包含下层节点的层次结构。具体而言，“Root”是最顶层父节点，下面依次是“Default”、数据中心、主机，最后是分区。主机和分区的编号暗示了各层内部的顺序或逻辑排列。图中没有 URL 或参数。](https://bytebytego.com/images/courses/system-design-interview/s3-like-object-storage/figure-9-virtual-cluster-map-ESBSZKSE.svg)

图 9 虚拟集群映射

放置服务通过心跳持续监控所有数据节点。如果某个数据节点在一个可配置的 15 秒宽限期内没有发送心跳，放置服务就会在虚拟集群映射中将该节点标记为“宕机”。

这一服务至关重要，因此建议使用 Paxos \[13\] 或 Raft \[14\] 共识协议，构建由 5 个或 7 个放置服务节点组成的集群。共识协议能够保证，只要半数以上的节点健康，整个服务就能继续运行。例如，包含 7 个节点的放置服务集群可以容忍 3 个节点故障。如需进一步了解共识协议，请参阅参考资料 \[13\] \[14\]。

**数据节点**

数据节点存储实际的对象数据。它通过将数据复制到多个数据节点来保证可靠性和持久性，这些节点也称为一个复制组。

每个数据节点上都运行着一个数据服务守护进程。该守护进程持续向放置服务发送心跳。心跳消息包含以下关键信息：

-   该数据节点管理多少块磁盘（HDD 或 SSD）？
    
-   每块磁盘上存储了多少数据？
    

放置服务首次接收到某个数据节点的心跳时，会为该节点分配 ID，将其加入虚拟集群映射，并返回以下信息：

-   数据节点的唯一 ID
    
-   虚拟集群映射
    
-   应将数据复制到哪里

接下来看看数据如何在数据节点中持久化。

1.  API 服务将对象数据转发给数据存储。
    
2.  数据路由服务为对象生成一个 UUID，并查询放置服务，确定存储该对象的数据节点。放置服务检查虚拟集群映射，返回主数据节点。
    
3.  数据路由服务将数据及其 UUID 直接发送给主数据节点。
    
4.  主数据节点在本地保存数据，并将其复制到两个从数据节点。数据成功复制到所有从节点后，主节点向数据路由服务返回响应。
    
5.  对象的 UUID（ObjId）返回给 API 服务。
    

在第 2 步中，放置服务以对象的 UUID 为输入，返回对象对应的复制组。它如何实现这一点？需要记住，这一查找必须具有确定性，并且在增加或移除复制组后仍能正常工作。一致性哈希是这类查找函数的常见实现方式，更多信息参见 \[15\]。

在第 4 步中，主数据节点将数据复制到所有从节点后才返回响应。这使所有数据节点之间的数据保持强一致性，但也带来了延迟代价，因为必须等待最慢的副本完成。图 11 展示了一致性与延迟之间的权衡。

#### 数据的组织方式

下面看看每个数据节点如何管理数据。一个简单的方案是将每个对象存储为独立文件。这种方法可以工作，但小文件数量很多时，性能就会下降。文件系统中存在过多小文件会带来两个问题。首先，它会浪费大量数据块。文件系统以离散的磁盘块存储文件，各磁盘块大小相同，并在卷初始化时确定。典型的块大小约为 4 KB。即使文件小于 4 KB，也会占用整个磁盘块。如果文件系统保存了大量小文件，就会浪费大量磁盘块，因为每个块中只有一小部分空间存放了小文件。

其次，小文件过多可能耗尽系统的 inode。文件系统将文件位置及其他信息保存在称为 inode 的特殊数据块中。对大多数文件系统来说，inode 数量在磁盘初始化时就已固定。数百万个小文件可能消耗掉全部 inode。此外，即使积极缓存文件系统元数据，操作系统也不擅长处理大量 inode。因此，实际中将小对象各自保存为独立文件的效果并不好。

为解决这些问题，可以将许多小对象合并到一个更大的文件中。其概念类似于预写日志（write-ahead log，WAL）。保存对象时，将其追加到现有的读写文件中。当读写文件达到容量阈值（通常设置为几个 GB）后，将其标记为只读，并创建新的读写文件来接收新对象。文件一旦被标记为只读，就只能处理读请求。图 12 解释了这一过程。

我们考虑了两种保存映射的方案：RocksDB \[16\] 这类基于文件的键值存储，以及关系型数据库。RocksDB 基于 SSTable \[17\]，写入速度快，但读取较慢。关系型数据库通常使用基于 B+ 树 \[18\] 的存储引擎，读取速度快，但写入较慢。如前所述，这里的数据访问模式是一次写入、多次读取。关系型数据库提供更好的读取性能，因此比 RocksDB 更合适。

#### 持久性

对数据存储系统而言，数据可靠性极其重要。如何构建一个提供 6 个 9 持久性的存储系统？必须仔细考虑每一种故障情况，并妥善复制数据。

##### 硬件故障与故障域

无论使用哪种介质，硬盘故障都不可避免。某些存储介质的持久性可能优于其他介质，但无法依靠一块硬盘实现持久性目标。一种经过验证的提高持久性的方法是将数据复制到多块硬盘，使单块磁盘故障不会影响数据整体的可用性。在本设计中，我们将数据复制三份。

假设机械硬盘的年故障率为 0.81% \[20\]，这一数字非常依赖型号和厂商。保留 3 份数据副本，可靠性便为 1-(0.0081)^3=~0.999999。这只是非常粗略的估算，更精细的计算请参阅 \[20\]。

要完整评估持久性，还必须考虑不同故障域的影响。故障域是环境中的一个物理或逻辑范围，当关键服务出现问题时，这一范围会受到不利影响。在现代数据中心，服务器通常放在机架 \[21\] 中，机架再按排、楼层或房间分组。由于同一机架共享网络交换机和电源，该机架内的所有服务器都处于同一个机架级故障域。现代服务器内部共享主板、处理器、电源、HDD 等组件，因此服务器内的组件处于同一个节点级故障域。

下面是大规模故障域隔离的一个典型例子。数据中心通常将彼此不共享基础设施的部分划分为不同的可用区（Availability Zone，AZ）。我们将数据复制到不同的可用区，以尽量减小故障影响（图 14）。注意，故障域层级的选择并不会直接提高数据持久性，但在大范围停电、冷却系统故障、自然灾害等极端情况下，可以带来更好的可靠性。

##### 纠删码

保留三份完整数据副本，大致可以提供 6 个 9 的数据持久性。还有其他办法进一步提高持久性吗？有，纠删码就是一种选择。纠删码 \[22\] 采用不同方式保障数据持久性：将数据切分成更小的数据块，放到不同服务器上，并生成用于冗余的校验块。发生故障时，可以通过数据块和校验块重建数据。图 15 展示了一个具体例子：4 + 2 纠删码。

1.  将数据切分为大小相等的四个数据块 d1、d2、d3 和 d4。

3.  节点崩溃导致数据 d3 和 d4 丢失。
    
4.  利用 d1、d2、p1、p2 的已知值，通过数学公式重建丢失的数据 d3 和 d4。

纠删码需要多少额外空间？每两个数据块需要一个校验块，因此存储开销为 50%（图 17）。相比之下，三副本复制的存储开销为 200%（图 17）。

#### 正确性校验

纠删码能以相近的存储成本提高数据持久性。接下来解决另一个棘手的问题：数据损坏。

如果磁盘完全失效，并且能够检测到这一故障，就可以将其视为数据节点故障。在这种情况下，可以利用纠删码重建数据。然而，在大规模系统中，内存中的数据损坏也经常发生。

使用（8+4）纠删码和校验和校验时，读取数据的过程如下：

1.  获取对象数据及其校验和。
    
2.  根据接收到的数据计算校验和。
    
    (a). 如果两个校验和一致，数据就没有错误。
    
    (b). 如果校验和不同，说明数据已损坏。此时尝试从其他故障域读取数据来恢复。

### 元数据的数据模型

本节先讨论数据库模式，再深入研究如何扩展数据库。

##### 模式

数据库模式需要支持以下 3 种查询：

查询 1：根据对象名查找对象 ID。

查询 2：根据对象名插入和删除对象。

查询 3：列出存储桶中具有相同前缀的对象。

##### 扩展 bucket 表

通常会限制每个用户可创建的存储桶数量，因此 bucket 表不会太大。假设有 100 万客户，每位客户拥有 10 个存储桶，每条记录占用 1 KB，则需要 10 GB（100 万 \* 10 \* 1KB）的存储空间。整张表可以轻松容纳在现代数据库服务器中。不过，一台数据库服务器的 CPU 或网络带宽可能不足以处理全部读请求。此时，可以将读取负载分散到多个数据库副本上。

##### 扩展 object 表

object 表保存对象元数据。在本设计的规模下，数据集很可能无法容纳在单个数据库实例中。可以通过分片来扩展 object 表。

一种选择是按 _bucket\_id_ 分片，将同一个存储桶中的所有对象存储在同一个分片中。这种方式不可行，因为一个存储桶可能包含数十亿个对象，容易形成热点分片。

另一种选择是按 _object\_id_ 分片。这种分片方案可以均匀分配负载，但无法高效执行查询 1 和查询 2，因为它们都基于 URI。

我们选择按 _bucket\_name_ 和 _object\_name_ 的组合分片，因为大多数元数据操作都基于对象 URI，例如按 URI 查找对象 ID，或通过 URI 上传对象。为了均匀分布数据，可以将（_bucket\_name_、_object\_name)_ 的哈希值用作分片键。

采用这种分片方案，前两种查询很容易支持，但最后一种查询的实现方式就不那么明显了。下面来看一看。

### 列出存储桶中的对象

对象存储以扁平结构组织文件，而不是采用文件系统中的层次结构。可以使用 _s3://bucket-name/object-name._ 格式的路径访问对象。例如，_s3://mybucket/abc/d/e/f/file.txt_ 包含以下部分：

-   存储桶名称：mybucket
    
-   对象名：abc/d/e/f/file.txt
    

为方便用户组织存储桶中的对象，S3 引入了“前缀”的概念。前缀是对象名开头的一段字符串。S3 利用前缀，以类似目录的方式组织数据。不过，前缀并不是目录。按前缀列出存储桶内容时，只会返回对象名以该前缀开头的对象。

在上面路径为 _s3://mybucket/abc/d/e/f/file.txt_ 的例子中，前缀是 _abc/d/e/f/._

AWS S3 的列举命令有 3 种典型用法：

1.  列出某个用户拥有的所有存储桶。命令如下：
    
    ```
    aws s3 list-buckets
    ```
    
2.  列出存储桶中与指定前缀处于同一层级的所有对象。命令如下：
    
    ```
    aws s3 ls s3://mybucket/abc/
    ```
    
    在这种模式下，指定前缀之后的名称中如果还有斜杠，相应对象就会被归并到一个公共前缀下。例如，存储桶中有以下对象：
    
    ```
    CA/cities/losangeles.txt
    CA/cities/sanfrancisco.txt
    NY/cities/ny.txt
    federal.txt
    ```
    
    使用“/”前缀列出存储桶内容时，会返回以下结果，CA/ 和 NY/ 下的所有内容都被归并到各自的前缀下：
    
    CA/ NY/ federal.txt
    
3.  递归列出存储桶中具有相同前缀的所有对象。命令如下：
    
    ```
    aws s3 ls s3://mybucket/abc/ --recursive
    ```
    
    仍以上面的对象为例，使用 `CA/` 前缀列出存储桶内容时，会返回以下结果：
    
    ```
    CA/cities/losangeles.txt
    CA/cities/sanfrancisco.txt
    ```
    

#### 单个数据库

先来看看仅使用单个数据库时，如何支持列举命令。要列出某个用户拥有的所有存储桶，可以执行以下查询：

```
SELECT * FROM bucket WHERE owner_id={id}
```

要列出存储桶中具有相同前缀的所有对象，可以执行如下查询。

```
SELECT * FROM object WHERE bucket_id = "123" AND object_name LIKE `abc/%`
```

在这个例子中，我们查找 bucket\_id 等于“123”、且具有“abc/”前缀的所有对象。对于指定前缀之后的名称中还有斜杠的对象，由应用代码进行归并，如前面用法 2 所述。

同一个查询也能支持前面用法 3 中的递归列举模式。应用代码直接列出具有相同前缀的所有对象，不执行归并。

#### 分布式数据库

元数据表分片后，列举功能就难以实现，因为无法确定哪些分片包含目标数据。最直接的方案是在所有分片上执行搜索查询，再汇总结果。具体可以这样做：

1.  元数据服务在每个分片上执行以下查询：
    
    ```
    SELECT * FROM object WHERE bucket_id = “123” AND object_name LIKE `a/b/%`
    ```
    
2.  元数据服务汇总各分片返回的所有对象，并将结果返回给调用方。
    

这一方案可以工作，但实现分页有些复杂。在解释原因之前，先回顾一下单个数据库这一简单场景下的分页机制。要分页返回对象列表，每页包含 10 个对象，最初的 SELECT 查询如下：

```
SELECT * FROM object WHERE
bucket_id = "123" AND object_name LIKE `a/b/%`
ORDER BY object_name OFFSET 0 LIMIT 10
```

OFFSET 和 LIMIT 将结果限制为前 10 个对象。下一次调用时，用户在请求中向服务器提供提示，使服务器知道应使用 OFFSET 为 10 的查询获取第二页。这个提示通常通过游标实现，服务器在每页响应中将游标返回给客户端。偏移量信息编码在游标中。客户端请求下一页时携带该游标，服务器解码后，利用其中的偏移量构造下一页的查询。沿用前面的例子，第二页查询如下：

```
SELECT * FROM metadata
WHERE bucket_id = "123" AND object_name LIKE `a/b/%`
ORDER BY object_name OFFSET 10 LIMIT 10
```

客户端与服务器不断重复这一请求过程，直到服务器返回一个特殊游标，表示整个列表已经结束。

现在来看看，为什么分片数据库的分页支持比较复杂。对象分布在不同分片上，各分片返回的结果数量很可能不同。有的分片会返回满页的 10 个对象，有的只能返回部分对象，甚至没有对象。应用代码接收所有分片的结果，汇总并排序，在这个例子中仅返回一页 10 个对象。当前这一轮未返回的对象，下一轮仍然需要考虑。这意味着每个分片的偏移量很可能不同。服务器必须跟踪所有分片的偏移量，并将它们与游标关联。如果有数百个分片，就需要跟踪数百个偏移量。

有一种方案可以解决这个问题，但需要做一些权衡。对象存储针对超大规模和高持久性进行了优化，对象列举性能通常不是首要目标。事实上，所有商业对象存储都支持对象列举，但性能并非最优。利用这一点，可以将列举所需的数据反规范化到一张单独的表中，并按存储桶 ID 分片。该表仅用于列出对象。这样，即使存储桶包含数十亿个对象，也能提供可接受的性能。列举查询因此被限制在单个数据库中，实现大为简化。

### 对象版本控制

版本控制是一项在存储桶中保留对象多个版本的功能。启用版本控制后，可以恢复意外删除或覆盖的对象。例如，修改某个文档后，以相同名称保存到同一个存储桶中。未启用版本控制时，元数据存储中的旧文档元数据会被新版本替换。旧文档被标记为已删除，其存储空间随后会由垃圾回收器回收。启用版本控制后，对象存储会在元数据存储中保留文档的所有历史版本，对象存储中的旧文档版本也不会被标记为已删除。

图 22 解释了如何上传启用版本控制的对象。要实现这一点，首先需要为存储桶启用版本控制。

![图中展示了对象存储的系统架构。用户发起 HTTP PUT 对象请求（①），先由负载均衡器处理，并将请求分发到 API 服务。API 服务与身份服务交互（②），对用户进行身份验证和授权。验证成功后，API 服务检查对象是否存在、是否启用版本控制（④）。随后，对象被上传到存储服务（③），数据复制到一个主存储节点和两个从存储节点，组成数据存储。与此同时，API 服务创建对象元数据（⑤），将其保存到元数据服务，后者再将数据持久化到元数据数据库。元数据服务负责管理对象元数据，存储服务则负责实际对象存储和复制，以实现高可用性。整个系统旨在提供稳健的对象存储，具备身份验证、版本控制和数据冗余等功能。](https://bytebytego.com/images/courses/system-design-interview/s3-like-object-storage/figure-22-object-versioning-RHMOOBIT.svg)

### 优化大文件上传

在粗略估算中，我们估计 20% 的对象是大对象，其中一些可能超过几个 GB。虽然可以直接上传这样大的对象文件，但可能耗时很长。如果上传过程中网络连接中断，就必须重新开始。更好的方案是将大对象切分成较小的分段，分别上传。所有分段上传完成后，对象存储再将其重新组装成完整对象。这一过程称为分段上传。

图 25 展示了分段上传的工作方式：

![图中以时序图展示了分段文件上传过程。用户以小人图标表示，与矩形框表示的“数据存储”交互。过程分为初始化、分段上传和完成三个阶段。初始化阶段中，用户发起分段上传（步骤①），数据存储返回唯一的 `uploadID`（步骤②）。分段上传阶段中，用户将文件的各个分段（分段 1、分段 2……分段 8）连同 `uploadID` 一起发送给数据存储。每个分段上传后（步骤③），数据存储返回该分段的唯一标识符 `ETag`（步骤④）。最后，在完成阶段，用户向数据存储发送分段上传完成消息（步骤⑤），其中包含 `uploadID` 以及此前获取的所有 `ETags`（ETag 1、ETag 2……ETag 8）。完成后，数据存储向用户发送“成功”消息（步骤⑥）。虚线划分各个阶段，带编号的圆圈表示步骤顺序，箭头表示用户与数据存储之间的信息流方向。](https://bytebytego.com/images/courses/system-design-interview/s3-like-object-storage/figure-25-multipart-upload-KDHGYB2U.svg)

图 25 分段上传

1.  客户端调用对象存储，发起分段上传。
    
2.  数据存储返回 uploadID，用于唯一标识此次上传。
    
3.  客户端将大文件切分成小对象，并开始上传。假设文件大小为 1.6GB，客户端将其切分为 8 段，每段大小为 200 MB。客户端将第一段与第 2 步收到的 uploadID 一同上传到数据存储。
    
4.  一个分段上传完成后，数据存储返回一个 ETag，它本质上是该分段的 md5 校验和，用于校验分段上传。
    
5.  所有分段上传完成后，客户端发送完成分段上传的请求，其中包含 uploadID、分段编号和 ETag。
    
6.  数据存储根据分段编号，将各分段重新组装成对象。由于对象非常大，这一过程可能需要几分钟。组装完成后，向客户端返回成功消息。
    

这种方案有一个潜在问题：对象重新组装完成后，原来的分段就不再有用。为解决这一问题，可以引入垃圾回收服务，负责释放不再需要的分段所占用的空间。

### 垃圾回收

垃圾回收是自动回收不再使用的存储空间的过程。以下几种情况可能产生垃圾数据：

-   延迟删除对象。执行删除时，只将对象标记为已删除，而不实际删除。
    
-   孤立数据。例如，只上传了一半的数据，或已放弃的分段上传。
    
-   损坏的数据。未通过校验和校验的数据。
    

垃圾回收器不会立即从数据存储中移除对象，而是通过压实机制定期清理已删除对象。

垃圾回收器还负责回收副本中未使用的空间。采用复制时，需要从主节点和备份节点上都删除对象。采用纠删码时，若使用（8+4）配置，则需要从全部 12 个节点上删除对象。

图 26 展示了压实过程的一个例子。

1.  垃圾回收器将“/data/b”中的对象复制到名为“/data/d”的新文件。注意，它会跳过“Object 2”和“Object 5”，因为这两个对象的删除标记均已设为 true。
    
2.  所有对象复制完成后，垃圾回收器更新 object\_mapping 表。例如，“Object 3”的 obj\_id 和 object\_size 字段保持不变，但 file\_name 和 start\_offset 会更新为新位置。为保证数据一致性，最好将 file\_name 和 start\_offset 的更新操作放在一个数据库事务中。
    

![图中展示了数据压实过程，包括“压实前”和“压实后”两种状态，每种状态都有一个只读文件和一张 `object_mapping` 表。表中包含 `obj_id`、`file_name`、`offset` 和 `obj_size` 列。压实前，只读文件依次包含对象 2、对象 3 和对象 5。`object_mapping` 表显示，对象 3 的 `obj_id` 为“object 3”，`file_name` 为“/data/b”，位于文件偏移量 `0x232B3` 处。压实后，对象 2 和对象 5 被移除，对象 3 移到新位置。`object_mapping` 表随之更新：对象 3 的 `file_name` 变为“/data/d”，偏移量变为 `0x10013`。标为“1”的虚线箭头表示对象 3 从旧位置移动到压实后的新位置。标为“2”的弯曲箭头表示 `object_mapping` 表的更新过程，展示对象 3 文件名和偏移量的变化。“X”标记突出显示压实过程中被移除的对象。](https://bytebytego.com/images/courses/system-design-interview/s3-like-object-storage/figure-26-compaction-GGRMBRFH.svg)

图 26 压实

从图 26 可以看出，压实后的新文件比旧文件小。为避免产生大量小文件，垃圾回收器通常会等到有大量只读文件需要压实时才执行操作，将多个只读文件中的对象追加到少数几个较大的新文件中。
