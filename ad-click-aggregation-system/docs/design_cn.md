# 广告点击事件聚合：参考设计

## 进程与持久化边界

可运行实验环境包含六个独立进程：一个入口/原始日志 HTTP 服务、四个分区聚合 HTTP 服务和一个查询/归并 HTTP 服务。查询服务与工作进程从不打开入口数据库。每个工作进程拥有各自独立的 SQLite 数据库，并通过 HTTP 拉取分页数据。不使用内存队列或共享 Python 对象来替代传输。

入口服务将规范化后的不可变事件与分区序列头写入同一个 SQLite WAL 事务，并设置 `synchronous=FULL`。`event_id` 是全局唯一键。相同 ID 携带相同规范化负载时返回其原始位置；携带不同负载时返回 409 并回滚整个批次。ID 与原始数据被持续保留且不会自动过期，因此去重能力在所有支持的重放场景下均有效。原始日志默认上限为一百万个唯一事件；超过后新写入返回 429，而完全相同的重复事件仍可成功写入。一个批次包含 1–200 个事件，一个日志分页最多包含 200 个事件。

这里刻意采用单一持久化日志所有者。它是一个传输层参考实现，不是复制的 Kafka 替代品。它不复用第 20 章的线上协议：这个小型源协议暴露的是不可变、可独立重放的分区序列与血缘（lineage）。用复制队列替换该源时，必须保留这些不变量以及本地原子检查点契约。本文不声称具备复制 broker 或协调者故障转移能力。

## 事件身份与热点分区

事件必须恰好包含 `event_id`、`ad_id`、`click_timestamp`、`user_id`、`ip`、`country` 六个字段。时间戳为整数 epoch 秒，最多比入口接收时间超前 30 秒。国家码规范化为两位大写字母；IP 采用 Python 的 IP 地址规范化处理。字符串维度限制在 128 个字符以内。未知字段与畸形数据会在追加之前导致整个批次失败。

`partition = first_64_bits(SHA256(canonical_JSON(event_id))) % partition_count`。以事件身份作为盐（salt）进行散列，使单个热点广告也能分散到各个工作进程。分区数量持久化在日志中，不能就地修改。工作进程持久化其被分配的分区；修改队列血缘会触发失败关闭（fail closed）。扩容需要将数据排空/重放到新日志并生成新的结果，然后显式修改部署配置；不存在自动的在线重新分配或再均衡。

## 恰好一次效果与恢复

传输层是至少一次（at least once）语义：工作进程根据其持久化的本地检查点请求下一页数据。工作进程在单个事务中完成血缘校验、偏移量与 SHA256 负载校验和验证、插入去重键、递增维度桶并推进检查点。提交前崩溃会同时回滚计数与检查点。提交后，下一次拉取从保存的位置继续；重放旧位置是空操作（no-op）。每个工作进程内部的事件级去重还能在兼容源中保护后续位置出现的重复 ID。

不存在可能先于输出持久化的独立队列 ACK。遇到畸形/损坏/有缺口的源数据时，工作进程保留失败偏移量并暴露错误；不会静默跳过与计费相关的事件。重建使用新的显式命名数据库，并捕获一个有限的原始日志头部。CLI 输出路径被独占保留，避免覆盖已有结果。提升重建生成的结果代是运维操作，不会自动替换正在运行的存储。

JSONL 尾随器（tailer）在收到入口 ACK 后，将字节偏移量与已消费文件前缀的 SHA256 记入检查点。丢失 ACK 或本地检查点缺失时，稳定 ID 的重放是安全的。不完整的最后一行会等待换行符。前缀被篡改/截断时失败关闭；日志轮转需要新的检查点。尾随检查点只有一个所有者；不允许并发尾随器共享同一个检查点文件。历史时间戳始终可重放，因为摄取侧不存在事件时间的下限截断。

## 事件时间、watermark 与修正语义

桶使用 `floor(click_timestamp / 60) * 60`，所有查询使用分钟对齐的 `[from,to)` 区间。每个区间最多 1440 分钟。非分钟对齐的滑动窗口被有意拒绝。默认查询结束于当前分钟边界，因此覆盖最近一个完整分钟。

每个分区的 watermark 单调递增：记录一条数据后，它取以下三者的最大值：先前值、已见最大事件时间减去允许迟到时间、记录的入口接收时间减去允许迟到时间。空闲且已追上的工作进程还会按「墙钟时间减去迟到时间」推进它。默认允许迟到 120 秒。因此 watermark 假设各节点时钟大致同步；重启不会使 watermark 回退。对于桶结束时间已小于等于先前 watermark 的事件，会递增迟到修正计数器。

所有合法的迟到事件仍会被计入，包括超过允许迟到时间的事件。`closed` 表示请求的结束时间小于等于每个分区的 watermark；它不承诺结果不可变，也不承诺队列没有积压。迟到事件会递增该桶的修订号（revision）与分区检查点。响应携带检查点向量、当前滞后估计、watermark、`closed` 以及 `late_corrections_allowed=true`。迟到计数器是受空闲墙钟推进影响的运维观测值，不是离线重放得到的确定性计费结果。

## 过滤、精确 Top N 与一致性

一个桶行包含 `(minute, ad_id, user_id, ip, country, count, revision)`，带复合主键。二级索引按分钟覆盖广告、国家、用户与 IP。过滤条件是精确的 AND 组合；IPv6 的不同书写形式会规范化为相同值。系统不为每种过滤组合物化维度立方体（cube），但高基数维度仍可能产生接近每事件一行的数据。这是以存储换取对任意受支持维度交集的支持。

每个工作进程将其桶求和为**所有**匹配广告的总量，最多 10,000 个候选广告。查询进程并发抓取各分区，将每个广告跨分区求和，然后按计数降序、广告 ID 升序排序以确定并列次序。它还强制执行全局 10,000 候选上限，以及 1–1000 范围内的请求 Top N。预算超限返回 422，而不是近似/截断的答案。在使用盐化热点键时，本地 Top N 截断是错误的：四个分片上各自 `hot=6` 的广告全局以 24 获胜，即使每个分片的本地赢家是 9。真实的网络测试覆盖了这个反例。

计数与检查点来自每个工作进程的一个读事务。整体响应是这些快照组成的向量，而不是跨所有分区的原子快照。滞后（lag）比较使用在工作进程读取之前获取的源头部快照，如果某个工作进程推进超过了它，则下限取零。Lag=0 不是线性一致（linearizable）的新鲜度保证。工作进程缺失/出错、配置的分区缺失以及血缘不一致都返回 503。系统绝不会将部分 Top N 作为成功查询上报。

## 重放与独立对账

`rebuild` 将原始事件流输入同一个聚合实现，写入单独的数据库（Kappa 风格）。`reconcile` 在一个事务中独立读取每个工作进程的审计哈希与其检查点，然后仅对该位置之前的原始事件进行批量计数。它对排序后的完整维度行做哈希，而不仅仅是总点击数，因此能够检测出总量相等但分配错误的情形。各分区的审计快照时间可能不同，但每次比较都被其自身源位置精确界定。比较不会改写在线数据；发现不一致时 CLI 以退出码 1 上报。当前的批处理/审计实现将行加载进内存，属于管理用小规模工具，不是分布式十亿事件批处理引擎。

## 安全与运维限制

四个不同的 bearer 凭据分别隔离写、读、内部/原始数据与管理能力。凭据缺失或过短会阻止启动。原始日志与用户/IP 维度行仅对内部/管理角色可用；公开健康检查不包含机密。请求上限 1 MiB，HTTP 客户端响应上限 8 MiB。默认绑定 localhost。该服务器没有 TLS、租户 ACL、静态加密、反欺诈、自动化隐私保留或分布式限流；在部署到互联网之前，需要生产级网关以及隐私/数据生命周期设计。

工作进程状态暴露持久化位置、桶数量、watermark、修正计数、最近轮询时间与当前错误。入口服务暴露容量与分区头部。这些支持积压与对账监控；不声称接入任何第三方监控供应商。SQLite 与原始日志仍是单机故障域，HTTP 工作进程为静态配置，没有自动的工作进程/存储故障转移。测试覆盖保留的本地磁盘上的真实进程退出与重启，不包括主机/磁盘丢失或复制共识。原书的吞吐与可用性目标仍未验证。
