# 酒店预订参考设计

## 服务边界与存储

本实验室运行六个独立进程：HTTP 网关、两个酒店分片 HTTP 服务器、两个 saga（补偿）工作进程，以及一个持久化的**模拟**支付 HTTP 服务。网关和工作进程不直接打开分片数据库；所有生产路径的通信均经由 HTTP。每个分片拥有独立的 SQLite WAL 文件，支付模拟器另有一个。只有故障测试会从单独的子进程打开分片文件，以注入提交前进程退出或校验单元不变量。

路由规则为 `first_64_bits(SHA256(canonical_JSON(hotel_id))) % shard_count`。同一家酒店的目录、房型、日期库存、订单、夜间快照和支付 outbox（发件箱）在同一分片内共置。因此，多晚预订不需要跨分片分布式事务。分片 ID/数量在启动时持久化并校验，非所属分片写入将失败。网关配置在整个部署中必须保持一致；在线重新分片功能尚未实现。变更拓扑需要显式离线迁移，而非更改运行中的分片数量。

预订的是**房型**，而非具体物理房间号。酒店与房型删除采用软删除（active 标志），阻止新预订同时保留库存、订单和取消/退款访问权限。重新激活需通过显式管理 PUT 操作。每日日历行由管理员预填；缺失的日期会被拒绝而非推断补齐。本参考实现中没有两年期日历批量预填调度器。

## 库存与价格不变量

库存主键为 `(hotel, room_type, UTC_calendar_day)`，包含容量、超售百分比、价格美分、已保留数量和版本号。已保留数量包含待付款占用和已确认订单。SQL 约束为：

```sql
CHECK(reserved >= 0 AND reserved <= capacity + (capacity * overbook) / 100)
```

所有操作数均为整数，且输入将容量限制在 100000 以内，因此除法会向下取整额外允许量。9 间物理房、10% 超售时仍允许 9 份预订；10 间房允许 11 份；20 间房允许 22 份。超售百分比限制为 0–10。日历变更不能将容量/策略降到低于当前已占用数量以下：同一约束会拒绝并回滚整批管理操作。

`BEGIN IMMEDIATE` 事务锁定此 SQLite 分片的写入器，读取每一夜的当前价格，校验精确的预期总额，条件性递增每一夜的已保留数量，创建订单和夜间价格快照，并插入其支付 outbox 任务和 HELD 事件。任何一夜失败、行缺失、价格不匹配或崩溃都会导致整个操作回滚。条件更新在 SQL 中重复容量谓词；CHECK 约束作为最终防线，即使绕过应用层校验也能拦截。管理侧的价格变更会保留之前已保存的订单快照。

在 PostgreSQL 中，悲观行锁可按稳定顺序只锁定相关日期。乐观比较交换可使用版本字段配合冲突重试，但在热门酒店上会遭受重复重试。本参考实现刻意选择 SQLite 的写入器序列化 + 条件更新 + 约束组合；其版本字段是可观测元数据，而非实现的乐观锁算法。未声称有行级锁吞吐量或对比基准。分片将不同酒店的写入器分离，而单一热门酒店在同一分片内保持串行化。

报价和可用性读取是建议性的。用户以美分提供 `expected_total`（预期总额）；若与当前事务的单价 × 数量之和不匹配，则在任何库存变更之前返回 409。接受的总额和每晚价格在创建时冻结。税费/费用/汇率未纳入；仅支持 USD 货币。入住使用 `[checkin,checkout)` 日期范围，最多 30 晚、10 间房，限于未来 730 个 UTC 日历日。使用 UTC 是显式简化，不支持酒店本地时区。

## 幂等性与宾客授权

订单幂等作用域为 `(hotel, user, request_key)`，通过持久化 UNIQUE 约束实现。订单 ID 为 `hotel_id + '.' + first_128_bits(SHA256(canonical_JSON([user, request_key])))`；酒店 ID 仅允许 ASCII 字母/数字/下划线/连字符，以便直接路由。请求体指纹防止同一密钥更改日期、房间数量、预期价格或模拟支付方式。重复请求返回同一订单的当前状态，即使入住日期或价格已变更，也不会重新占用库存或再次扣款。校验在此之前进行，专门为此目的。身份和收据不会自动过期。

Bearer token（持有人令牌）映射到已配置的宾客身份；宾客 ID 绝不从预订请求体中接受。宾客只能读取/取消自己的订单，缺失或属于他人的 ID 都返回 404。历史查询按酒店范围，使用有界 100 条目的 ID 游标，不是跨分片全局宾客索引，也不是跨并发插入的快照。本参考实现中管理员管理所有酒店，可查看/取消订单；按酒店分配员工 ACL 是生产扩展。管理员使用实际配置的宾客凭据创建预订，而非隐式冒充宾客。

## 订单/支付状态机与补偿

订单状态包括 PENDING（待确认）、CONFIRMED（已确认）、CANCELLED（已取消）、EXPIRED（已过期）和 REJECTED（已拒绝）。独立的支付状态包括 NONE（无）、CHARGING（扣款中）、PAID（已付款）、REFUND_PENDING（退款中）、REFUNDED（已退款）和 DECLINED（已拒绝）。创建订单时会占用所有夜晚，但**不会**确认住宿。在占用过期前全额模拟支付成功使 PENDING → CONFIRMED/PAID。显式拒绝则拒绝并释放占用。支付超时/HTTP 错误绝不等于拒绝：结果未知，任务保持持久化以便重试。

取消是幂等的，使用订单的 `held`（已占用）标志原子性地恰好释放一次库存。已确认且已付款的订单入队全额退款；待确认订单保留任何之前已尝试的扣款任务，以便解析未知结果。如果订单已被取消或过期，首次扣款尝试会被跳过，避免不必要的初始扣款。对于之前已尝试过的操作，重试可能发现更早的扣款记录，或完成一个未到达支付服务商的操作；如果订单不再符合条件，任何成功都会立即入队补偿性退款。异步中间状态对宾客可见。

工作进程每轮最多清理 100 个过期 PENDING 订单，先释放其占用库存再认领下一个任务。过期在清理时生效，而非硬实时 TTL 保证：工作进程停机可能保守地降低可用性直到恢复。如果扣款在过期后才完成，结算在写事务内部重新校验系统时钟，释放库存并安排退款，而非确认订单。订单锁定使取消、过期和结算的竞争串行化。已确认的订单不会因支付占用而过期。本参考实现允许无罚金全额取消/退款；生产级取消政策不在范围内。

## 持久化任务、租约与支付模拟

扣款任务 ID 为 `charge:<order_id>`，退款任务 ID 为 `refund:<order_id>`。任务、订单状态变更和持久化事件与其对应的库存事务一起提交。认领任务时，在联系支付服务之前先提交尝试次数和随机租约令牌。工作进程崩溃或回调丢失会留下可回收的租约；结算同时校验令牌和持久化的预订/操作/金额，以隔离过期的工作进程。默认租约时长为两秒；幂等的支付服务商操作可容忍租约在慢速 HTTP 调用期间过期而产生的重叠请求。HTTP 工作在库存写事务之外执行。

模拟器在自己的 SQLite 事务中存储冻结的操作指纹和结果。相同操作返回其原始收据，附带尝试次数；同一 ID 下金额变更会失败。退款要求有匹配的已付款扣款记录，持久化退款操作确保退款只发生一次。唯一支持的支付方式是 `test-ok` 和 `test-decline`；没有卡、银行或真实支付 SDK。支付适配器接口明确了边界，但未实现或验证真实的支付服务商集成。

仅供测试使用的经认证的模拟器控制可在**提交支付结果之后**返回 503，或临时拒绝退款。前者模拟确认丢失，后者模拟退款服务中断。重试使用有界指数退避（当前指数上限下最多 25.6 秒），持久化错误记录，持续执行直到收据结算；财务上的不确定性绝不会被静默转为死信。分片回调失败会在租约或 outbox 延迟后重试。支付服务和分片重启时，操作/任务在本地磁盘上保留。持久化事件端点是轮询式日志；它不是交付保证的外部通知总线。任务状态暴露尝试次数和最近的错误，供运维人员关注。

## 缓存与运行限制

详情和可用性使用线程安全的有界 LRU（128 条目，1 秒 TTL）。键包含分片的持久化修订号。当独立工作进程进行库存变更时，会递增该修订号，从而无需共享内存即可使 HTTP 进程缓存的可用性失效。缓存仍需要一次廉价的修订号查询，可能与并发提交产生竞态；读取是建议性的，写入始终查询事务。订单/支付读取不走缓存。

所有服务默认绑定 localhost；请求 JSON 限制为 1 MiB，HTTP 客户端响应限制为 4 MiB。必须区分宾客/管理员/内部/支付四种凭据；原始内部 outbox/事件 API 和模拟器控制不可通过公共网关访问。没有 TLS、限流网关、卡处理、租户隔离、静态加密或自动化隐私/收据保留。配置和 `.runtime` 被忽略，但部署凭据仍需运维保护。

SQLite 分片、网关配置和模拟账本没有复制、共识或自动故障转移。测试覆盖磁盘持久化的进程崩溃，而非主机/磁盘丢失。工作进程可重启并恢复租约，但没有编排领导者选举。两分片实验室演示物理数据分离和路由，而非自动集群扩容或本书所述 5000 酒店容量。未提供搜索、真实房间分配、动态定价算法、真实支付或生产级可用性声明。
