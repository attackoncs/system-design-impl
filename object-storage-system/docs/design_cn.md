# 类 S3 对象存储参考设计

## 进程与权责划分

实验环境中运行着六个独立的 HTTP 进程：一个目录/API 协调器、两个元数据分片和三个数据节点。元数据与数据块的访问通过 HTTP 完成，没有用共享的 Python 对象来充当副本。目录（Catalog）拥有私有桶、多部分上传会话/分片和列举快照；元数据分片（Metadata shard）拥有版本/清单（manifest）、请求回执以及删除时间戳；各节点则拥有数据块文件和可废弃的物理索引。

数据放置策略为 `first_64_bits(SHA256(canonical_JSON([bucket_uuid,key]))) % shard_count`。同一个键的所有版本始终位于同一个元数据分片上。持久化的拓扑结构不允许在已有数据库上修改分片 ID 或分片数量。目前没有在线迁移、自动升主或元数据复制机制。

唯一的协调器通过进程锁对操作和维护任务进行串行化。这保护了发布、桶删除、分片暂存和垃圾回收（GC）不会互相竞争，同时也限制了吞吐量。不支持第二个活跃协调器或绕过协调器的直接写入。本地多个进程并不等同于独立的物理磁盘、主机或可用区。

## 版本与发布

私有桶名全局唯一。重新创建同名桶会获得新的 UUID。键为纯扁平名称，最长 512 字节（UTF-8），可以包含斜杠和 Unicode 字符，且永远不会映射到本地路径。桶的版本化始终开启。

每次 PUT 操作先以 SHA256 为地址暂存数据块（最大 256 KiB），并行尝试三个数据节点，默认要求每个数据块至少收到两个持久化确认；配置可以收紧为三个。只有在确认后，才通过一个元数据事务发布完整且有序的数据块清单、总 SHA256/长度以及新的 UUID 版本。写入失败会留下可被回收的暂存数据块，不会产生可见的部分对象。两个确认并不保证立即有三份健康副本。空对象不需要数据块。

幂等性回执按 `(bucket,key,request_key)` 唯一。相同清单/内容返回原有版本；内容变化则返回 409 冲突。已被永久删除的版本，其回执不能重新创建它。单次 PUT 上限为 4 MiB。

不带版本的 DELETE 会发布一个删除标记。最新读取/列举会隐藏该键，但旧版本读取仍然可用。删除标记本身可以被移除，移除后会显示上一版本。指定确切版本的删除会将其标记为已移除；保留策略则会在每个键上只保留最新的 N 个活跃版本（标记也计入），其余标记为已移除。宽限期（grace）保护最近被移除的字节不被回收。桶删除要求不存在活跃版本、删除标记以及进行中/正在完成的会话。被移除的行和回执会保留以支持去重，不会自动清除。

## 多部分上传状态机

多部分上传初始化会绑定桶、键、请求键、总大小/哈希以及一小时超时。分片 1–64 不可变，单个分片 1 字节至 1 MiB，逐个进行 SHA256 校验。被接受的分片已达到数据写入阈值并拥有持久化的清单。相同意图/分片字节的重放是安全的。分片本身不会以对象形式对外可见。

完成（complete）要求分片从 1 开始连续编号，总数不超过 256 数据块（即 64 MiB），并对整个有序内容与预期长度/哈希进行校验。在跨服务发布之前，会先写入并持久化一个 `completing`（正在完成）意图。分片在该点之后被冻结，不能更改或中止。发布使用原始请求键；崩溃发生在发布之前或发布之后但目录尚未提交 `complete` 结果时，重试或维护进程可以安全地从中断处继续。不会产生第二个版本。

过期只会中止 `active`（活跃）会话。维护进程会优先恢复 `completing` 状态的会话，永远不会假设原始超时意味着发布失败。活跃/正在完成的上传会持有数据块引用，防止其被回收；已完成会话的历史记录本身不会在其版本被移除后继续持有数据。读取时在内存中组装有界对象；这不是 GB 级的流式读取。

## 打包小数据块

大小不超过 64 KiB 的数据块共享一个追加式打包文件（append pack file）；更大的数据块各自拥有一个以哈希命名的独立文件。SQLite 将哈希映射到打包文件中的偏移量/长度或大文件路径。打包记录存储魔数、长度、SHA256、创建时间、有效载荷以及覆盖头部和有效载荷的 CRC32。PUT 在提交索引之前会对记录执行 fsync。索引提交过程中若被中断，会留下一个安全的孤立记录，可在启动时恢复。

GC 在删除小块时，会先追加并 fsync 删除墓碑（tombstone），然后移除对应索引条目，防止索引重建时把已回收的数据"复活"。大文件 PUT 会先刷盘，再以原子方式替换文件后更新索引；恢复流程会校验文件名和内容哈希。每次 GET 也会校验 SHA256。

`CURRENT` 文件标识权威的打包文件代际。启动时重建索引，只截断不完整的末尾记录。完整但 CRC 错误的记录保持不可达；副本可以对其进行修复。魔数或长度无效时，系统保守地关闭，等待运维介入而不是猜测新的边界。索引丢失不会导致有效的打包数据丢失。

压缩会持有节点锁，将当前被索引的活跃小块写入新的代际文件并 fsync，原子地切换 CURRENT 指针，重建索引，最后移除旧代际。活跃数据块损坏时，压缩会中止，等待修复。在指针切换前，重启会使用旧打包文件；切换后使用新打包文件。测试覆盖磁盘保留情况下的索引重建、尾部截断、墓碑处理和压缩行为，但不覆盖每一种断电/文件系统崩溃情形。

## 列举快照

协调器从每个元数据分片合并最新可见行（或所有活跃版本），对键排序后在目录中冻结至多 10,000 行。协调器在捕获快照期间排除自身产生的变更；不存在分布式 SQL 事务或独立的元数据写入器支持。

HMAC-SHA256 token 编码快照 ID/索引，并将服务端状态绑定到所有者、桶 UUID、前缀、版本模式和分页大小。token 五分钟后过期。后续分页使用已冻结的行，在此期间即使有新增或删除标记，枚举结果也保持稳定。这保证了枚举的稳定性，但不保证下载的可恢复性：显式删除某个版本可能使其已保存的列举条目变得不可读。若某个分片缺失，列举操作会直接失败，而不是返回部分结果。

## 清理、修复与垃圾回收

读取操作先解析清单，然后依次尝试各数据节点，直到找到并校验通过每个数据块的副本，之后再校验完整长度/哈希。如果没有找到好副本则返回 503，而不是返回被篡改的数据。读取不会假设修复已经发生。

管理维护流程会先恢复进行中的完成操作，再让活跃会话过期，然后收集所有元数据引用：活跃版本和宽限期内的最近被移除版本。进行中/正在完成的上传也会加入引用集合。如果有任何元数据来源缺失，扫描会停止。请求/内存上限为 50,000 个唯一数据块哈希，超限时显式失败。

清理（scrubbing）会在每个节点上校验每个活跃哈希，从好的副本源修复缺失/损坏的副本，并报告修复成功的副本、写入失败和不可恢复的哈希。随后让节点回收宽限期（默认 60 秒，测试中显式使用 0）之外的无引用数据块。协调器的串行化机制防止进行中的上传发布与标记-清扫之间产生竞争。节点锁保护 IO、压缩和回收。只要有任何版本或上传在引用，数据块就会被保留。实现是一个有界的全量扫描，不是分布式的生产级垃圾回收器。

正常复制大约需要 3 倍的字节存储。纠删码可以节省空间，但需要编码、多个可用分片和重建带宽。目前没有实现纠删码编解码器或独立故障域测试。如果所有校验副本都丢失，则不可恢复。

## 安全与范围

静态用户拥有私有桶。内部/管理 token 与 continuation 签名密钥分离。用户无法直接访问数据块/元数据端点。服务器只绑定回环地址。不宣称兼容 S3 Signature V4、IAM 策略、TLS、加密、公共桶、范围读取或预签名 URL。

目录和元数据是单一所有者的 SQLite 故障域，修复需要显式调度。测试保留磁盘，或在保留原始字节的同时模拟节点目录缺失。没有自动选主、自主多主机修复、在线分片迁移、生产生命周期/归档或 SLA。原书 100 PB、六个九耐久性和四个九可用性目标尚未验证。
