# Requirements: Real-time Gaming Leaderboard

依据根目录《System Design Interview.md》第 26 章。目标是月赛积分、Top 10、个人竞赛名次及前后四个显示位置；原书 2500 峰值加分 QPS/2500 万月活为未验证生产目标。

1. 信任的比赛服务提交唯一比赛 ID、获胜者、2–8 个参与者和结束时间；每胜恰好 +1，不接受客户端自报 points。
2. 所有已注册玩家进入当月赛季，包括零分用户。月份按 UTC，自然月边界开始新排名，不清除历史数据。
3. 结束月份决定归属，允许月末后 48 小时迟到；关闭后仅接受已处理事件的同内容重试。未来偏差最多 30 秒，未注册时的比赛拒绝。
4. 同分共享竞赛名次 `1 + 严格高分人数`；例如 1、2、2、4。显示顺序同分按用户 ID 升序，Top 10 恰好最多 10 人，不展开并列组。
5. 邻近窗口为前后最多四个显示位置，不是四个不同分数组；返回竞赛名次和唯一显示 position。
6. SQLite 权威比赛/积分日志持久去重，Redis sorted-set 是可重建投影。比分、事件与幂等凭据同事务提交。
7. 应用按固定用户哈希路由到相互独立的 Redis 主备对，使用真实复制、AOF 与日志重建；不是 Redis Cluster CRC16 路由或自动重分片。禁止缺失分片的部分排名，不自动猜测提升备用节点。
8. 读写暴露持久接收与投影完成的区别；正常写入等待短投影屏障，故障期间 202 保存，读不到完整屏障则 503。
9. 验证并发重复、同分/零分、跨月迟到、提交回滚、真实主进程退出/人工提升/AOF恢复、独立对账与重建，实测延迟。

参考容量上限为 10000 注册玩家，积分最大 10 亿。没有真实比赛反作弊、完整账号体系、自动 Sentinel/共识选主、跨机房 Redis、权威数据库 HA 或在线重分片。
