# 月度游戏排行榜参考设计

## 权威服务与进程边界

本实验室共有七个进程：一个权威 SQLite/HTTP 服务、两个 HTTP 投影节点，以及四个真实 Redis 进程（两对相互独立分片的主/备节点）。投影节点通过 HTTP 获取带校验和的分片事件页，并使用标准库 RESP2 客户端发出真实的 Redis 命令/Lua。没有 Redis mock、共享内存排名替代品，也不依赖此前章节的源代码。测试可以复用已安装/解压的 Redis 可执行文件，但并不打包捆绑。

SQLite WAL（synchronous FULL）存储玩家资料、注册时间、赛季、绝对权威分数、唯一比赛凭据（receipt），以及每个比分分片的连续事件序列。比分变更、事件与凭据在同一个事务中提交；提交前失败会全部回滚。源血缘（source lineage）UUID 与不可变的分片/宽限期配置在重启后保持不变。缺失或重建的权威状态不会被静默当作同一数据集。

权威服务让排名查询共享源读快照，公开变更、重建和对账独占。内部事件流绕过该锁，使投影器能够在公开请求等待屏障期间继续追赶。因此，在同一次全局排名查询的各阶段之间，源分数不会发生变化。这是有意以吞吐量换取可评估的快照模型；多个活跃权威进程或绕过此协调器独立写入的客户端不受支持。权威 SQLite 没有复制或自动故障转移。

## 可信比赛与月度成员资格

只有单独的游戏服务 bearer token 才能提交 `{match_id,winner,players,ended_at}`。不接受 points 字段；每次唯一胜局恰好加一分。参与者必须互不相同、在比赛结束前已注册，并且包含获胜者。这是对可信结果生产者的身份认证；它并不实现游戏反作弊，也不是比赛确曾发生的密码学证明。

比赛 ID 的唯一性是全局且持久的。参与者在哈希前会做顺序规范化。相同 ID/内容即使在赛季关闭后也返回原始凭据；内容不同则返回 409。凭据中的分数是原始受理时的分数，而不是新的当前排名。Redis 数据丢失不会导致再次加分，因为重放发送的是绝对分数而非增量操作。

赛季是自然的 UTC 月份。所有已注册玩家（包括零胜玩家）都会被播种（seed）进当前月份。新月键以零分起步并保留旧赛季。历史创建只包含在该月结束前注册的资料。比赛时间戳决定所属赛季，允许至多 30 秒的未来偏差；未来月份的比赛会被拒绝。新事件被接受到「月末 + 48 小时」为止（不含该时刻）；此后已有凭据可以重放而不发生任何变更。后来的账号不能认领更早的比赛。

受理截止之后，由管理操作执行的关闭（close）会创建不可变的 SQL 结算（settlement）：全板摘要、玩家数量，以及带名次/位置的 Top 10。重复关闭返回相同结果。截止后的迟到事件即使尚未调用关闭也会被拒绝。结算是权威 SQL 数据，不需要信任 Redis。资料可以更改显示名称，而不会改变历史数值分数或结算 ID/哈希。

## Redis 表示与精确并列

用户被分配到 `first_64_bits(SHA256(canonical_JSON(user_id))) % N`。每个月份/分片有两个 Sorted Set：

- 分数集合（Score set）：member=用户 ID，score=负的胜场数。按分数升序排列时，胜场最多者排在最前，并列时按 ASCII 用户 ID 排序。
- 顺序集合（Order set）：每个成员的 score 都是零；member=`%010d:(user_id)`，以 `1000000000 - wins` 作为十位数字前缀。其字典序即完整的显示顺序。

第二个集合使全局位置/邻居查询无需拉取一个巨大的同分数组。分数上限为 10^9，处于 Redis 双精度浮点可精确表示的整数范围内，也与固定的字典序前缀宽度一致。用户 ID 使用有界的 ASCII 字母/数字/下划线/连字符，使 SQL/Python/Redis 的并列排序结果一致。

竞赛名次（competition rank）是跨**所有**用户分片的 `1 + sum(ZCOUNT(score_set, -inf, exclusive(-wins)))`。显示位置（display position）是 `1 + sum(ZLEXCOUNT(order_set, -, exclusive(target_member)))`。因此并列用户共享名次，但占据唯一且确定的位置。`ZRANK` 本身并不用作竞赛名次。

Top 10 从每个分片获取各自的本地 Top 10，按胜场降序/ID 升序合并，恰好保留十行。这一结果是精确的，因为每个用户只存在于一个分片上；与加盐聚合键不同，候选者的分数从不在分片间拆分。全局所有领先用户都位于合并前缀中，因此可以从其第一个并列位置推算出竞赛名次。Top 10 不会为了展开并列而超出行数上限。

对于邻居窗口，每个分片在目标复合成员的上方和下方各返回最多四个条目。服务合并出每侧最接近的四个，加上目标本身，并为所有返回的不同分数获取严格更高的计数。结果行同时暴露名次与位置。这些是相邻的显示行，而不是完整的并列组或不同的名次层级。缺失任何一个分片都会使全局查询失败，而不是返回近似或部分排名。

## 原子投影与读取屏障

事件流具备分片所有权、源血缘、连续本地序列号和 SHA256 载荷校验和。投影器在应用之前验证整页。Lua 原子地更新绝对分数、移除旧的复合顺序成员、插入其替代者，并提交血缘/位置。旧的/过期页面不会加分。Lua 在执行变更前预校验偏移量与键类型；意外的键损坏会停止推进。空闲轮询不会重写未变化的游标/AOF 状态。

Redis 的进度与其投影数据存储在一起。Redis 状态丢失后从位置零开始，重放所有保留的权威事件，包括零分阶段的赛季注册。源血缘发生变化时以失败关闭（fail closed），直到显式重建。管理性重建只清除本应用的命名空间/月份键，然后由常规投影器重放。其他应用的旧 Redis 数据不会被清空；FLUSHALL 仅在对完全归本实验室所有的可丢弃实例进行测试时使用。

在公开读取之前，权威服务捕获所有当前源头并等待匹配的 Redis 血缘/位置。公开权威锁在其多阶段读取期间阻止更新的写入，因此到达这些头部的投影在用户分片之间构成一致的源屏障。正常写响应最多等待大约一秒以完成投影：200 表示已投影，202 表示比赛已持久受理但尚未完全投影。无法建立完整屏障的读取以 503 失败。网络截止时间是尽力而为，不是严格的响应时间 SLA。

资料名称使用按源profile_revision绑定的有界缓存，未命中时批量读取SQL；积分和Top10不使用应用缓存。内部状态暴露投影位置、观测到的源头、轮询时间与错误。独立对账在相同读取屏障的约束下，将所有已投影的 `(user,score)` 对与权威 SQL 进行比较。在 10000 玩家参考上限下，这是一次管理性全量扫描，而非生产级分布式审计引擎。

## 主/备与恢复语义

每个 Redis 主备对都使用密码、开启 AOF（`appendfsync always`），以及真实的异步 REPLICAOF 复制。经测试的 WSL 挂载工作区需要 `repl-diskless-load swapdb`；纯 AOF（`aof-use-rdb-preamble no`）在本实验中避免了基于 RDB 的磁盘加载。这是针对单个实例的测试配置，不是系统级内核改动，也不构成可用性保证。

投影节点通过短超时的 ROLE 探测来发现两个已配置端点的角色。必须恰好有一个可达的主节点。没有自动选举或 Sentinel。为了安全地故障转移，操作者首先隔离（fence）/停止旧主节点，然后用 REPLICAOF NO ONE 提升副本；返回的旧主节点必须配置为被提升端点的副本。出现两个可达主节点时以失败关闭。短的角色探测截止时间防止不可用的端点/WSL 端口转发器拖慢每一次排名请求。

复制可能滞后。提升一个过期的副本并不意味着授权过期排名：其游标必须追赶至权威源头，且日志（journal）会恢复错过的绝对更新。AOF 测试会先停止投影器，对被提升的 Redis 执行硬退出/重启，并在重启投影之前直接验证已保存的分数，从而区分 AOF 恢复与日志修复。另有独立测试清空自有 Redis 数据集、重新打开权威服务、通过对账检测被故意破坏的索引并重建它们。

本实验在停止自有 Redis 之前会检查服务器 run ID，并使用其已验证的进程 ID 注入硬退出。WSL 子进程只在隔离的工作区实验室目录下运行。测试保留本地磁盘；它们不演示跨主机仲裁、主机/磁盘丢失、AOF 断电保证，或从丢失的 SQLite 文件恢复权威服务。

## 分区替代方案与限制

分数范围分区可以从更高分区的计数推导排名，但当分数跨越边界时需要迁移玩家；密集的分数簇还需要范围再平衡。对用户做哈希可以避免普通加分的迁移，但需要 scatter/gather 来获得全局计数与候选者。额外的字典序索引高效地解决了确定性的并列位置。这是手动应用层分片，而不是把单个巨大 Sorted Set 键交给 Redis Cluster 哈希槽分布。

NoSQL 分数排序索引同样需要为热点月度分区做写分片以及跨分片排名聚合；二级索引最终一致的可见性会让读取屏障复杂化。本文不声称实现了 DynamoDB、Cassandra、分数范围迁移或 Redis Cluster，也没有对其做基准测试。代码只实现并验证了哈希分片算法。

静态的 admin/read/game/internal 凭据彼此不同；玩家不能直接加分。服务器与 Redis 端点使用回环地址。没有提供完整账号认证、TLS、限流网关、反作弊、权威服务 HA、自动故障转移、在线拓扑变更或日志/赛季保留策略。两个索引、保留的凭据/事件以及历史赛季会消耗额外空间。本实验室的 10000 玩家/10^9 分数上限、单活协调器与实测延迟并不能证明原书 2500 万 MAU/2500 峰值加分 QPS 的目标。
